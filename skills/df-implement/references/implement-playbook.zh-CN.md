## 1. Plan 忠诚度边界案例

三种判定：**OK**（实施自由——直接干）、**REPORT**（可以干或注明，但报告必须
浮出水面）、**STOP**（停下任务，把决定交回委派方）。标"禁止"的意思是：悄悄
干了就是失职，不是这件事本身不行。

| 情况 | 判定 | 理由 |
|---|---|---|
| Plan 说"加输入校验"；自然的写法需要一个小 helper | OK | 内部拆分是第 7 级的自由 |
| Plan 的 Design 点名 A 模块；代码放 B 模块更顺手 | STOP | 模块归属是明说的约束。如果你觉得边界本身划错了，那是改 Plan 的事，不是你的决定 |
| 需要的 helper 仓库里已有，但 Plan 没提复用 | OK，复用 | 阶梯第 2 级压过 Plan 的沉默；报告里注明 |
| 在任务旁边发现一个既有的 bug | REPORT | 写进 `Notes/deviations`；没被要求就不修——范围归委派方 |
| 本任务的 bug 根因在声明文件之外 | REPORT，经同意后修 | 根因规则适用，但跨出声明文件边界就是改范围 → 要一句明确的放行 |
| Verify 命令老老实实跑了两次都失败 | STOP | 两次失败说明设计或环境有问题，不是你努力不够。带两次输出上报 |
| Design 假设的 API 能力代码里没有 | STOP | Plan 按字面立不住；现凑替代品就是"Plan 的精神" |
| 两条验收标准互相矛盾 | STOP | 矛盾在实施层无解 |
| 数据模型驮不动计划的行为 | STOP | 模型级缺口 → 改 Plan |
| 一次依赖升级能干净地满足需求 | REPORT | 写明阶梯第 5 级理由后允许；升级动 lockfile——必须浮出水面 |
| 已知天花板的性能捷径（全局锁、O(n²) 扫描） | OK，带标记 | `// simplified:` 一行，含升级路径 |
| 为省事砍校验、错误处理、安全 | 禁止 | 永远不许简化掉——什么标记都不合法 |
| 放宽验收标准让测试通过 | 禁止 | 断言比 Plan 要的少的绿灯测试，是穿着绿衣服的失败交付 |
| "顺手"重构旁边的代码 | 禁止 | 搭车重构污染评审 diff；作为后续建议提出 |
| 测试实现细节（fixture 风格、断言形式） | OK | 测试必须先存在、必须钉住行为；风格归你 |
| Plan 没列的测试，但代码暴露了一个边界情况 | OK | 守护真实行为的测试永远不算范围蔓延——加进报告 |

**表格背后的模式**：Plan *明说的*约束是墙；Plan *没说的*都归你；让 Plan
*按字面立不住*的东西是停车信号。

## 2. 阶梯实战爬法

每个示例：要求 → 爬法 → 落点 → 报告行。

**"给这个接口加限流。"**
爬法：第 1 级——限流在 Plan 的验收标准里吗？在 → 不可跳。第 2 级——
`rg -il "rate.?limit"` 发现网关已有限流中间件、支持按路由配置。落点：把
路由注册进现有限流器配置，约 3 行。报告：
`Done: 经既有网关限流中间件加限流（纯配置，3 行）。Skipped: 无——第 2 级复用。`

**"解析上传的 YAML 配置并校验必填字段。"**
爬法：第 3 级——语言标准库的 YAML 解析器管解析。校验上跑第 1 级——必填
字段检查是信任边界输入校验（永远不许简化掉），所以就算没有现成库也要写。
落点：标准库解析 + 10 行显式必填校验。报告：
`Done: 标准库 yaml 解析 + 显式必填校验。Skipped: 配置 schema 库——10 行代码不值得引依赖。`

**"缓存这些 API 响应。"**
爬法：先跑第 1 级——缓存写进 Plan 了吗？写了，它就存在。第 5 级——已装的
HTTP 层自带响应缓存、支持 TTL。落点：开开关配 TTL，约 2 行配置。第 7 级
（手搓缓存类）永远轮不到。报告：
`Done: 经 <已装层> 加响应缓存，TTL 60s。Skipped: 自定义缓存类——现成缓存实测不够用时再加。`

**"修复：用户购买后偶尔看到过期的总额。"**
爬法：症状是"总额过期"；根因候选在读路径、写路径或缓存层。动手前 `rg`
总额函数的调用方 → 发现写路径漏了一个缓存键的失效。落点：在所有购买路径
汇合的地方加一行失效——不是在读路径上贴刷新膏药。报告用 `file:line` 指出
缺口位置和修复位置，写明根因。

要内化的直觉：每次爬都从第 1 级开始、手里拿着 Plan 的验收标准；每个落点
都能一句话说清。

## 3. dev-flow Plan Task 里的 TDD 接线

dev-flow 的 Task 到手时就是按 TDD 预制的。Changes 列表第一条永远是 RED。
完整循环：

```text
1. RED    — 按 Behavior 规格写失败测试。跑它。
           确认它以正确的理由失败（断言失败，
           不是 import 错误/笔误）。
2. 写回   — RED 阶段，把 Task 的验收标准变成
           真实命令，就地写回 Plan（两拍 AC 契约：
           判据式 AC 以后过不了 `complete`；
           命令必须现在就存在）。
3. GREEN  — 通过测试的最小代码。写的过程爬阶梯；
           测试不动。
4. REFACTOR — 测试绿着清理；重构改变测试钉住的东西时
           测试同步调整。
5. Verify — 跑 Task 的 Verify 命令。必须通过。
6. Done   — 勾掉 Task 的 Done 复选框，回填实际改动文件，
           提交（一个 Task 一个提交）。
```

实践中最容易咬人的规则：

- **RED 必须以正确的理由失败。** 在 import 上报错的测试不是失败测试，是坏
  测试。先修好测试本身，再看断言失败。
- **RED 红之前不写实现。** 先写修复后补测试，测试就会变成同义反复。
- **`TDD: false` 也留一个能跑的检查**——基于 assert 的自检或一个小测试。
  琐碎的一行代码是唯一全豁免。
- **AC 写回不是可选项。** 忘了它，`complete` 硬门禁晚点卡住，还得有人在
  代码已绿之后回来补 RED 阶段的活——这是最贵的顺序。

## 4. 偏离协议——停下上报格式

三种情况触发停车：Plan 按字面立不住（设计缺口、自相矛盾、能力缺失）、根因
修法超出声明范围、同一个 Verify 失败了两次。其他情况都装得进报告的
`Notes/deviations` 行。

停车时用这个格式，让委派方一眼读完就能拍板：

```text
STOP —— Plan 偏离

Task: <任务名 / 行为组>
Found: <与 Plan 矛盾的东西，带 file:line 证据>
Why the Plan can't hold: <一小段——讲机制，不讲故事>
Options:
  A. <路径> — 代价：<diff 大小 / 改什么>
  B. <路径> — 代价：<…>
Awaiting: 改 Plan，或指定选项。
```

绝不能用这些代替停车：现场凑替代设计、悄悄实现需求的"精神"、靠膨胀 diff
硬把 Plan 顶起来、发现之后继续写代码"好歹有点东西可交"。一个停下并交出
清晰偏离报告的任务是成功的任务——失败模式是偏离直到评审才被发现。

够不上停车、值得一提的边界情况进报告：

```text
Notes/deviations: 复用了既有 <X>（Plan 对复用沉默）；在 <Y> 的 file:line
发现既有 bug——未修，超出范围。
```

## 5. 你的证据报告如何喂给评审

评审者（rook，经 df-implement-review）靠你交回去的东西干活。报告的每一行
都有下游消费者：

| 你的行 | 评审消费点 | 造假或漏写的下场 |
|---|---|---|
| `Touched` | Q1 范围核对（`git diff --name-status` vs 声明） | 动了但没报的文件 → "未声明改动" WARNING |
| `Verified` | Q4 测试完整性——命令是可复跑的证据 | 不带命令的"绿了"按未验证处理 |
| RED 阶段 AC 写回 | `complete` 硬门禁 + Agent Verification | 缺命令会卡住整个 Plan |
| `// simplified:` 标记 | 精简扫描——转成有据可查的 INFO，不是赘肉 finding | 没标记的捷径读起来是未声明的债 → REVISE |
| `Skipped` 行 | 精简计数（`net: -N lines possible`） | 没有——这是加分项；没跳过东西才省略 |
| 偏离备注 | Requirement Questions / 上下文 | 评审才发现的未披露偏离 → BLOCK，不是 WARNING |

一个测试的下限两边都有保护：评审永远不会把你的单个冒烟测试当赘肉，你也
永远不跳过它。非平凡逻辑零测试，WARNING 上写着你的名字。

报告边干边写——每批之后——不要最后凭记忆写。凭记忆写的报告就是文件漏报
和命令编造的出生地。
