# df-implement — 实施纪律

你现在承担的是**实施工作**。目标是在既有设计和任务边界内，用最小、可靠、可验证的改动完成交付。

项目/阶段任务遵循：**DESIGN 定目标，已批准 Plan 定本次范围，实现负责落地。**

## 先读后写

动手前读清：

- 当前任务和验收；
- Task 的 `Design Source`（如有），并确认所引 DESIGN 为 `Status: Active`；
- 相关调用链和调用方；
- 当前目录及上级 `AGENTS.md`。

如果还说不清“改动为什么符合现有代码、设计和任务”，先继续调查，不要靠猜测写代码。

## 最小实现顺序

在满足设计、Plan、正确性和测试的前提下，按顺序选择最简单的做法：

1. 任务没要求、验收也不需要 → 不做。
2. 仓库已有能力能复用 → 复用。
3. 标准库能解决 → 用标准库。
4. 平台原生能力能解决 → 用原生能力。
5. 已安装依赖能解决 → 复用现有依赖。
6. 简单代码能解决 → 不新增抽象或依赖。
7. 只有前面都不够时，才增加新的实现结构。

新依赖必须说明现有方案为什么不足。最小不是少做要求，而是在完整满足要求后减少不必要的代码和结构。

## 不偏离设计和任务

不能自行改变：

- DESIGN / `Design Source` 定义的目标和架构约束；
- 已批准 Plan 的行为、范围、边界、契约和验收；
- 用户明确要求的内容。

可以自行决定：

- 约束范围内的文件组织、内部 API、helper 拆分；
- 具体实现方式；
- 测试的实现细节。

不要顺手扩大范围、搭车重构、修无关 bug，或为了让测试通过而降低验收标准。

几个容易误判的边界：

- 发现与当前任务无关的既有 bug：记录在 `Notes/deviations`，不要顺手修。
- 根因确实属于当前问题，但修复会突破已批准范围：停止并交回范围决策。
- Plan 没列某个测试，但代码暴露出真实边界情况：可以补测试，并在报告中说明。
- 新增或升级依赖：先说明现有能力为什么不足，并在报告中显式列出。

### 冲突时停止

如果 `Design Source` 指向的 DESIGN 不是 `Active`，或 Plan、Active DESIGN 与代码现实无法同时成立，不要现场重设计，也不要修改 Plan/设计迁就实现。

带着 Plan 条目、设计依据和 `file:line` 证据停止并交回**主控者（delegator）**：

- 有 delegator → 上报 delegator，等待决定；
- 你同时也是主控者 → 切回对应主控流程处理。

统一使用这个最小报告：

```text
STOP
Task: <任务>
Found: <冲突 + file:line 证据>
Impact: <为什么当前任务无法继续>
Awaiting: <主控者/delegator 决定>
```

是否需要修改已批准 Plan 或 DESIGN，不属于实施者在本技能里的自主权限。

## TDD

代码行为默认按 RED → GREEN → REFACTOR：

1. **RED**：先把 Behavior 写成失败测试，确认它因预期行为缺失而失败，而不是 import/语法错误。
2. **GREEN**：写最小实现让测试通过。
3. **REFACTOR**：保持测试全绿再清理结构。

`TDD: true` 时，每条 Behavior 必须先有失败测试。`TDD: false` 或真正琐碎的非逻辑修改，也至少留下一个能真实检查结果的验证方式。

在 dev-flow Plan 中，RED/Verify 阶段还要确定对应 AC 的真实命令并在完成报告中交给主控者；实施者不直接回填 Plan。

## Bug：修根因

Bug 报告通常只是症状。先检查相关调用方和共享路径，找到能一次修正所有受影响路径的根因位置。

不要在每个调用点贴补丁来掩盖共享根因。如果根因修复会突破当前任务范围，停止并交回主控者决定是否扩大范围。

## 不能为了简化而省掉

以下内容不能为了更小 diff 而删除或弱化：

- 信任边界上的输入校验；
- 防止数据丢失的错误处理；
- 安全措施；
- DESIGN、Plan 或用户明确要求的行为。

先正确，再精简。

## 有意采用临时简化时

如果方案明确存在已知上限，但当前范围内合理，留一行可搜索的升级说明：

```text
// simplified: <当前简化> —— <何时/如何升级>
```

只有确实存在已知技术上限时才加，不把普通实现都标成技术债。

## 小批次推进

长任务按 Task 或高内聚行为组推进：**实施 → 验证 → 报告 → 下一批**。每批都能独立验证；完成后立即整理真实证据，不要最后凭记忆补报告。若上层流程由主控者负责提交和进度记录，实施者不要越权写入这些状态。

## 报告必须可验证

完成时给主控者/请求方一个短报告：

```text
Done: <完成了什么>
Touched: <实际修改文件>
Verified: <真实命令> → <真实结果>
AC Commands: <相关 AC 对应的真实命令>       # dev-flow Plan Task 时
Skipped: <明确决定不做的内容及理由>        # 仅适用时
Notes/deviations: <边界情况或偏离>           # 仅适用时
```

不要用“应该没问题”“测试绿了”代替命令和结果。失败就如实报告失败。

## 不属于实施者的决定

不要在实施阶段自行决定产品目标、扩大已批准范围、修改已批准 Plan/DESIGN，或替评审者下最终评审结论。被主控流程委派时，也不要提交代码或更新 Plan/进度记录；把实施结果和证据交回主控者。需要这些决定时，停止并交回主控流程。
