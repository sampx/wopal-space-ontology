## 1. 通读 Plan

在运行任何探针之前，带行号完整读一遍 Plan。阅读时建立三份清单：

1. **断言** —— 每一条具体的事实性声明（计数、路径、行锚点、文档章节、ID、命令、flag）。
2. **符号** —— 反引号内每个形似代码的标识符，连同消费它的 Task 和应当产出它的 Task。
3. **文件** —— 出现的每个文件路径，连同出现场景（Task 的 `Files`、`Changes`、`Affected Files` 行、`Pre-read`、测试路径）。

然后开始探针。不要在阅读与探针之间来回切换——每次回读 Plan 的代价都高于省下的探针成本。

从一开始就留意 Plan 自己声明的执行模式：Plan 可能声明"wave 表达依赖层级，不代表并行批次"，在同一棵共享 worktree 内顺序执行。这一句话会改变 C1 的重叠判定与 C5 的顺序判定。

## 2. C1 — 产物闭合

### 检查为何存在

两份彼此独立的清单在描述同一批工作：各 Task 的 `Files`/`Changes`，以及 Plan 级的 `Affected Files` 表。它们在不同时刻写成，会漂移。漂移意味着要么发生了契约外的改动，要么声明的范围从未交付。

### 流程

1. **提取各 Task 的文件。** 对每个 Task，从 `**Files**` 与 `**Changes**` 收集路径。
2. **提取表格文件。** 从 `## Affected Files` 各行收集路径。
3. **双向求差。**
   - `task_files − table_files` → 未被范围契约覆盖的工作
   - `table_files − task_files` → 有声明范围却无产出方
4. **核对操作类型。** 对每个声明为新建的文件，确认它尚不存在；对每个声明为删除的文件，确认它确实存在；对声明为修改的，确认它存在。
5. **检查同 wave 重叠。** 按 wave 列出文件。仅当 Plan 声明并行执行时，同一 wave 内的交集才算冲突。若 Plan 说明 wave 只是顺序执行的依赖层级，重叠是预期内的——不要报。

### 严重度

| 情形 | 严重度 |
|---|---|
| 表格中的某行没有产出它的 Task | BLOCKER |
| Task 修改了文件，但该文件不在其 `Files` 字段中 | WARNING |
| Task 的 `Files` 含某个不在 `Affected Files` 中的路径 | WARNING |
| 声明为新建的文件已存在 / 声明为删除的文件不存在 | WARNING |
| Plan 声明并行执行时，同 wave 文件重叠 | BLOCKER |
| Plan 声明顺序执行时，同 wave 文件重叠 | 不是发现 |

### 常见误报

表格行有时会写下并非文件的叙述性路径（例如由代码而非 Plan 产出的运行态产物名）。报"缺少产出方"之前先看 `Role` 列——若该行记录的是代码产出的产物，它不需要 Task。

## 3. C2 — 符号闭合

### 检查为何存在

跨 Task 的 Plan 在接缝处断裂。后置的 Task 调用了某个函数、错误码、导出类型、常量、fixture、环境变量或 CLI flag，而没有任何前置 Task 创建它——或者创建时拼写不同。Plan 读起来是连贯的，执行时撞上未定义标识符。

### 流程

1. **收集消费方。** 按顺序走过各 Task，收集被*使用*的、形似代码的反引号标识符：函数与方法调用、大写下划线常量、导出类型、fixture、CLI flag、环境变量，以及文件的导出物。
2. **收集生产方。** 收集各 Task *声明*的标识符："登记 X"、"创建 Y"、"导出 Z"，以及将承载它们的新文件路径。
3. **把每个消费方匹配到生产方。** 确认：
   - Plan 中某处存在生产方
   - 两边拼写完全一致
   - 生产方所在 Task 在声明的顺序上早于消费方
4. **检查登记完整性。** 当某个 Task 声称登记*一组*符号（"登记五项错误码：A、B、C、D、E"）时，核验 Plan 中其他地方用到的每个符号都在该集合内——并确认没有 Task 往 Plan 从未列出的文件里登记。

### 严重度

| 情形 | 严重度 |
|---|---|
| 消费的符号在 Plan 中找不到任何生产方 | BLOCKER |
| 生产方名称与消费方预期的名称不一致 | BLOCKER |
| 生产方所在 wave 晚于消费方 | BLOCKER |
| 生产方存在，但其导出/注册位置未声明且对接线有影响 | WARNING |
| 生产方的文件不在 `Affected Files` 中 | 改记入 C1 |

### 效率提示

本检查完全静态——只需要 Plan，不需要仓库。读完 Plan 后一次做完。它是单位投入产出最高的检查，因为接缝失败既常见，又对形式校验器完全不可见。

## 4. C3 — 事实核验

### 检查为何存在

Plan 是针对某个代码心智模型写成的，而该模型常由更早的阅读拼装而来。模型一旦过期，每个 Task 都继承这个错误，并且它在执行中途、上下文已花掉之后才暴露。仓库是唯一的权威。

### 流程

按断言类别逐类机械核验。绝不要用"看起来合理"把一个断言带过去。

| 断言类别 | 探针 | 是否承重 |
|---|---|---|
| 计数（"36 项能力"、"8 个技能"） | 在真相源里数一遍 | 是——计数正是工作的依据 |
| 路径 / 文件名 | `test -e`、`ls`、`rg --files` | 是 |
| 行锚点（"`file.ts:619-669`"） | 在目标版本上 `sed -n 'Np' file` | 视情况——核验*陈述*，容忍小幅漂移 |
| 引用的文档章节 | `rg -n '^#{2,3} Section' doc.md` | 是——它是 Plan 的权威引用 |
| 决策 / Gap 编号（`D-xx`、项目 gap 或 issue 编号） | 在真相源中 `rg -n` 该编号 | 是 |
| AC 中的命令与 flag | 确认命令存在且接受该参数 | 是 |
| 已存在 vs 新建 | `test -e` | 是 |
| 已存在 vs 删除 | `test -e` | 是 |
| 环境状态声明（"这些符号链接存在"） | 检查真实环境 | 是——若它正是工作的正当性所在 |

### 版本纪律

声明每一次事实核验所依据的版本：Plan 的 `Base Commit`、worktree HEAD，或集成分支 HEAD。事实会随提交漂移；不带版本锚定的发现，在任何人提交之后即不可信。

Plan 声明了 worktree 时，代码事实必须在**该 worktree 的 HEAD** 上探查——不要在集成分支上，它可能领先或落后。

### 严重度

| 情形 | 严重度 |
|---|---|
| 承重断言不成立——改动的正当性正建立在它之上 | BLOCKER |
| 断言不成立，且建立在它之上的 Task 会做错事 | BLOCKER |
| 描述性漂移，不影响实际工作（大文件中锚点略偏） | WARNING |
| 表面漂移（计数不精确、顺序差异） | INFO |
| 无法从工作区定案的断言 | `Unverified` —— 不是发现 |

### 锚点漂移的判定

行锚点的作用是定位代码，不是要求逐字精确。探查锚点并读它上下几行：
- 落在所述结构上 → 通过
- 落在附近，结构清晰可辨 → 通过
- 落在无关代码上，或结构在别处 → WARNING
- 所述结构在声明的版本上不存在 → 承重则 BLOCKER，否则 WARNING

## 5. C4 — 契约一致

### 检查为何存在

Plan 在一张契约网中执行：设计文档、项目 `AGENTS.md`、既有接口、同族惯例。Plan 与其中之一相悖却不说明时，交付物就违反了一份没人重新协商过的契约。

### 流程

1. **收集已声明的权威。** 从 Technical Context 与 `Pre-read` 中，列出 Plan 声明为依据的设计文档、规则文件与接口。
2. **定位每一项声明的依据。** 确认引用的章节确实存在，且表述与 Plan 所述一致。
3. **对每项 Plan 决策，找到对应的权威表述。** Plan 做出的选择若文档亦有涉及，逐项比对。
4. **对任何偏离归类：**
   - **已承认** —— Plan 说明了该偏离并给出理由，或声明将同步更新文档 → 不是发现
   - **已延后** —— Plan 明确排除（例如 Out of Scope 并给出理由）→ 不是发现
   - **静默** —— 既未承认也未论证的偏离 → 发现

### 严重度

| 情形 | 严重度 |
|---|---|
| 与设计文档或项目规范的静默偏离 | WARNING |
| 偏离破坏了已声明的安全约束 | BLOCKER |
| Plan 引用的文档章节不存在，或并未表述 Plan 所称内容 | WARNING（若该引用承重，改记入 C3） |
| Plan 已承认并论证该偏离 | 不是发现 |

### 判定说明

并非每一条文档表述都具有约束力。较旧的文档可能描述的是已被取代的模型，而 Plan 实现的是当前模型。判定冲突之前，先确认*对于本 Plan 所实现的模型*，哪份文档是权威。若 Plan 针对的是较新的模型、而旧文档仍在描述旧模型，问题在于 Plan 是否承认了这一点——而不在于谁"更对"。

## 6. C5 — 可实施性

### 检查为何存在

Plan 就是实施方拿到的东西。执行某个 Task 的一方从 Plan 及其中点名的文件出发，而不是从作者脑内未写下的上下文出发——只有结合那部分上下文才能成立的 Task，会卡住、临时发挥或跑偏。另外，无人认领的验收标准永远不会被证明。

### 流程

**第一步 —— AC 归属。**
1. 按编号列出 `### Agent Verification` 中的每条 AC。
2. 从每个 Task 的 `**Verification Intent**` 收集被引用的集合。
3. 求差。未被引用的 AC 没有归属。
4. 对确实跨 Task 的 AC，确认它们被显式标注为跨多个 Task，而不是静默地无人认领。
5. 检查归属层级：可自动化的验证（测试、lint、typecheck、静态检查、可脚本断言的项）应位于 Agent Verification；只有需要人工观察的标准才属于 User Validation。放错层级会浪费相应责任方的时间。

**第二步 —— 交接就绪度。**
对每个 Task，自问：只知本 Plan 与声明的 `Pre-read`，实施它的一方能否开工：
- 前置 Task 的接口、类型与产出是否被**点名**而非暗示（"使用 Task 2 的响应结构"偏弱；"调用 `parseConfig(path)` 返回 `ParsedConfig`"才算就绪）？
- Task 自身的产出是否定义得足够清楚，让*下一个* Task 能消费？
- `Pre-read` 列出的文件是否正确——以及这些文件是否存在？

**第三步 —— 顺序。**
- 声明的 wave/依赖顺序与依赖表一致（没有消费方先于生产方）。
- 声明的执行模式与现实相符：若 Plan 说"wave 是依赖层级，在同一 worktree 内顺序执行"，不要因同 wave 文件重叠而扣分；若它声称 wave 并行，则核验文件是否互不重叠。
- 没有 Task 依赖某个 Plan 从未安排创建的产品或产物。

**第四步 —— 可运行性。**
- 每条 AC 命令都能在 Plan 声明的环境中运行：正确的项目根、存在的脚本名、可用的工具链，以及所需的任何准备已作为步骤存在。
- 需要状态型前置条件的 AC（运行中的服务、已构建的产物、临时 home）要声明该前置条件，或包含建立它的步骤。
- 失败语义被反转的命令（否定式断言）要正确声明预期的退出码。

### 严重度

| 情形 | 严重度 |
|---|---|
| AC 无 Task 认领 | WARNING |
| AC 命令按声明无法在所述环境运行 | BLOCKER |
| 可自动化的验证被放进 User Validation | WARNING |
| 仅能人工观察的标准被声称为 Agent 可验证 | WARNING |
| Task 无法仅凭 Plan + 声明的 `Pre-read` 开工 | WARNING |
| 声明的顺序与声明的依赖矛盾 | BLOCKER |
| `Pre-read` 指向不存在的文件 | WARNING |
| AC 运行前需要未声明的前置条件 | WARNING |

### 判定说明

对属于显而易见序列中一步的 Task，不要勉强报交接缺口。标准是"一个有能力的实施方能否推进"。只在缺失信息会导致走错方向时才报——必须靠猜的接口、有歧义的产出形态，或实施方无法自行发现的依赖。

## 7. C6 — 目标保真

### 检查为何存在

代价最高的失败是 Plan 通过了所有结构检查却仍然欠交付：Goal 的组成项没有 Task、决策被悄悄缩成第一版、验收标准根本无法失败。

### 流程

1. **拆解 Goal。** 把 `## Goal` 拆成各自有独立意义的组成项。逐项找出交付它的 Task。
2. **把决策追踪到交付。** 对 Key Decisions 中的每个 `D-xx`，找出实现它的 Task，并确认交付内容与决策的范围相符。
3. **扫描缩水措辞。** 在 Task 文本中搜索 `v1`、`v2`、"简化"、"暂时静态"、"硬编码"、"placeholder"、"基础版本"、"最小实现"、"未接入"、"未连接"、"stub"、"后续增强"、"稍后接入"、"暂时跳过"、"暂时"。
4. **逐条裁定。** 依次问两个问题：
   - 该缩水是否与 Goal 或某个 `D-xx` 相矛盾？若不矛盾 → 不是发现。
   - 某个 `D-xx` 或范围声明是否**授权**了该缩水？若是 → 不是发现。Plan 明确声明时分阶段交付是正当的。
5. **检验每条 AC 的可证伪性。** 自问：若功能坏掉，这条命令会失败吗？无论功能好坏都通过的 AC——在需要证明行为的地方只断言存在性，或只是复述改动——是装饰。

### 严重度

| 情形 | 严重度 |
|---|---|
| Goal 组成项无 Task 覆盖 | BLOCKER |
| 决策被缩水而 Plan 未承认 | BLOCKER |
| 缩水措辞由 `D-xx` 或范围声明授权 | 不是发现 |
| AC 无 Task 认领 | WARNING |
| AC 无法失败 | WARNING |
| Goal 被提及但从未以可检验的形式陈述 | WARNING |

### 为什么缩水的决策是 BLOCKER 而非 WARNING

缩水的交付一旦走到 `verify`，执行预算已经花完。在执行之前抓住它，正是本审查的全部价值。若 Plan 想要分阶段交付，正确做法是*把它说出来*——把它表述为交付物、调整 Goal，或拆成显式的后续项。不能通过的是静默缩水。

## 8. 严重度校准

四个类别，按读者应采取的行动定义：

| 类别 | 含义 | 检验问题 |
|---|---|---|
| **BLOCKER** | 照此执行会失败、违反契约，或欠交付 Goal | "这样交付出去，是坏的，还是不诚实的？" |
| **WARNING** | 执行能成功，但 Plan 不安全、有歧义，或在本应验证处未验证 | "这会带来返工，还是会掩盖缺口？" |
| **INFO** | 值得知道、无需行动的改进 | "一个合理的作者会耸耸肩吗？" |
| **Unverified** | 无法从工作区定案的断言 | "我是不是没能查这个？" |

刻意缺席的：**体量/数量阈值**。上下文预算按 Task 管理，不按 Plan 管理；大而内聚的 Plan 是正常的。永远不要把 Task 数、文件数或 wave 数作为发现上报。

### 校准练习

| 情形 | 正确判定 |
|---|---|
| Plan 有 12 个 Task，全部互相依赖，Plan 声明不拆分并给出理由 | 不是发现（体量不是缺陷） |
| Plan 声明某文件为新建，但该文件已存在 | WARNING（前提过期；实施者会临场发挥） |
| Task 引用了没有任何其他 Task 创建的函数 | BLOCKER |
| 某 Task 登记 5 个错误码，后面某个 Task 用了第 6 个 | BLOCKER |
| 锚点 `file.ts:964` 落在所述函数上，实际在 967 行 | 不是发现 |
| 锚点 `file.ts:964` 落在无关代码块，函数在 1200 行 | WARNING |
| Plan 与它同时引用的设计文档矛盾，且未承认 | WARNING |
| Plan 与设计文档矛盾，并声明"本 Plan 取代文档 Y 的 §X" | 不是发现 |
| AC 是 `rg -c 'pattern' file ≥ 1`，而该文件在功能损坏时也可能包含该模式 | WARNING（可证伪性弱） |
| 缩水为 `v1`，而 `D-04` 说"先用静态数据，后续动态化——本 Plan 交付静态层" | 不是发现 |
| 缩水为 `v1`，而 `D-04` 说"配置展示计算出的成本" | BLOCKER |
| 因缺少沙箱而无法核验的担忧 | `Unverified`，永远不是发现 |

## 9. 完整示例

### 示例 A — 符号闭合抓出未登记的错误码

**Plan 形态**：Task 2 创建错误码模块，登记五个码：`A_MISSING`、`A_INVALID`、`S_MISSING`、`S_INVALID`、`C_UNRESOLVED`。Task 4 描述一个失败分支"以 `TEMPLATE_MISSING` 快速失败"。

**探针**：列出已登记的集合，列出 Plan 中所有被使用的 `UPPER_SNAKE` 码，求差。

**发现**：
```yaml
check: C2_symbol_closure
severity: blocker
plan_location: "{plan}.md:{Task 4 分支所在行}"
reality: "已登记集合见 {plan}.md:{Task 2 声明所在行}；其中没有 TEMPLATE_MISSING"
impact: "Task 4 的失败分支无法按字面实现；实施者会临时新增第二个登记点，或复用一个错误的码"
fix: "把 TEMPLATE_MISSING 加入登记 Task，或改为引用一个已存在的码"
```

### 示例 B — 产物闭合抓出双向漂移

**Plan 形态**：Task 2 的 `Changes` 包含"第 3 步：在 `src/lib/errors.ts` 登记五个错误码"。Task 3 包含"第 2 步：在 `src/lib/errors.ts` 登记 `SYNC_APPLY_FAILED`"。`Affected Files` 表有十个组件的行；里面没有 `src/lib/errors.ts`。

**发现**：
```yaml
check: C1_artifact_closure
severity: warning
plan_location: "{plan}.md:{Task 2 第 3 步所在行}"
reality: "{plan}.md:{行范围} 的 Affected Files 表中没有 src/lib/errors.ts 这一行"
impact: "该文件被两个 Task 修改，却位于 Plan 声明的文件范围之外"
fix: "补一行 Affected Files，指明该文件以及会触碰它的 Task"
```

### 示例 C — 承重前提上的事实核验

**Plan 形态**：Technical Context 断言"旧 schema 路径已从本体中消失，因此初始化必然失败"。Task 4 移除读取该路径的代码，AC#7 断言全仓搜索旧标识符零命中。

**探针**：在声明的版本上，搜索仓库中的旧路径，以及该读取方的调用者。

**发现**：
```yaml
check: C3_fact_verification
severity: blocker
plan_location: "{plan}.md:{前提所在行}"
reality: "{file}:{line} 仍在导入并调用旧读取方；Plan 的搜索清单未包含该调用点"
revision: "{commit}"
impact: "『不存在其他调用者』这一前提不成立；那条全仓 AC 无法通过，因为仍有未点名的调用点存在"
fix: "把剩余的调用点写入某个 Task 的范围，或加入移除 Task"
```

注意：一旦核验了前提，AC 本身就暴露了这个缺陷——Plan 自己的验收标准会在 `verify` 阶段失败，而那时整个执行预算已经花完。这正是 C3 存在的意义。

### 示例 D — 正确地*不*上报

**Plan 形态**：六个 Task、11 行 `Affected Files`、四个 wave；某个 `D-10` 声明"单 Plan 交付，不按任务数量拆分；各 Task 相互依赖；上下文预算按 Task 管理"。

**正确处理**：不因体量、Task 数或文件数报任何发现。`D-10` 是作者显式且有理由的决策。如有价值，记入 Positive Findings（"单 Plan 决策是显式的，理由也已说明"）。如果审查模板诱使你去报"6 个 Task 超过了推荐的 2–3"，那个模板已经不存在了——这里没有这条规则。

### 示例 E — 可实施性抓出无人认领的验收标准

**Plan 形态**：13 条 Agent Verification AC。六个 Task 声明了 `Verification Intent`；被引用的集合覆盖 AC 1–6、8、10、12、13。AC 7、9、11 未被任何 Task 引用；只有 AC#10 带有显式的"跨 Task"标注。

**发现**：
```yaml
check: C5_executability
severity: warning
plan_location: "{plan}.md:{AC 7、9、11 所在行范围}"
reality: "没有任何 Verification Intent 引用它们；只有 AC#10 标注为跨 Task"
impact: "三条验收标准没有归属，执行计划中没有任何环节负责证明它们"
fix: "把每条 AC 指派到某个 Task 的 Verification Intent，或显式标注为跨 Task"
```

## 10. 报告骨架

```markdown
# Plan 审查 — {plan-name}

## 概要
- 审查类型: Plan
- 判定: PASS | REVISE | BLOCK
- 统计: Blocker N / Warning N / Info N / Unverified N
- 参照版本: {revision}

## Blocker
### B-01: {标题}
- Plan 位置: `{plan}.md:{line}`
- 现实现实: `{file}:{line}` / `{output}` — {冲突}
- 影响: {执行时的失败模式}
- 修复方向: {补什么、改什么}

## Warning
{同 Blocker}

## Info
{每条一行}

## Unverified
- {断言} — 未验证原因: {为什么查不了}

## Requirement Questions
{仅当需求本身有歧义时}

## Positive Findings
- {已核验的项 —— 写明核验方式}

## UNCOVERED CHECKS
{仅当有检查未能完成时}
```

### 判定决策

- 出现任何 Blocker → `BLOCK`
- 无 Blocker，但至少一个 Warning → `REVISE`
- 只有 Info（或什么都没有）→ `PASS`
- `Unverified` 永远不改变判定；它只用于告知读者

### PASS 时 Positive Findings 是强制的

`PASS` 必须说明检查了什么、怎么检查的——例如"Technical Context 中的计数已对照其真相源核验；引用的文件路径在声明版本上全部存在；引用的设计章节全部存在；每条 AC 都有 Task 的 Verification Intent 引用"。一个光秃秃的 `PASS` 是在要求读者凭信仰接受你的结论，这会让审查失去意义。
