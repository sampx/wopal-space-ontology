# 项目与子模块现状 DESIGN 编写与审查指南

本指南服务于项目与子模块**现状 DESIGN**（`DESIGN.md` 与 `DESIGN-<module>.md`）的创建、日常同步与交付前语义审查，并与 `df-implement`、`df-implement-review` 共享同一套写作与验收尺度。

## 核心原则：给第一次接手的人看的真实系统图

一份合格的项目现状 DESIGN 不是设计蓝图草稿，也不是代码清单转写，而是**不阅读源码就能准确把握当前系统的说明书**：

1. **受众导向与渐进深度**：
   - **第一层（用户可观察行为）**：系统或该模块当前实际解决什么问题、对外提供什么核心能力、如何触发或使用、用户能直接观察到什么结果、有哪些重要限制与前提条件。
   - **第二层（概念结构）**：内部模块分工、数据/控制流、状态与数据所有权（谁创建、谁修改、存哪里、何时失效）。
   - **第三层（开发者契约细节）**：关键接口、配置约束、生效业务规则、异常与完整失败后果、以及指向对应源码载体路径的链接。
   - **不要一上来堆目录树或内部类列表**——读者先懂“它干什么、边界在哪里”，再往下钻模块实现。

2. **现状真实性 + 业务规则与 Key Decisions 归属**：
   - **只写已落地并经核实的现实**。严禁把 Proposal 里的未来设计、计划中接口、TODO 能力写成当前已经具备的功能。
   - **生效业务规则并入 DESIGN**：不再另立 `BUSINESS_RULES.md`。所有生效的业务校验、权限边界、配额限制、状态机守则直接写进所属主/子 `DESIGN` 对应契约或独立 `## Business Rules & Failure Boundaries` 小节（待决变更归 Proposal；存量历史 `BUSINESS_RULES.md` 仅作只读参考）。
   - **`## Key Decisions` 保持轻量化**：只保留已落地核心结论（1–3 句讲清“选了什么、为何选它”）及指向对应 Proposal 的**标准相对 Markdown 链接**（如 `[<yyyy-mm-dd-slug>](./proposals/implemented/<class>/<yyyy-mm-dd-slug>.md)` 或引用封存历史时的 `[<yyyy-mm-dd-slug>](./proposals/archived/<class>/<yyyy-mm-dd-slug>.md)`；无关联 Proposal 时写 `N/A`），不写不可跳转的裸反引号路径，也不复制长篇替代方案讨论。

3. **完整行为契约与通用子模块骨架**：
   - 子 DESIGN（`templates/design-sub.md`）采用**“固定首尾锚点 + 1..N 个领域自由分节”**的通用结构，既不把插件扩展点等特定架构绑死到普通项目上，又能托住复杂子系统深度：
     - 固定入口锚点（`## Overview and Scope`、`## Usage and Interface Contracts`）+ 按模块真实领域概念命名 **1..N 个 `## <Domain Concept>` 章节** + 固定状态/边界/出口锚点（`## Data and State Model`、`## Business Rules and Failure Boundaries`、`## Reference Documents`）。
   - 上述章节整体必须满足**五项必填覆盖要素核对单（5-Point Required Coverage Checklist）**：
     1. **行为主体与触发前提**（谁在什么前置状态下发起）
     2. **组件协作与核心时序**（关键执行步骤或 ASCII 流转/状态图）
     3. **许可、义务与不变量**（`must` / `may` / `must not` 与条件分支）
     4. **副作用与状态落点**（写了哪些持久化状态、文件、缓存或事件）
     5. **完整失败后果与恢复路径**（错误语义、部分失败回滚 vs 持久化残留、人工/调用方恢复手段）
   - **严禁手抄易变代码清单**：不手抄完整源码目录树、全部命令 flags 表格、完整 API 字段表或函数签名清单。需要具体字段或参数定义时，用一句话概括契约范围并用相对链接指向定义它的源码文件。
   - **在主 `## Module Architecture` 维护 `Source Carrier` 映射**：为每个模块标注源码承载前缀（如 `src/auth/`），供 `verify-docset.py --check-sync` 自动把代码改动映射到所属文档。

## 防多 Agent 并行冲突结构准则

四条硬规则从文档组织上根除多人/多 Agent 并行修改撞车：

| 规则 | 做法 | 为什么这样做 |
|---|---|---|
| **1. 主 `DESIGN.md` 强制压薄** | 主文档只保留项目定位、能力边界摘要、跨模块主流程、全局状态所有权与 `## Module Architecture` 模块地图表（带子文档链接） | 主文档内容越稳定、越少模块实现细节，并发开发时越不需要改动主文档 |
| **2. 多模块默认拆子文档** | 只要项目包含多个独立模块或清晰职责域，**立即按模块拆出 `DESIGN-<module>.md`**（不等到 500 行阈值）；单模块紧耦合小型项目保留单份 `DESIGN.md` | 把日常变更自然隔离到各自模块的物理文件内；同时注意紧耦合的单一契约不要机械切碎成碎片 |
| **3. 去掉头部 `Sub-DESIGNs` 枚举** | 项目主 `DESIGN.md` 头部**不写** `Sub-DESIGNs` 全量索引表；仅各子 `DESIGN-<module>.md` 头部写 `> **Parent**: ./DESIGN.md` 单向挂回 | 消除集中索引热点——两个并发分支各自新建或修改不同子文档时零主文档头冲突 |
| **4. 严守写集与单模块静默** | 日常开发或修单个模块的 Bug 只改所属 `DESIGN-<module>.md`；多 Agent 并行期间严禁修改授权写集以外的主 `DESIGN.md` 或其他模块子文档；发现写集外漂移只在交付汇报的 `DESIGN Sync` 中上报主控 | 把跨文档/主地图整合统一交给主控协调阶段，避免并发分叉 |

## 实测取证标准（Fact-Check Procedure）

更新或新建现状 DESIGN 时，不得凭记忆或“按设计应该如此”编写事实：

1. **源码与配置核实**：文中涉及的路径、命令名、开关名称、配置默认键值、状态枚举与错误提示语，必须对照当前工作区源码或配置文件逐一确认。
2. **实际运行取证**：对文档中描述的新增或改动行为、CLI 命令、构建/检查命令、关键失败分支，尽可能实际运行测试或命令并核对其真实输出。
3. **未实测显式标注**：若受限于外部环境、缺失凭据或未包含在本任务内而无法亲手运行验证，**必须在对应说明处及交付汇报中显式标注“未实测（待在 <条件> 下实测验证）”**，绝不允许把推测或“只读了代码未跑”写成“已实测/已通过”。

## 双场景同步 SOP

### 场景 A：有 Proposal 驱动的功能或架构变更

1. Proposal 审议与待交付期间，所有设计提案留在 `proposals/proposed/<class>/yyyy-mm-dd-<slug>.md`：**既不把未落地设计预写进现状 DESIGN，也不在现状 DESIGN 的正文或 `## Reference Documents` 中挂载指向 `proposals/proposed/` 或 `proposals/rejected/` 的链接**（提案路径是易变临时态，`proposals/proposed/` 目录本身即索引，反向挂载会造成主文档热点与断链）。
2. 当实施交付完成并经过测试验证时，**在同一轮交付中完成同步**：
   - 依据真实代码、测试与实测输出，更新受影响模块的 `DESIGN-<module>.md`（或小型单模块 `DESIGN.md`）；
   - 仅当本次变更引入/删除模块、调整模块间职责分工或改变项目级边界时，由主控整合更新薄主 `DESIGN.md` 地图及 `## Key Decisions`；
   - 将对应 Proposal 从 `proposed/<class>/` 同交付迁入 `implemented/<class>/` 并改写为现在时 `Decision`/`Consequences`（若分多个 Plan 实施，仅当全部批准范围完成核验后才迁入 `implemented/`）。

### 场景 B：无 Proposal 的日常修 Bug、小调整与内部重构

| 变更性质 | 是否更新 DESIGN | 改动位置与做法 |
|---|---|---|
| **改变对外可见行为、接口、业务约束、默认值、限制或失败表现**；或**发现原 DESIGN 写错/过时** | **必须同步更新** | 仅更新受影响模块的 `DESIGN-<module>.md`（单模块不碰主 `DESIGN.md`）；如改动使已归属 `proposals/implemented/` 中的路径/默认键过时，一并做事实同步（不篡改决策） |
| **纯内部实现重构 / 代码整理**（外部行为、契约、边界、限制、所有权与文档原描述均未变化） | **不改 DESIGN** | 不为刷存在感制造无实质改变的文档噪音 |
| **并行实施期间发现授权写集外文档过时** | **绝不越界修改** | 守住自身写集；在汇报/交付清单中明确列出漂移位置与建议修改，上报主控协调 |

## 统一语义审查清单与 Slop Checklist

本清单用于 `dev-doc-master` 交付前自检，同时作为 `df-implement-review` 检查代码↔DESIGN 一致性的唯一文档审查基准（无需在其他技能另写第二套标准）：

### 1. 新人盲读测试（Newcomer Test）
请（或假定）一位未读过本项目源码的读者只阅读主 `DESIGN.md` 与对应子 `DESIGN-<module>.md`：
- 能否清晰说出系统/该模块提供什么真实能力、怎么用？
- 能否理清模块职责边界与数据流向，不需要自己从零猜谁负责什么？
- 能否准确说出主要业务限制、前置条件与失败后会发生什么？
- 能否直接从地图找到需要继续深入的子文档或源码入口？

### 2. 证据核实与防夸大（Evidence Review）
- 文中每条行为、命令、配置、默认值与限制，是否能在当前代码、测试或本次运行结果中找到证据？
- 是否混入了尚未实现的 Proposal 内容、假想接口或“预计以后支持”的未来态描写？
- 用只列文件名/函数列表充当设计说明的情况是否已清理？
- 未亲手验证的说明是否诚实标注了“未实测（需在何条件下验证）”，而非谎称已验证？

### 3. Slop Checklist（反 AI 废话与文档腐烂检查）
逐条排查并在发现时清理：
- [ ] **思考过程与会话视角泄露**：是否出现“我先研究了……”、“根据上述讨论”、“本次修改重构了……”、“之所以这样设计是因为刚才……”等 AI 推理痕迹或会话视角？现状文档只写系统当下是什么，不写代理工作日志。
- [ ] **实现状态标签与过程史**：是否出现 `WIP`、`Done`、`Pending`、`In Progress`、`TBD`、复选框进度列表、或“已废弃”、“已迁移自 X”、“原方案是……”等过程态标签？
- [ ] **规则堆砌（Rule Bloat）**：是否在多处反复堆砌同一条大白话警示（`NOTE`、`IMPORTANT`、`WARNING` 块满天飞）？精简为在唯一权威位置讲清约束。
- [ ] **滥用加粗（Bold Abuse）**：是否在普通叙述段中整段整行大量加粗导致视觉噪音？加粗只留给表格主键、少数关键概念词或真正高风险停机红线。
- [ ] **跨级逐字重复**：是否把主 `DESIGN.md` 的内容完整复制到 `DESIGN-<module>.md`，或者把 `AGENTS.md` 命令清单 / Proposal 原文原封不动粘进 DESIGN？各层只保留自己的视角并通过相对链接互引。
- [ ] **段落墙与抽象黑话糊弄**：是否出现 5 行以上塞满多条规则与括号补充的密集长段，或拿“形态/门面/抽象边界”等大词遮掩具体的字段、命令或报错规则？

## 可读性校准红线、正反范例与学习闭环

“写对了（事实准确）”不等于“人看得懂（阅读友好）”。交付前必须对照以下红线与范例自检。

### 人类可读性红线

1. **开篇 3–5 句人话导读**：`## Capability Scope` 与 `## Overview and Scope` 开篇必须用 3–5 句朴素自然语言说明“解决什么问题、谁来用、可观察效果与最重要限制”——开篇严禁堆砌内部类名、辅助函数或目录树。
2. **同一概念死守同一个词**：全篇对同一领域概念只用一个固定称呼，绝不为了文采轮换同义词。
3. **用具体事实取代抽象黑话**：把 `shape / surface / seam / boundary / contract`（形态、门面、缝合面、抽象边界）视作警示词——凡是能直接说出具体配置键、CLI 命令、校验阈值或错误码的，绝不用抽象大词糊弄读者。
4. **严禁段落墙（Paragraph Walls）**：超过 4–5 行、同时夹带多条规则或括号附注的密集段落，必须拆成主动语态短句、要点列表、表格或 ASCII 流程图。

### 五组正反校准范例（过简 vs AI 代码翻译腔 vs 人类易读恰到好处）

| 场景 | 过简（丢失关键契约） | AI 代码腔 / 段落墙（人看不下去） | 人类易读（恰到好处的目标标尺） |
|---|---|---|---|
| **1. 模块开篇导读** | “负责鉴权。” | “`AuthService` 在 `src/auth/mw.ts` 注册 `JwtMiddleware`，调用 `decodeToken()` 并在事件总线派发 `auth:verified`。” | “在业务处理器执行前校验 HTTP 请求的 Bearer Token。调用方携带 `Authorization: Bearer <token>`；无效或过期 Token 在网关层直接返回 401，不会触发下游处理逻辑。” |
| **2. 失败与回滚保证** | “把会话事件写入磁盘。” | “在 `try/catch` 内调用 `appendFile()`，若 `fsync()` 抛异常则触发 `truncateSync()`。” | “每批事件写入并 `fsync` 成功后才返回。若写入或落盘失败，存储层会把文件截断回写入前的字节长度，确保磁盘上不残留半条脏数据。” |
| **3. 具体事实 vs 抽象黑话** | “校验输入形态边界。” | “在进入持久化层前针对运行时契约缝合面完成载荷门面校验。” | “当 `timeoutMs` 不是 `100` 到 `60000` 之间的整数时直接拒绝请求，返回 `ERR_INVALID_TIMEOUT`，不创建任务记录。” |
| **4. 配置约束 vs 手抄全表** | “支持 YAML 配置。” | *（把 `src/config.ts` 里的 35 个字段和 JSDoc 原封不动抄成一整页大表）* | “`root` 必填且无默认值（若回退到当前工作目录，会随启动目录变化打散日志）。`compression` 默认 `'zstd'`（设为 `'none'` 可按行直读纯文本）；完整字段定义见 `src/config.ts`。” |
| **5. 主语、时序与所有权** | “停机时取消任务。” | “在销毁阶段，停机编排器会跨提供者门面传播取消信号并异步收敛。” | “停机时，协调器先向各提供者发起取消请求，再释放子作用域；各提供者必须等待名下工作任务全部退出后，`dispose()` 才会完成返回。” |

### 用户纠偏与学习沉淀闭环

每当用户或评审指出某段文档“看不懂、太像代码翻译或信息缺失”并拍板了理想改法时，不改完即忘，按三步固化学习成果：

1. **当场横扫同类段落**：将定案的写法原则立刻应用到当前文档集内所有同类段落。
2. **项目专属偏好**（本项目术语表、读者背景、本地文档脚本约束）→ 经 `space-master` 精简沉淀进 `<project>/docs/AGENTS.md` 或 `<project>/AGENTS.md`（仅在确实引入长期本地约束时写入）。
3. **跨项目共性毛病** → 去掉会话过程噪声，把“坏写法 vs 好写法”提炼成一条极简案例沉淀到本范例表（经本体进化或 `/learn` 跨会话持久化）；凡能用规则稳定判定的高频缺陷，顺手升级为 `scripts/verify-docset.py` 的新机械检查项。

## 四道质量检验与把控闭环

仅靠“写进规则文档让 Agent 自觉遵守”必然漏检。文档质量必须由全链路机械门禁与对抗式独立复核共同托底：

1. **第一道——实施出口变更映射门禁（`verify-docset.py --check-sync`）**：
   - 解析主 `DESIGN.md` → `## Module Architecture` 的 `Source Carrier` 前缀，将本轮非测试代码改动（`--base <git-ref>` 或当前工作区变更）自动映射到对应 `DESIGN-<module>.md`（单模块映射到 `DESIGN.md`）。
   - 凡改动模块代码却未在同批变更中同步所属 DESIGN，脚本直接判 FAIL——从源头抓出“该写却没写”；纯内部重构必须显式传入 `--pure-refactor "<原因>"` 留痕交评审核验。
2. **第二道——确定性结构与边界硬门禁（`verify-docset.py` 1–11 项）**：
   - 在磁盘上强校验子文档 `Parent` 指回、**零孤立子 DESIGN**（所有 `DESIGN-*.md` 必须在主文档正文除 `Reference Documents` 外被链接）、**零模板占位符残留与空表格行**、**所有 `##` 章节非空**、项目主/生效模块子文档**强制存在 `## Business Rules and Failure Boundaries`**、相对链接无断链、零绝对路径、零过程态禁语、固定英文头部词表与合法 `Status`。
3. **第三道——结构化交付交接网关（`df-implement` / `dev-flow` 中的 `DESIGN Sync`）**：
   - 实施交付汇报强制要求非空 `DESIGN Sync` 字段，附上：① `verify-docset.py --check-sync` 运行结果、改动的 `DESIGN-<module>.md` 章节与实测依据；或 ② `--pure-refactor` 正当性说明及写集外文档漂移上报。缺少该证据的交付由主控直接打回。
4. **第四道——只读独立评审的反向追责（`df-implement-review`）**：
   - 隔离的只读评审者不轻信作者汇报，直接拿真实 `git diff` 反查所属 `DESIGN`：发现公开行为、接口、默认配置、错误码或约束变化未更新文档，或发现“纯内部重构”实则夹带外部契约变更，**直接判为 Blocker**。
   - 同时对照**五项必填覆盖要素核对单**、**新人盲读测试**、**证据核实**（对照代码与命令实测核对默认值/路径/错误表现）与 **Slop Checklist** 逐条检验文档内容深度与可读性。
