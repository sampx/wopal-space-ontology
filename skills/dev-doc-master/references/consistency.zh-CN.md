# 文档集一致性 — 通用规则

这些规则适用于产品与项目文档集中的每一份文档：PRD、产品 DESIGN、项目主/子现状 DESIGN，以及它们与 Proposal、AGENTS.md 的分工。目标是让每份文档保持单归属、可核实、低冲突、易读懂，并将维护成本控制到最低。

## 不编号章节

标题通过 Markdown 标题层级表达结构，而非数字。写 `## Capability Scope`，绝不写 `## 1. Capability Scope`。章节编号迫使每次插入、移动或删除都要重编号；纯标题层级天然承受结构编辑。适用于每一份生成或更新的文档。

## 现状准确性（项目/子 DESIGN）与过程禁语

**项目与子模块 DESIGN 是现状文档**：它们只描述当前在代码中已落地、可核实存在与运行的系统行为、接口契约、生效业务规则与失败边界。未实施的未来提案、待开发计划、构想态接口归 **Proposal**，绝不预先冒充为已支持功能。

**产品 PRD 与产品 DESIGN** 承载产品方向、系统分层与能力图，允许陈述已确认的产品意图，但仍必须区分真实实现与方向目标，具体路径/配置事实不得与仓库现实相矛盾。

所有设计文档**禁止过程态迁移碎语**：不写 "deprecated"、"legacy"、"moved from X"、"old path"、"migration"、"已废弃"、"已放弃"、"不再执行"、"历史机制" 之类叙事。当职责归他处所有时，直接陈述当前归属，不写演变流水账。

## 写作风格

准确内容只完成一半工作；另一半是人能读懂。以下规则适用于文档集中每份文档的每一句话。

### 自然语言

写得像工程师向首次接手的同事清楚解释一件事。大声朗读句子——如果像模板拼装或机器套话，立即重写。优先用朴素动词与具体名词，避免抽象名词堆砌和无意义修饰语。

### 一句一个想法

保持句子简短，每句只承担一个核心断言。一句含两个独立论断时拆成两句，避免把契约条件埋进长复合句里。

### 肯定与归属优于否定排除

先正面说明组件实际做什么、拥有什么、谁负责什么，再明确必要限制。边界陈述尽量同时点明两侧各自所有者，例如 `"X handles request routing; Y owns session persistence"`，而非通篇罗列 `"X does not do ..."`。但对于关键失败边界、禁止动作（`must not`）与不可达状态，必须正面且精确地写出禁止条件及触发后果，不可因“肯定优先”而漏掉失败保证。

## 只用相对链接

所有文档链接必须相对于仓库根目录或当前文档所在目录（如 `./DESIGN-auth.md`、`../proposals/implemented/architecture/2026-11-20-oauth.md`）。绝对路径（`/Users/...`、`/Volumes/...`、`file:///...`）一律禁止，确保文档提交进 git 后跨环境依然有效。

## 头部 = 必须，末尾 = 参考

每份文档有两个职责不同的链接区：

- **头部**（标题后的元数据块）：只放**必须遵循**的依赖文档——父文档或受约束的兄弟文档（例如 PRD 的 `Related DESIGN`、子 DESIGN 的 `Parent: ./DESIGN.md`、项目 DESIGN 的 `Parent Architecture` / `Parent Product`、产品 DESIGN 的 `Sibling DESIGNs`）。
- **末尾**（`## Reference Documents`）：放**仅参考**材料——提供背景或历史对照但不构成契约约束的资料。严禁在此处（或正文任意位置）链接未落地的 `proposals/proposed/` 或已否决的 `proposals/rejected/` 提案；DESIGN 文档只允许链接已实施的 `proposals/implemented/` 或封存历史的 `proposals/archived/`。

一份文档非此即彼，绝不同时出现在头部与末尾 `## Reference Documents` 中，否则读者无法区分强制约束与背景阅读。

### 义务测试

当文档归区不确定时，问“读者是否必须先理解并受限于该文档才能评估本设计”：

- **必须遵循** → 放在头部（跨仓库或不同命名都不削弱依赖义务）。
- **仅作参考** → 放在末尾 `## Reference Documents`。

## 语言

无论正文使用何种语言，每份文档的**章节标题**与**头部字段名**始终保持英文（如 `## Module Architecture`、`> **Status**:`）。质量门脚本按字面匹配这些令牌，稳定词表也保证文档跨项目可比。

正文内容与头部字段值的解释文字跟随用户偏好语言。用户使用中文时，正文与字段解释使用自然流畅的中文；标题与头部字段名保留英文。

## 防并行冲突与单事实单所有者

多 Agent 并行交付时，文档合并冲突几乎全部源于“集中索引文件”和“人人可改共享总文档”。遵循以下结构纪律消除冲突源：

1. **单事实单所有者**：每个核心事实只在所属文档阐述一遍，不跨层级（主 DESIGN ↔ 子 DESIGN ↔ Proposal ↔ AGENTS.md）复制粘贴。
2. **薄主 `DESIGN.md` 地图 + 默认按模块拆分子文档**：多模块项目默认将主 `DESIGN.md` 压薄为系统定位、核心流转与模块地图表，各模块内部架构、接口契约、生效规则与失败边界下沉至 `DESIGN-<module>.md`（不等到 500 行才拆）。紧密耦合的小型单模块项目保留单份 `DESIGN.md`。
3. **全面取消主文档头部 `Sub-DESIGNs` 枚举**：所有主 `DESIGN.md`（含产品 DESIGN 与项目主 DESIGN）均不在头部罗列全部 `DESIGN-*.md` 子文档，凭 `DESIGN-*.md` 文件命名与正文对应章节/模块地图链接识别，并由每个子文档头部通过 `Parent: ./DESIGN.md` 单向挂回主文档。这样多分支并行增改子文档时彻底不碰撞主文档头部。
4. **并行不越界与单模块静默规则**：日常单模块开发或修 Bug 不修改主 `DESIGN.md`。并行任务期间，各执行者只能编辑授权写集内的模块 `DESIGN-<module>.md`；发现主文档或他人模块文档存在漂移时，**只向主控报告漂移，严禁越界修改共享文档**。
5. **不手抄易变代码清单**：严禁把源码目录树、完整 CLI 参数表、全量 API 字段表或函数列表搬进 DESIGN；只写架构边界、行为契约并链接到源码。

## 伴随文档 vs 子 DESIGN

支持性文档按**内容职责**分类，而非按原文件名猜测：

- **子 DESIGN**（`DESIGN-<module>.md` 或 `DESIGN-<topic>.md`）：分解主 DESIGN 中某独立模块或架构关注点的正式架构/契约文档。头部携带 `Parent: ./DESIGN.md`，由主文档正文模块地图或章节链接引用，不出现在末尾 `## Reference Documents` 中。
- **伴随文档**（如 `BRANDING.md`、`API-CONTRACT.md`）：属于文档集、跨切面复用但并非主 DESIGN 某模块分解的单一真相源。保持原文件名，不强改 `DESIGN-*.md`，在主文档头部 `Companion Documents` 或文档关系表中声明。

若一份原本使用临时名称（如 `AUTH-PROTOCOL.md`）的文件实际承担某个模块或架构子系统的完整契约，应分类并重命名为 `DESIGN-<module>.md`，加上 `Parent: ./DESIGN.md`，并纳入主文档地图。

## 文档生命周期：草稿与生效

| 状态 | 含义 | 说明 |
|---|---|---|
| `Draft` | 草稿 | 新建或正在补充中的文档，尚未完成实证与评审 |
| `Proposed` | 待审 | 已撰写完毕等待确认，尚未正式生效 |
| `Active` | 生效 | 当前运行契约已核实且正式生效（现状 DESIGN 的常态） |

设计文档没有 `"Completed"` 状态：实施进展或交付任务属于 Proposal 或可选 Plan，不属于 DESIGN 状态值。项目现状 DESIGN 随着系统演化就地同步并维持 `Active`。

## 头部字段集

每份文档头部字段名必须来自以下固定英文词表（不自行发明新字段名）：

| 字段 | 适用于 | 含义 |
|---|---|---|
| `Status` | 每份文档 | 生命周期状态：`Draft`、`Proposed`、`Active` |
| `Updated` | 每份文档 | 最后更新日期，`YYYY-MM-DD`，每次编辑刷新 |
| `Parent Architecture` | 项目 DESIGN、子 DESIGN | 本文档遵循的上层产品架构 DESIGN；独立项目为 `N/A` |
| `Parent Product` | 项目 DESIGN、子 DESIGN | 本文档遵循的产品 PRD；无关联产品为 `N/A` |
| `Parent` | 子文档（子 PRD / 子 DESIGN） | 当前目录树中的直接父文档，如 `./DESIGN.md` |
| `Product Intent` | 产品 DESIGN | 该产品 DESIGN 遵循的产品 PRD |
| `Sibling DESIGNs` | 产品 DESIGN | 本产品核心子系统的项目 DESIGN；其契约约束本设计 |
| `Sub-DESIGNs` | 历史兼容 | 仅用于容忍存量未改老文档不报未知字段错；所有产品与项目主 `DESIGN.md` 均不再在头部枚举子文档 |
| `Sub-PRDs` | 主 PRD | 主 PRD 下每个 `PRD-<topic>.md` 枚举 |
| `Companion Documents` | 主 DESIGN / PRD | 跨切面伴随真相源（如 `BRANDING.md`、`API-CONTRACT.md`） |
| `Scope` | 任何文档 | 标题本身存在歧义时用一行收窄本文档覆盖范围 |

两条约束：

- 不使用与当前文档无关的字段（例如子 DESIGN 不写 `Sibling DESIGNs`）。
- `Parent` 与 `Parent Architecture` 是相互独立的两行，不可合并：`Parent` 指向本目录主文档（`./DESIGN.md`），`Parent Architecture` 指向项目之上的产品架构 DESIGN。

## 强制质量门

每次创建或更新文档集收尾时，先完成语义审查，再运行确定性脚本（不可用脚本替代语义审查，也不可跳过脚本检查）：

1. **语义审查（必查）**：依据 `references/design-project-guide.md` 完成文字质量、**五项必填覆盖要素**与防漂移审查（其中语言自然清晰、单归属与 **Slop Checklist** 适用于全部文档；**“必须已交付并经代码/运行实测核实”仅约束项目与模块现状 DESIGN**，产品 PRD 与产品 DESIGN 含产品子 DESIGN 允许并应该先于项目实施规划目标架构与未来演进）。
2. **机械门禁（必过）**：运行 `python3 scripts/verify-docset.py <docs-dir> --main DESIGN.md`（代码与文档联动交付时加 `--check-sync [--base <git-ref>]`；PRD 使用 `--main PRD.md`），验证：
   - 扫描磁盘发现 `DESIGN-*.md` 子文档并确认每个子文档头部带有 `Parent: ./DESIGN.md` 指回（**全面取消所有主文档的 `Sub-DESIGNs` 头部枚举检查**；存量历史文档保留该字段亦不报未知字段错），且均在主文档正文除 `Reference Documents` 外被链接（零孤立子文档）
   - 零绝对路径（`/Users/...`、`/Volumes/...`、`file:///...`）
   - 相对 Markdown 链接与头部 `./`、`../` 反引号路径均能解析到存在的文件
   - 末尾 `## Reference Documents` 不重复列出头部链接或本地子 DESIGN
   - 零未替换模板占位符与空表格骨架行
   - 所有 `##` 章节非空，且项目主/生效模块子文档必备 `## Business Rules and Failure Boundaries`
   - 无过程态禁语（`deprecated`、`moved from`、`no longer`、`已废弃`、`已放弃`、`不再执行`、`历史机制` 等），含 `Updated` 日期、合法英文头部字段与有效 `Status`（`Draft` / `Proposed` / `Active`）
   - 可选 `--check-sync`：依 `## Module Architecture` 的 `Source Carrier` 将非测试代码改动映射到所属 `DESIGN-<module>.md`，要求同步更新或显式声明 `--pure-refactor "<原因>"` 交评审复核

## 文档集一致性与变更联动

修改一份文档时检查受影响的关联文档，但严格遵守并行边界与职责分离：

| 变更类型 | 必须联动检查的文档 | 注意事项 |
|---|---|---|
| PRD 变更 | 产品 DESIGN、受影响项目现状 DESIGN 边界 | 若为未实施能力，走 Proposal 而非预写进现状 DESIGN |
| 产品 DESIGN 变更 | 关联子系统现状 DESIGN（是否产生漂移或需发起 Proposal） | 保持原有产品架构与能力图结构 |
| 代码/功能/Bug 交付 | 受影响模块的 `DESIGN-<module>.md`（+ 必要时薄主 `DESIGN.md`）+ 对应 Proposal | 纯内部重构不动 DESIGN；并行期写集外漂移只上报主控 |
| 项目主 `DESIGN.md` | 下属受影响子 `DESIGN-*.md`、关联产品架构边界 | 保持主文档为薄地图，不堆入模块实现细节 |
| 模块子 `DESIGN-<module>.md` | 主 `DESIGN.md` 模块地图中对应一行定位描述 | 仅当模块增删或职责改名时才更新主地图 |
| `AGENTS.md` | 对应项目/模块现状 DESIGN 与实际命令/测试结果 | 长期工程约束变更交 `space-master` 维护 |

## 文档角色：什么内容归哪里

每个重要事实在工作空间中只有一个权威归属：

| 文档载体 | 承载的内容 | 不承载的内容 |
|---|---|---|
| **PRD** | 产品意图、用户问题、价值主张、产品范围与边界 | 内部架构、模块布局、技术选型、验收代码详情 |
| **Proposal**（`proposals/{proposed,implemented,rejected,archived}/{class}/...`） | 重大变更的设计理由、方案对比、未实施计划（`proposed/`）、最终决策与后果（`implemented/`）、否决防错理由（`rejected/`） | 充当日常系统说明书；记录细粒度代码任务进度 |
| **Product DESIGN** | 产品系统分层、子系统边界、运行时模型、端到端流程、能力路线图 | 单项目内部实现、未交付过程台账 |
| **Project / Sub DESIGN**（现状文档） | **已落地可核实的**项目/模块能力（用户优先）、组件协作、接口与状态契约、**生效业务规则**、异常与完整失败边界 | 未实施蓝图、思考过程、手抄文件树/全量参数表、测试步骤 |
| **Plan**（可选，复杂实施使用） | 复杂跨模块/跨项目的 Task 拆分、并行写集划分、验证与交付编排 | 替代 Proposal 做架构审批，或替代 DESIGN 成为长期系统说明 |
| **AGENTS.md** | Agent 操作命令、门禁检查、编码约定、分支/测试要求（由 `space-master` 维护） | 系统架构叙事、业务规则讲解、方案对比 |

**历史兼容提示**：项目不再新建独立 `BUSINESS_RULES.md`（亦不使用 `Phase` / `GAPS.md` 跟踪进度）；已生效的业务规则与失败边界直接并入所属主/子 `DESIGN` 契约，待决规则变更归 Proposal。若仓库存有历史 `BUSINESS_RULES.md`，仅作只读历史参考，新规则与失效更新不再写入其中。

**同一事实的两面各自归位**：部署/构建机制 *是什么*（结构、文件分布、回滚语义）写入 DESIGN；Agent 必须 *执行什么命令/门禁* 写入 `AGENTS.md`。双方互链，绝不整段互抄。

## 对齐过程的边界纪律

执行文档整理或一致性对齐时，只修正规则管辖范围内的问题，绝不越权制造决策：

- **修复规则管辖的事**：头部词汇、相对链接、去绝对路径、移除过程态碎语、拆薄主文档地图、清除 AI 流水账与无依据断言。
- **不发明未定决策**：若发现文档描述的产品边界模棱两可、代码与设计发生方向性冲突，记录现象交用户或主控定案。
- **先从代码与运行结果取证**：凡能直接读源码、跑命令或看测试得到答案的事实，直接取证核实，不把机械问题抛给用户反问。
- **报告写集外漂移，不越界修改**：发现与当前任务无关或属于并行他人的文档漂移时，修好自身写集内的事实，在汇报中点明写集外漂移由主控统一协调。
