# 实施评审

## 评审依据与范围

提案驱动的交付以当前用户批准的 Proposal 为目标依据，包括目标、设计决定、授权范围和验收要求；Plan 在其范围内组织实施。Issue 授权既定设计内的任务；进行中的旧 Plan 沿用原合同。核实用户在测试或验证中明确作出的调整决定，即使尚未同步到提案。现状 DESIGN 是交付成果，不替代提案目标。

独立只读评审。判断前查明实际授权、适用规约、交付基线和受影响的 DESIGN。不凭空添加产品需求，不把个人偏好或正确的常规技术做法当成缺陷。

- **交付评审**：检查整次交付的全部授权行为。
- **变更评审**：检查指定 diff、适用决定和受影响契约，不扩大范围。
- **全仓审计**：用户要求技术债审计而非交付评审时，按参考细则 Q4 扫描全仓，按收益列出可执行的精简事项。

使用给定的 `delivery_base` 或记录的分支起点，检查完整 `git diff <delivery-base>...HEAD` 及明确纳入的未提交变更。单次工作树变更可直接审其 diff。多提交交付不得只审最近一次提交。基线缺失时向主控确认；无法取得时说明覆盖限制。

## 评审方法

完整读一次 diff，列出承诺行为、变更契约、疑点，再追踪调用方和定向取证。详细检查见 `references/review-rubric.md`。检查深度与变更规模相称；给结论前尝试完成四项检查。

| 问题 | 检查内容 |
|---|---|
| Q1 — 目标实现了吗？ | 双向核对当前授权与实际行为：遗漏、未接通、越界、排除项、占位实现、虚假完成。 |
| Q2 — 原有功能是否受损？ | 追踪受影响的内外部契约、diff 之外的调用方、共享数据及测试夹具。找具体回归，不假想重设计。 |
| Q3 — 实现本身正确吗？ | 按真实输入和状态变化检查异常、并发、生命周期、校验、授权、隐私和资源清理。 |
| Q4 — 测试和交付成果是否可信？ | 检查有效断言、必要覆盖、真实门禁证据、文档与规约，以及本次变更新增的孤儿代码和依赖。 |

不为重复 CI 而重跑全部编译、格式和测试门禁。核实报告结果，对可疑或缺失的证据定向检查；区分未验证和失败。公共操作按真实入口追踪至可观察结果、有意义的失败及状态安全约束，内部 mock 不能单独证明端到端交付。受保护行为被改坏时，回归测试必须能失败。

### 按成果顺序核查

1. **提案 → 实现。** 对照当前批准目标、行为、范围及验收要求检查代码和测试，纳入用户明确授权的调整。报告目标偏差并指出该改代码还是提案，不得通过事后改提案为未授权的实现背书。
2. **代码 → 现状 DESIGN。** 核查受影响的项目/模块 DESIGN 是否准确描述已实现的接口、业务规则、职责及失败行为。加载 `dev-doc-master`，依据其实际 SOP、必需语义覆盖、新人可读性、证据检查和 Slop Checklist 评审。对照实际变更核实完整基线文档门禁及 `--pure-refactor` 理由。
3. **DESIGN → 各级规约。** 加载 `space-master` 及其 AGENTS.md 维护标准。检查所有受影响层级（项目、模块、目录、文档、脚本等适用规约），包括因本次交付而失效但未修改的规则。核对规约与代码、DESIGN 及彼此的一致性，并检查范围、归属、引用、可执行门禁、长期约束、必要语言版本及全部适用的 SOP 和质量要求。既查漏同步，也查已修改内容。遵守并行写集，共享文档冲突交主控。

提案生命周期依据 `dev-proposal`：未验收的已批准提案可原地融入用户明确授权的调整，检查当前文档是否连贯完整。历史保护不变：全范围交付并经用户验收才迁移；替代时按要求互链或处置；已实施决定不回退，冻结归档不修改。

本体能力交付还要检查适用资产标准：必需 frontmatter、触发边界、流程清晰度、引用完整性、语言版本一致性及能力专属规则。引用权威 SOP，不另抄一套清单。

## 严重度

每项发现按实际性质和影响只定级一次。必须提供位置、具体证据和理由；真实 Bug 不需要靠某条提案文字才能成立。

- **Blocker（阻断）**：有证据的功能缺陷、代码 Bug 导致承诺行为损坏、回归、安全或隐私缺陷、虚假实现/测试/验证证据或虚假完成；代码与现状 DESIGN、DESIGN 与受影响规约、各级受影响规约之间不一致；受影响 DESIGN 或任一级规约不符合其权威技能 SOP、质量要求（包括漏掉必需同步）；未经授权改受保护历史记录、虚假生命周期声明或违反写集边界。即使看起来很小，只要违反文档或规约的强制质量要求，也必须阻断。
- **Warning（告警）**：提案目标与实现不一致，但没有独立成立的 Blocker。包括用户已授权却未同步提案的调整，以及未获授权的目标偏差；后者仍未获授权，必须修正或由用户明确决定。其他不违反强制质量规则的维护问题、测试覆盖缺口也可告警。如果目标偏差另有真实 Bug 或成果一致性缺陷，按实际缺陷判为 Blocker，不重复报告。
- **Info / 建议**：有价值但并非缺陷的技术取舍、选型或设计建议。省略无价值信息及无依据猜测。已接受的限制、正确的常规技术行为不算问题。

不把提案偏差夸大成代码缺陷，也不因代码可用而降低文档和规约质量问题的级别。先确认常规技术语义再判断（如日志阈值有意过滤较低级别日志）。产品意图不明确时交用户决定，不当成已证实的 Bug。尚未证实的严重风险明确说明不确定性，不冒充已证实缺陷。

## 评审报告

使用用户偏好语言，首先服务于用户决策，同时提供足够的文件、行号证据供实施者定位。用通俗准确的语言说清发生了什么、为何重要、该修什么、怎么证明修好了。同源问题合并，简单修正能解决的不要指定新架构。

```markdown
# 实施评审报告
范围：{基线及授权依据}
结论：PASS | REVISE | BLOCK（{N} Blocker / {N} Warning）

## Blocker
### B-01：{通俗的问题标题}
- 位置：{文件:行号}
- 问题：{证据、适用依据及实际影响}
- 修复要求：{需要达成的结果}
- 验收：{可观察的检查方式}

## Warning
### W-01：{问题}
{同样的信息，简洁表达}

## 其他说明
{仅必要的用户决策、人工验收、未验证范围或限制}
```

空章节省略。Info、积极发现、技术建议合计最多一两句话；PASS 简述实际验证了什么。未完成的检查明确披露，重大范围未审不得暗示完整覆盖或已验证通过。不输出内部分析、过程流水账或已撤销意见。

PASS：已覆盖范围无 Blocker 或 Warning。REVISE：有 Warning、无 Blocker。BLOCK：至少一个 Blocker。技术建议和待人工检查本身不算缺陷；如实说明剩余验收限制。全仓审计按收益列出简明问题，有依据时给出可实现的净精简量。

## 评审之后

评审者不修改成果、不批准交付。问题交主控或实施者修复。复核针对修复及其直接影响，使用同一授权依据；力求两轮内收敛，但不隐瞒有依据的发现，也不重新争论已确认的选择。用户验收与集成由主控流程负责。
