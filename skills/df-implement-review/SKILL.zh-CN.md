# df-implement-review — 实施评审

## 评审回答四个问题

凡是溜过测试、lint、typecheck 和 CI 的失败，都属于这四类之一。

| | 问题 | 抓什么 |
|---|----------|---------|
| Q1 | 改动真的交付了它声称的东西吗？ | 空壳、占位、没接线的代码、缩水的范围 |
| Q2 | 改动破坏了本来正常的东西吗？ | 无声的行为变化、被打断的调用点、漂移的契约 |
| Q3 | 新代码路径在真实输入和状态下正确吗？ | 并发 bug、泄漏、边界错误、错误处理缺陷、安全洞 |
| Q4 | 证据站得住吗？改动留下了什么债？ | 假测试、没测的分支、虚胖、错误抽象 |

## 先选模式

开始时定死，依据是 prompt 带了什么：

- **交付评审**——prompt 带 Plan 路径、进化提案、明确的真相或验收标准。改动是排定范围内的一次交付。先对照真相验证，再跑 Q1–Q4。
- **变更评审**——prompt 只带改动本身：工作区编辑、一个 commit、一段 range、一份文件清单。没有 Plan。用改动自己声明的意图（commit message、prompt 里的背景）当 Q1 的规格，跑 Q1–Q4。

变更评审里，**不要脑补产品需求**。业务逻辑归变更所有者，除非 prompt 写明 `business_logic_review: requested`。取决于产品意图的缺口放进 `Requirement Questions`。

prompt 什么上下文都没有时，审最窄的自卫范围——声明项目路径下的工作区改动——并在报告里说明。

prompt 可能携带的输入字段：`review_type: implementation`、`project_path`、`change_scope: working_tree`、`commit: <hash>`、`commit_range: <A>..<B>`、`background`、Plan 或提案路径、`design_docs: <path>`、`business_logic_review: requested`。

## 机械门禁管的部分

测试、lint、typecheck、CI 已经判定改动编译通过、测试通过、格式合规。复查这些是浪费。唯一可以问的测试问题是：**这个测试真的证得了它声称保护的行为吗**（Q4）——永远不是"测试过没过"。

你的对象是门禁看不见的东西：改动真实、完整、可达；没有无声破坏既有行为；在用户会碰到的场景下正确。

改动没问题就简短说没问题，然后停。这个评审是被刻意调用的，不是走仪式。

## 怎么干：读一遍、建三张清单、再探查

效率是评审质量的一部分——耗时拉长的评审只会产出噪音。两阶段：

**阶段一——读一遍，建三张清单。** 把 diff（`git diff`、`git show <hash>` 或 `git diff <A>..<B>`）和被改文件读一遍。读的过程中填三张清单：

1. **主张**——改动必须满足的每条交付物或验收标准（Plan 或提案的真相，或改动自己声明的意图）。
2. **契约面**——diff 改动的每个导出符号、签名、schema、共享类型、配置，外加逻辑变了但签名没变的每个函数。
3. **标记**——扫查时要验证的可疑点：疑似空壳、接线缺口、可疑测试、虚肥候选。

**阶段二——从清单探查，绝不回读。** 每个问题用清单配定点命令（`rg`、`git diff`、`sed -n`）消费。不重扫读过的文件。除非某条主张或契约边界指向改动之外，否则不读改动外的文件。机械扫查（空壳模式、跳过的测试、危险 API）攒成一批跑——见 rubric 的探查捆绑包。

## Q1 — 改动真的交付了它声称的东西吗？

优先级最高。"完成了但没完成"的改动大多死在这。

- **空壳扫查。** 扫被改文件里的占位模式：注释空壳（`TODO: implement`）、占位文本（"coming soon"、"TBD"）、空返回（`return null`、`return {}`）、只打日志的 handler、硬编码假值、空事件处理器、缺字段的数据壳。完整目录见 rubric §2。
- **接线检查。** 每个新产物：用到处 import 了吗、真被引用了吗、从入口可达吗。组件 → 数据源被消费。查询结果 → 被返回，不是被丢弃。新路由 → 被注册。
- **范围双向查。** 声明范围 vs 交付范围（`git diff --name-status`）：承诺了但没有、出现了但没声明、没打招呼就删了。
- **设计合规。** 交付评审里：对照触碰区域的成文约束查——架构边界、模块归属、写成"必须"的 API 契约。能跑但违反成文约束的交付，没交付设计。

严重度：占据声称行为的空壳、声称的产物缺失、违反明确的 Plan 真相或设计约束 → **BLOCKER**；真实但不可达 → **WARNING**（可达性本身就是主张时升 BLOCKER）；未声明的删除 → **WARNING**。显式决策授权的缩水是决策，不是缺陷。

## Q2 — 改动破坏了本来正常的东西吗？

机械门禁最容易漏的检查。溜过去的是：**无声的行为变化**——签名没变、测试全绿、语义变了——以及没有任何测试覆盖的行为被破坏。

- **提取契约面**（阶段一清单 2）。逻辑变了但签名没变的函数也要算——那些最危险。
- **找全部消费者。** 全项目 `rg <symbol>`，**包括 diff 之外的文件**。每个消费者问一句：改动打破了这个调用方依赖的假设吗？可空性变了？同步变异步了？顺序变了？错误契约变了？
- **查测试基础设施。** diff 改了共享 fixture、mock 或 helper，用它们的既有测试是不是在断言更弱或别的东西？

规模规则：消费者多 → `rg -l`，抽代表性样本读，说明没覆盖什么。

严重度：有具体场景的 diff 外调用点被打破 → **BLOCKER**；可能是故意的语义变化 → **WARNING**（严重时挂 `Serious Logic Risks`）；消费者没查全 → 进 `UNCOVERED STEPS`，绝不假装覆盖。

## Q3 — 新代码路径在真实输入和状态下正确吗？

拿改动 hunks 对着缺陷目录（rubric §4）走一遍，别信直觉：并发与共享状态、资源生命周期、边界与数值、异步缺口、被吞的错误、不安全强转、安全（未参数化的查询、`innerHTML`、新路由缺鉴权、代码里的密钥）。

只报有具体失败场景的 finding——"在 Z 情况下这里返回 Y"。模糊的担忧不是 finding；要么落地，要么闭嘴。

严重度：有具体场景的缺陷、可利用的安全洞 → **BLOCKER**；有场景的疑似风险、公共面缺校验 → **WARNING**。

## Q4 — 证据站得住吗？改动留下了什么债？

三部分。

**测试诚信。** 把每条声称的行为对到覆盖它的测试，然后读它们到底断言了什么。坏模式：跳过的测试、循环证明、占位断言、只验存在性的断言、关键分支没测。标准：**行为坏了这个测试会红吗？** 声称行为的测试被跳过/循环/占位 → **BLOCKER**；改动的分支没测 → **WARNING**。

**文档漂移。** 每个变更的外部契约（API、schema、CLI 标志、配置键），找到描述它的文档，查改动同步了没有。文档过期 → **WARNING**（REVISE——修法是更新文档）；违反成文的文档同步规则 → **BLOCKER**。纯内部重构不触发。

**债——Lean 扫查。** 用五个标签猎虚胖。每条 finding 一行：位置、砍什么、拿什么替。**没有替换方案的 finding 是抱怨，不是 finding。**

| 标签 | 抓什么 | 替换方案 |
|---|---|---|
| `delete:` | 死代码、没人用的灵活性、投机功能、零引用的依赖 | 什么都不用 |
| `stdlib:` | 标准库本来就有的东西手写了一遍 | 点名那个函数 |
| `native:` | 代码或依赖在干平台白送的事 | 点名那个特性 |
| `yagni:` | 单实现接口、单产品工厂、没人设置的配置、只有一个调用者的层 | 出现第二个需求前先内联 |
| `shrink:` | 同样的逻辑，更短更清晰的写法 | 给出更短的写法 |

绝不标：逻辑坏了会红的那个最小检查（一个冒烟测试、一条 assert）——那是极简底线，不是赘肉。绝不简化掉：信任边界上的输入校验、防数据丢失的错误处理、安全措施。先正确，后精简——永不拿一个换另一个。

严重度：重复实现了仓库已有的基础设施（仓库已有、点名 `file:line`），或没必要却新增重量级依赖 → **WARNING**（REVISE）；其余 lean 类 → **INFO**。

报告结尾：`net: -N lines, -M dependencies possible`。没得砍 → `Lean already. Ship.`

## 本体进化提案的交付评审

prompt 带进化提案路径时，改动落地的是能力资产（技能、规则、agent、命令）。在 Q1 常规检查之上加一道门：

**能力标准门。** 落地文件必须满足平台自身的资产标准：frontmatter 有 `name` + `description`；触发条件写在 description 里，不许埋进正文；正文 = 工作流、输出、注意事项；长内容下沉到 `references/`；`scripts/` 只放确定性的、可复用的逻辑；不发明多余结构。description 和正文必须大白话、精准——agent 读一遍就知道该干什么；堆黑话和机器腔的段落与别处一样算 finding。

严重度：交付物违反成文标准 → **WARNING**（REVISE）；description 无法触发或正文无法照做 → 至少 **WARNING**，资产落地后根本没法用（缺 frontmatter、引用不存在的文件）时升 **BLOCKER**。

这道门是提案评审（df-proposal-review）的补充：那边查的是**声称的**交付物，这边查的是**落地的**文件。

## 规模：快速 vs 完整评审

- **快速**——diff 小（约 ≤ 50 行、单文件、局部改动）：四个问题都跑，但每题几个探查、不查 rubric；建一条 todo；出短报告。
- **完整**——其余一切：每题一条 todo，碰到生僻领域开 rubric，出完整报告。

小 diff 也不许跳过 Q2——10 行的签名改动能打断一百个调用点。

## 误报校准

评审噪音是把不是缺陷的东西标成缺陷。不标：门禁已经管的；产品偏好（重要就进 `Requirement Questions`）；没有维护后果的风格小事；"换我会换个设计"；没有场景的不可验证担忧；没被要求审的范围；被授权的缩水；极简底线（一个冒烟测试、一条 assert）。每条 finding 都要引用位置和支持它的证据——否则至多 Info。

## 严重逻辑风险的标尺

有具体 `file:line` 证据、可能仍是需求驱动的严重逻辑风险（不可逆销毁、重大数据损坏、伤害用户）：报进 `Serious Logic Risks (Discuss with User)`。它不改裁决，除非 prompt 要求业务逻辑验证、或明确的真相被推翻。

## 预算——每次改动最多评审 2 次

每次改动（或每份 Plan）最多评审**两次**：首次评审 + 至多一次复审；复审报告即终局。

1. **首次评审必须穷尽**：四问全跑，所有 finding 一次性列全，包括边缘发现。藏着掖着是缺陷服务。
2. **复审 = 验证修复 + 全量重扫**：本轮发现的一切即终局——没有下一轮来补漏。

## 裁决与报告

```
PASS   — 无 Blocker，无 Warning
REVISE — 无 Blocker，至少一条 Warning
BLOCK  — 至少一条 Blocker
```

`Needs Human`、`Serious Logic Risks`、`Requirement Questions` 默认不改裁决。裁决前四问必须全部过手；Blocker 是一种严重度，不是跳过其余问题的许可证。预算耗尽时，报告里显式给出 `UNCOVERED STEPS` 节。

**完整报告：**

```markdown
# 实施评审 — {范围标签}

## Summary
- Review type: Implementation（交付评审 | 变更评审）
- Verdict: PASS | REVISE | BLOCK
- Counts: Blocker N / Warning N / Info N / Needs-human N
- Reviewed: {Plan/提案路径 / commit / commit range / working tree}
- Lean count: {net: -N lines, -M dependencies possible | Lean already}

## Blocker
### B-01: {标题}
- Location: `{file}:{line}`
- Evidence: {代码片段或命令输出}
- Impact: {什么失败，在哪个场景下}
- Fix direction: {改什么——具体，不是"改进它"}

## Warning
{同 Blocker 格式；Impact 可省}

## Info
{每条一行}

## Serious Logic Risks (Discuss with User)
{仅限可能由需求驱动的严重风险}

## Requirement Questions
{仅限代码自身无法判断的含糊或产品选择}

## Needs Human
- {条目} — 为什么只有人类观察能定案

## Positive Findings
- {已核实项：说明怎么核实的}

## UNCOVERED STEPS
{仅当有步骤没能完成}
```

**快速报告：** `Summary`（同字段）+ 一条合并的 `Findings` 列表（标 B/W/I）+ `Positive Findings`。

`PASS` 必须在 `Positive Findings` 里说明查了什么、怎么查的——光秃秃的 PASS 是要读者凭信仰接受裁决。

## 裁决之后

- **REVISE / BLOCK**：修复必须复审后才算干净。复用同一个评审会话（reply），先前的 finding 和处置都还在上下文里。
- **PASS**：这是给评审请求方的输入，不是自动门禁。它不授权合并或完成，也不替代机械门禁。
- 评审不授权动手改。finding 交回实现者。
