# 实施评审

## 评审依据与范围

提案驱动的交付以当前用户批准的 Proposal 为目标依据，包括目标、设计决定、授权范围、验收要求和未变更的上层设计约束；Plan 在其范围内组织实施。Issue 授权既定设计内的任务；进行中的旧 Plan 沿用原合同。核实用户在测试或验证中明确作出的调整决定，即使尚未同步到提案。现状 DESIGN 是交付成果，不替代提案目标。

独立评审与验证，不修改交付成果。判断前查明实际授权、适用规约、交付基线、上层架构及受影响的 DESIGN、术语表和伴随契约。依据这些材料和用户已明确的决定，了解产品用途、目标用户、部署与使用规模、信任边界和当前阶段；不凭空假设其他产品或未来场景的要求。

评审与 `df-implement` 的最小化实施原则一致：目标是在既定设计及真实使用场景内可靠交付。优先确认用户任务能否完成、重要行为是否正确、必要风险控制是否有效。接受符合当前范围的合理简化；不借正确性、安全、性能或测试之名追加未经授权的需求、过度防御、抽象或低收益修复。评审意见本身也须符合最小化原则：说明实际价值，优先最直接、最小的可靠修正；既定设计确需调整时交用户决定。

- **交付评审**：检查整次交付的全部授权行为。
- **变更评审**：检查指定 diff、适用决定和受影响契约，不扩大范围。
- **全仓审计**：用户要求技术债审计而非交付评审时，按参考细则 Q4 扫描全仓，按收益列出可执行的精简事项。

使用给定的 `delivery_base` 或记录的分支起点，检查完整 `git diff <delivery-base>...HEAD` 及明确纳入的未提交变更。单次工作树变更可直接审其 diff。多提交交付不得只审最近一次提交。基线缺失时向主控确认；无法取得时说明覆盖限制。

## 评审方法

完整读一次评审范围内的 diff，列出承诺行为、变更契约、疑点，再追踪调用方和定向取证。详细检查见 `references/review-rubric.md`。按真实业务影响和风险选择检查深度，而非穷举缺陷模式；给结论前完成四项检查或说明无法完成的部分。发现问题时，在本轮内追查共同根因、受影响的同类操作和直接调用链，合并报告完整修复边界及关键验收场景；不要找到第一处缺陷就结束，也不要为凑数扩大范围。

| 问题 | 检查内容 |
|---|---|
| Q1 — 目标实现了吗？ | 双向核对当前授权与实际行为：遗漏、未接通、越界、排除项、占位实现、虚假完成。 |
| Q2 — 原有功能是否受损？ | 追踪受影响的内外部契约、diff 之外的调用方、共享数据及测试夹具。找具体回归，不假想重设计。 |
| Q3 — 实现本身正确吗？ | 按真实输入和状态变化检查异常、并发、生命周期、校验、授权、隐私和资源清理。 |
| Q4 — 测试和交付成果是否可信？ | 检查有效断言、必要覆盖、真实门禁证据、文档与规约，以及本次变更新增的孤儿代码和依赖。 |

优先以可观察行为验证交付，再结合代码评审解释或定位缺陷。按授权的验收标准和 `rules/testing.md` 选择足以证明行为的最低成本验证：核实已有证据；对关键行为、可疑或缺失证据实际执行适用的定向测试、回放、CLI/API 或界面验证。公共操作从真实入口验证结果、有意义的失败及状态安全约束，内部 mock 不能单独证明端到端交付。复用项目现有测试和隔离环境；遵守用户授权及项目环境约束，临时验证产物不进入交付源码，不访问未授权的真实账号、数据或生产服务。受保护行为被改坏时，回归测试必须能失败。不为重复 CI 而重跑全部门禁；记录实际执行、观察结果和未验证事项，区分未验证、环境阻塞和产品失败。

### 按成果顺序核查

1. **提案 → 实现。** 双向对照已批准的设计决定、未变更上层约束、目标、行为、范围及验收要求核查代码与测试；将重要职责、依赖、接口、状态、默认值、失败和风险控制契约追到真实行为及验证证据，纳入用户明确授权的调整。报告目标偏差并指出该改代码还是提案，不得通过事后改提案为未授权的实现背书。
2. **代码 → 现状 DESIGN。** 核查受影响的项目/模块 DESIGN 是否准确描述已实现的接口、业务规则、职责及失败行为。按 `dev-doc-master/references/glossary.md` 检查受影响术语表及必需同步是否遗漏，对照获批目标和实际设计核实标准术语和定义，不强制造成无意义的词汇变动。加载 `dev-doc-master`，依据其实际 SOP、必需语义覆盖、新人可读性、证据检查和 Slop Checklist 评审。对照实际变更核实完整基线文档门禁及 `--pure-refactor` 理由。
3. **DESIGN → 各级规约。** 加载 `space-master` 及其 AGENTS.md 维护标准。检查所有受影响层级（项目、模块、目录、文档、脚本等适用规约），包括因本次交付而失效但未修改的规则。核对规约与代码、DESIGN 及彼此的一致性，并检查范围、归属、引用、可执行门禁、长期约束、必要语言版本及全部适用的 SOP 和质量要求。既查漏同步，也查已修改内容。遵守并行写集，共享文档冲突交主控。

提案生命周期依据 `dev-proposal`：未验收的已批准提案可原地融入用户明确授权的调整，检查当前文档是否连贯完整。历史保护不变：全范围交付并经用户验收才迁移；替代时按要求互链或处置；已实施决定不回退，冻结归档不修改。

本体能力交付还要检查适用资产标准：必需 frontmatter、触发边界、流程清晰度、引用完整性、语言版本一致性及能力专属规则。引用权威 SOP，不另抄一套清单。

## 严重度

每项发现按实际性质和影响只定级一次。必须提供位置、具体证据、可达触发条件、受影响的用户行为或约束及实际后果；真实 Bug 不需要靠某条提案文字才能成立。证明缺陷存在不等于证明值得阻断交付。结合实际部署、输入来源、触发可能性、后果、现有防护和修复成本判断；高后果的真实安全风险不能因低概率而忽略。对只有极端假设、没有实际影响或修复收益不足的事项不提出修复要求。

- **Blocker（阻断）**：有证据表明缺陷使当前重要承诺行为不能可靠完成、造成实质业务回归、严重稳定性/数据/安全/隐私后果，或存在虚假实现/测试/验证证据或虚假完成；业务 Proposal 驱动交付未经授权实质偏离获批设计决定或未变更上层架构约束（代码可用也阻断）；确证违反受影响 DESIGN、术语表、规约的一致性或其权威强制质量标准（包括漏掉必需同步），必需门禁失败；未经授权改受保护历史记录、虚假生命周期声明或违反写集边界。说明为什么不能带着该问题交付；不得把措辞偏好、内部实现细节或理论风险冒充强制标准。
- **Warning（告警）**：有明确实际影响且值得修正，但未达到阻断程度的缺陷；非关键目标偏差、已授权但尚未同步提案，或有实际价值的维护、测试覆盖问题。非关键未授权偏差仍须修正或由用户明确决定；正常实现自由不算偏差。告警应说明修正收益，允许主控按所属流程接受并记录后续处理；低收益问题不列为 Warning。已有独立成立的 Blocker 不重复报告。
- **Info / 建议**：有价值但并非缺陷的技术取舍、选型或设计建议。省略无价值信息及无依据猜测。已接受的限制、正确的常规技术行为不算问题。

不把提案偏差夸大成代码缺陷，也不因代码可用而放过明确违反强制标准的问题。先确认常规技术语义再判断（如日志阈值有意过滤较低级别日志）。产品意图不明确时交用户决定，不当成已证实的 Bug；尚未证实的严重风险明确说明不确定性。设计允许的限制不报告；如果当前设计本身的风险控制明显不合适，将其作为设计反馈交用户决定，不通过实施评审擅自提高标准。

## 评审报告

使用用户偏好语言，首先用通俗语言说清用户会遇到什么、为什么值得现在修、是否影响交付，再提供文件、行号证据供实施者定位。说明最小修复目标和可观察验收条件；同源问题合并，简单修正能解决的不要指定新架构。

```markdown
# 实施评审报告
范围：{基线及授权依据}
结论：PASS | REVISE | BLOCK（{N} Blocker / {N} Warning）

## Blocker
### B-01：{通俗的问题标题}
- 位置：{文件:行号}
- 问题：{证据、适用依据及实际影响}
- 修复要求：{需要达成的结果}
- 验收：{可观察的检查方式}

## Warning
### W-01：{问题}
{同样的信息，简洁表达}

## 验证结果
{关键行为、实际验证方式及结果；未执行的事项明确标注}

## 其他说明
{仅必要的用户决策、人工验收、未验证范围或限制}
```

空章节省略。Info、积极发现、技术建议合计最多一两句话；PASS 简述实际验证了什么。未完成的检查明确披露，重大范围未审不得暗示完整覆盖或已验证通过。不输出内部分析、过程流水账或已撤销意见。

PASS：已覆盖范围无 Blocker 或 Warning，允许存在非阻断建议。REVISE：有值得修订的 Warning、无 Blocker；主控可按所属流程记录接受的告警并有条件通过。BLOCK：至少一个 Blocker。技术建议、已接受的限制和待人工检查本身不算缺陷；如实说明剩余验收限制。全仓审计按收益列出简明问题，有依据时给出可实现的净精简量。

## 评审之后

评审者不修改成果、不批准交付。问题交主控或实施者修复。首轮完成全部适用检查并一次性报告有实际价值的问题；第二轮只核验已报告问题和修复的直接影响，优先执行约定验收条件，不重新全面审查。力求两轮内收敛；若未收敛，说明是原问题未修、新回归还是首轮遗漏，将剩余实质问题合并交主控，遵守 `dev-flow` 等所属流程的轮次上限；无所属上限时，两轮后由主控决定是否继续。达到上限时停止自动循环并交用户决定，不隐瞒重大风险，不为次要问题重新开启评审。用户验收与集成仍由主控流程负责。
