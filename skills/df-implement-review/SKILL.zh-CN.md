# df-implement-review — 实施审查

## 本次审查只回答四个问题

凡是穿透测试、lint、typecheck、CI 的失败，都属于这四个问题之一。

| | 问题 | 抓什么 |
|---|------|--------|
| Q1 | 声称的东西，真的交付了吗？ | 存根、空壳、没接线的代码、缩水交付 |
| Q2 | 有没有破坏已经正常工作的功能？ | 静默行为变更、被破坏的调用方、契约漂移 |
| Q3 | 新代码在真实输入/状态下会出错吗？ | 并发 bug、泄漏、边界错误、烂错误处理、安全漏洞 |
| Q4 | 证据站得住吗？留下了什么债？ | 假测试、未测分支、已分叉的重复、错误抽象 |

## 你管什么，机械门禁管什么

测试、lint、typecheck、CI 已经定了：能编译、能通过、格式干净。重复检查这些只是浪费。关于测试你只准问一个问题：**测试真的证明了它声称保护的东西吗**（Q4）——永远不问"测试过了没有"。

你的范围是门禁看不见的三件事：

- 变更**真实、完整、可达**
- 变更没有**静默破坏既有行为**
- 变更代码在用户实际会遇到的场景下**正确且安全**

如果变更没问题，简短说明结论即可收工。本审查是被刻意调用的，不是例行仪式。

## 审查模式

开始时定一次模式：

- **Plan 支撑审查** — prompt 里有 Plan 路径、显式真值或验收标准。先对照真值验证，再走完四个问题。设计文档（DESIGN.md、`docs/`、`AGENTS.md`）中针对所辖部分的显式约束，同样视为真值。
- **无 Plan diff 审查** — prompt 只给了变更载体（文件列表、working tree、commit、range）。用变更自身的声明意图（描述、commit message）作为 Q1 的规格，走完 Q1–Q4。

无 Plan 模式下，**禁止**自己发明产品需求。业务逻辑属于变更负责人，除非 prompt 写明 `business_logic_review: requested`。拿不准是否属于产品意图的问题，放进 `Requirement Questions`。

若 prompt 完全没给上下文，就审查最窄的可辩护范围——所声明项目路径下的 working tree 变更——并在报告里说明这一假设。

prompt 可能携带的字段：`review_type: implementation`、`project_path`、`change_scope: working_tree`、`commit: <hash>`、`commit_range: <A>..<B>`、`background`、Plan 路径、`design_docs: <path>`、`business_logic_review: requested`。

## 工作方式：读一遍，之后只做探针

效率是审查质量的一部分——耗时长、报噪音的审查没有价值。分两个阶段：

**阶段一：读一遍，建三张清单。** 把 diff 和变更文件从头到尾读一遍，边读边填三张清单，后续只从清单取材：

1. **声明清单** — 变更必须满足的每一条交付项或验收标准（Plan 真值，或变更自身的声明意图）。
2. **契约面清单** — diff 改到的每个导出符号、函数签名、schema、共享类型、配置项，加上"签名没变但逻辑变了"的函数（这是最危险的）。
3. **疑点清单** — 任何像存根、像接线缺口、像可疑测试的地方，留待扫描时核实。

**阶段二：从清单出发做定向探针，禁止回读。** 下面的每个问题都消费这三张清单，用定向命令（`rg`、`git diff`、`git show`、`sed -n`）验证。已读过的文件不要重读；与声明或契约面无关的文件不要读。机械扫描（存根模式、跳过测试、危险 API）合并成一批探针一次跑完——见 rubric 里的探针命令块。

## 四个问题

### Q1 — 声称的东西，真的交付了吗？

最高优先检查。"看着做完了其实没做完"的变更大多死在这里。

- **存根扫描。** 扫变更文件里的占位模式：注释存根（`TODO: implement`、`HACK:`）、占位文本（"coming soon"、"TBD"）、空返回（`return null`、`return {}`、`pass`）、只打日志的处理器、写死的假值、空事件处理器、未消费的异步结果、缺了声明所需字段的空壳模型。完整目录带探测命令：rubric §2。
- **接线检查。** 每个新产物：使用处真的 import 了吗？import 后真的用了吗？从入口（路由、渲染树、CLI、任务）真的可达吗？组件的数据请求消费了吗？state 真的渲染了吗？查询结果真的返回了、没有丢弃吗？新路由注册了吗？
- **范围双向比对。** 声明范围 vs 实际交付（`git diff --name-status`）：承诺了但缺席的，出现了但没声明的，未声明的删除。
- **设计一致性。** Plan 支撑模式：把变更对照所触及区域的书面约束检查——架构边界、模块归属、以"必须/应当"陈述的 API 契约。能跑、但违反了声明的约束，等于没有交付设计。叙事性描述被变更合理地推翻不算违反约束；但变更推翻了一项书面决策时，应当改写该决策（见 Q4 文档同步）。

严重度：存根占据了声明行为 → **BLOCKER**；声明的产物缺席 → **BLOCKER**；违反显式 Plan 真值或设计约束 → **BLOCKER**；真实但不可达 → **WARNING**（"可达"本身就是声明时 → **BLOCKER**）；未声明的删除 → **WARNING**。有 Plan 明确拍板的分阶段缩水，是决策不是缺陷。

### Q2 — 有没有破坏已经正常工作的功能？

这是机械门禁漏得最多的一关。类型检查抓得住编译失败，已有测试抓得住它们覆盖的东西。漏掉的是：**静默行为变更**——签名没变、类型没变、测试全绿，但语义变了；以及没有任何测试覆盖的行为被破坏。

- **提取契约面。** 从阶段一的清单 2 取材：diff 碰过的每个签名、返回类型、枚举值、schema 字段、共享类型、导出常量、配置项。**包括签名没变但逻辑变了的函数——这类最危险。**
- **找全所有消费方。** `rg <符号>` 全项目搜，**包括 diff 之外的文件**。对每个消费方问：它持有的既有假设被打破了吗？返回值的可空性变了？顺序变了？同步调用变异步了？原本有校验的输入现在没有？依赖旧行为的分支被重写了？
- **查测试基础设施。** 若 diff 改了共享的 fixture、mock、helper，检查用它们的既有测试的断言是否变弱或失真。

规模规则：契约面符号的消费方很多时，先 `rg -l` 列清单，抽代表性样本读，其余**明确说明没有全查**。

严重度：diff 之外的调用方被破坏且有具体场景 → **BLOCKER**；语义变了但可能是有意为之 → **WARNING**（严重的放 `Serious Logic Risks`）；消费方没查全 → 写进 `UNCOVERED STEPS`，不要假装查了。

### Q3 — 新代码在真实输入/状态下会出错吗？

缺陷藏在没人断言的支路、输入和时序里。对照缺陷模式目录（rubric §4）逐个 hunk 过，不要靠直觉：

- **并发与状态** — 竞态、共享可变状态、非原子读改写、重入、重复提交、无回滚的部分更新
- **资源生命周期** — 句柄未关、错误路径跳过清理、连接未归还池
- **边界与数值** — off-by-one、空集合、零/负输入、溢出
- **异步** — 缺 await、悬空 promise、未处理的 rejection、顺序假设
- **错误处理** — 吞异常、记日志后继续、把错误报成成功、部分失败后的不一致状态
- **类型/运行时缝** — 不安全断言、信任未校验输入、可空性假设
- **安全** — 用户输入未经参数化进入查询/shell/模板、`innerHTML`/`dangerouslySetInnerHTML`、不安全反序列化、缺校验、新路由缺鉴权、代码或日志里的密钥

只报有具体失败场景的发现——"在 Z 场景下会返回 Y"。空泛的担忧（"这里可能处理不了 X"）不是发现；要么找到依据，要么放弃。

严重度：有具体场景的缺陷 → **BLOCKER**；可利用的安全漏洞 → **BLOCKER**；有具体场景的潜在风险 → **WARNING**；公开接口缺输入校验 → **WARNING**。

### Q4 — 证据站得住吗？留下了什么债？

两部分。

- **测试完整性。** 测试有变更或行为有声明时：把每条声明行为映射到覆盖它的测试，然后读断言本身。坏模式：跳过/禁用的测试、循环证明（期望值由被测代码自己生成）、占位断言（`expect(true).toBe(true)`）、只查存在性的断言、没有断言的测试文件、快乐路径重复刷而真实分支没测。严重度：声明行为的测试被跳过/禁用/循环/占位 → **BLOCKER**；文件无断言或全是弱断言 → **WARNING**；变更分支未测 → **WARNING**。
- **文档同步。** 复用 Q2 的契约面清单：每个被变更的对外契约（API、schema、CLI 参数、配置键、行为语义），找到描述它的文档（`docs/`、`README`、`AGENTS.md`、公开 docstring），检查本次变更是否同步更新了。变更使文档过时或失真 → **WARNING**（REVISE——修复方式就是更新文档）；违反了 `AGENTS.md` 里成文的文档同步规则 → **BLOCKER**。项目文档在你可见仓库之外时，写进 `Needs Human`。纯内部重构、无契约变化的变更不触发本检查。
- **技术债。** 对照项目 `AGENTS.md` 与既有模式检查变更。真实债务信号（rubric §5）：错误抽象层、循环模块依赖、上帝模块、不对称 API（有 get 没 set、有 open 没 close）、复制粘贴已经分叉、魔法数字或写死的环境假设、为不存在的需求过度设计、死代码、注释掉的代码块。严重度：违反已声明的安全约束 → **BLOCKER**；违反规范、债务真实增长 → **WARNING**；死代码/TODO → **INFO**（掩盖声明行为时 → **WARNING**）。品味偏好不是发现。

## 规模：Quick 与 Full

- **Quick** — diff 小（约 ≤ 50 行、单文件、局部改动）：四个问题都走，但每问几盏探针即可、不查 rubric；todo 建一项；用简版报告。
- **Full** — 其余情况默认：每个问题一个 todo 项、遇到陌生领域打开 rubric、完整报告。

小 diff 也不要跳过 Q2——十行的签名变更可以砸烂一百个调用点。

## 误报校准

审查噪音就是把不是缺陷的东西报成缺陷。别报：门禁已经管过的东西；产品偏好（重要的放 `Requirement Questions`）；对可维护性或正确性没有影响的风格挑刺；"我会设计得不一样"；没有场景的担忧；没让你审的范围；已获授权的缩水。每条发现必须写位置和支撑证据——否则最多算 Info。

## 严重逻辑风险的量尺

若发现貌似成立的严重逻辑风险（不可逆破坏、重大数据损坏、用户伤害），有具体 `file:line` 证据、但仍有可能是需求驱动或有意的——不要默默把它归为 bug。报告在 `Serious Logic Risks (Discuss with User)`。它不影响判定，除非 prompt 要求业务逻辑校验或违反了显式 Plan 真值。

## 判定与报告

判定沿用 dev-flow 标准，报告可直接接入既有门禁：

```
PASS   — 无 Blocker、无 Warning
REVISE — 无 Blocker、有 Warning
BLOCK  — 有 Blocker
```

`Needs Human`、`Serious Logic Risks`、`Requirement Questions` 默认不影响判定。

给出判定前四个问题必须全部尝试——不要在第一个 Blocker 处停下；Blocker 是严重度，不是跳过其余检查的许可。预算耗尽时不要假装完成：在报告中写 `UNCOVERED STEPS`，说明哪些没做、为什么。

## 评审预算——每次变更最多评审 2 次

每次变更（或每个 Plan）rook 最多评审 **2 次**：首次 + 至多 1 次复审，之后评审**永久关闭**。计数对象是评审次数，不是会话——用新开会话、新任务等方式对同一变更取得第 3 次评审，同样违规。

1. **首次必须穷尽**：四个问题（Q1–Q4）全部跑完，一份报告列全所有 finding（含边缘发现），扣着不报 = 服务缺陷。
2. **复审 = 验证修复 + 全量重扫**，报告即终局。复审仍 BLOCK：修完后**不再送审**，按 finding 报告处置。
3. **Owner 义务（Wopal）**：委派评审/复审时，prompt 必须写明预算（如「评审预算：本次变更最多 2 次评审——本轮列全所有 finding，无下一轮」）。

**完整报告：**

```markdown
# 实施审查 — {范围标签}

## 概要
- 审查类型: Implementation (Plan-backed | Planless diff)
- 判定: PASS | REVISE | BLOCK
- 统计: Blocker N / Warning N / Info N / Needs-human N
- 审查对象: {Plan 路径 / commit / commit range / working tree}

## Blocker
### B-01: {标题}
- 位置: `{file}:{line}`
- 证据: {代码片段或命令输出}
- 影响: {在什么场景下、什么会失败}
- 修复方向: {改什么——要具体，禁止"优化一下"}

## Warning
{格式同 Blocker；"影响"可省略}

## Info
{每条一行}

## Serious Logic Risks (Discuss with User)
{仅当存在可能源于需求驱动的严重风险}

## Requirement Questions
{仅当需求有歧义、或产品选择无法仅凭代码判定}

## Needs Human
- {条目} — 为什么只有人工观察能定案

## Positive Findings
- {已核验通过的项：写明核验方式}

## UNCOVERED STEPS
{仅当有步骤未完成}
```

**简版报告：** `概要`（同字段）+ 合并的 `发现` 列表（标记 B/W/I）+ `Positive Findings`。

`PASS` 必须写 `Positive Findings`，说明检查了什么、怎么检查的——光秃秃的 PASS 等于要求读者凭信仰接受结论。

## 判定之后

- **REVISE / BLOCK**：修复后必须重新审查才算干净——没有重新验证的修复不叫修复。复用同一个审查会话（reply），让此前的发现及其处置留在上下文里；新开审查会丢掉它们。
- **PASS**：这是给请求审查方的输入，不是自动门禁。不授权 merge 或 complete，也不替代机械门禁。
- 审查不包含编辑授权。发现回交给实施方。
