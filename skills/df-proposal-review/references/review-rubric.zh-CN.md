# Plan 审查细则 — 详细流程

三个问题的完整流程。当某个问题需要完整方法、命令查证手册或范例时加载本文件。

**目的提醒**：本审查回答的是「这个 Plan 照字面执行能否成立」。它不审形式——形式由 `flow.sh plan check` 负责，且已经通过。

## 1. 通读 Plan

带行号把整份 Plan 读一遍，再跑任何命令。边读边建三张清单：

1. **事实**——每一条关于代码库的具体说法（计数、路径、行号锚点、文档章节、ID、命令、flag）。
2. **符号**——每个反引号里的代码名，标注哪个任务用它、哪个任务该创建它。
3. **文件**——所有出现过的路径，标注出现在哪（任务的 `Files`、`Changes`、`Affected Files` 行、`Pre-read`、测试路径）。

读完再跑命令。不要在「读」和「查」之间来回切换——每回头一次，成本都超过命令省的。

从一开始就记住 Plan 自己声明的执行方式：一份 Plan 可能声明「wave 是依赖层级，不是并行批次」，在同一个共享 worktree 里串行执行。这一句话就改变了 Q1 里文件重叠该怎么判。

## 2. Q1 — 各部分对得上

只需要 Plan 本身。读完立刻做——纯机械，抓的是最常见的跨任务缺陷。

### 2.1 预计文件范围（不做对账）

Task 不再携带 Files 字段。`## Affected Files` 表是预计范围，不是契约：实施 agent 会在真实代码上调整文件选择，Done 时回填实际触碰的文件。**不要把任务级文件清单和表做差集——这套对账已废弃。** 还能查的只剩两件事：

1. **过时的操作前提**：表里声明「新建」的文件其实已存在、声明「删除」的文件其实不存在——实施者会撞上一个错误前提（WARNING）。
2. **并行重叠**：Plan 声明并行执行时，各 wave 之间文件重叠是冲突（BLOCKER）。Plan 明说 wave 是串行依赖层级时，重叠是 Plan 的设计——不算 finding。

**常见误报**：表里的行有时写的是代码运行时自己产出的物，不是 Plan 去写的文件——记录生成物的行不需要生产方。

| 情况 | 严重度 |
|---|---|
| Affected Files 行的操作前提过时（新建但已存在 / 删除但不存在） | WARNING |
| 声明并行执行下文件重叠 | BLOCKER |
| 声明串行层级下文件重叠 | 不算 finding |
| 任务级文件清单和表对不上 | 不算 finding（对账已废弃） |

### 2.2 符号有出处

1. 按顺序过任务。收集任务*用到*的反引号代码名：函数与方法调用、大写蛇形常量、导出类型、fixture、CLI flag、环境变量。
2. 收集每个任务*声明*的名字：「register X」「create Y」「export Z」，以及承载它们的新文件。
3. 把每个「用到」的名字对上一个生产方。确认：
   - Plan 里某处有生产方
   - 拼写一字不差
   - 生产方的任务排在消费方的任务之前
4. 任务声明注册*一组*名字时（「注册五个错误码：A、B、C、D、E」），确认 Plan 里其他地方用到的每个名字都在这个集合里——而且没有任务把符号注册进一个 Plan 从没列过的文件。

| 情况 | 严重度 |
|---|---|
| 用到的名字在 Plan 里没有任何生产方 | BLOCKER |
| 生产方的名字和消费方期望的不一致 | BLOCKER |
| 生产方在消费方之后的 wave | BLOCKER |
| 生产方存在，但导出/注册位置没写明，且关系到接线 | WARNING |
| 生产方的文件不在 `Affected Files` 表里 | 归到 2.1 报 |

### 2.3 每个 AC 有人认领，且放对位置

1. 按编号列出 `### Agent Verification` 里的每个 AC。
2. 收集每个任务 `**Verification Intent**` 引用的集合。
3. 做差集。没被引用的 AC 没有主人。
4. 真正跨任务的 AC 必须明确标记 cross-task。
5. 查位置：测试、lint、typecheck、静态检查、可脚本化断言属于 Agent Verification；只有人工观察属于 User Validation。放错位置的验收标准浪费对应一方的时间。

**两拍制语境**：第一拍条目就是判据式（行为通过标准）——设计上合法；真实命令在 RED 阶段回填（第二拍），complete 门会强制已勾选条目带命令。永远不要把判据式条目本身当缺陷报——只报抓不住坏实现的判据（没写可观察结果、复述改动）。

| 情况 | 严重度 |
|---|---|
| AC 没人认领 | WARNING |
| 可自动化验证躺在 User Validation | WARNING |
| 纯人工观察的条目冒充 agent 可验证 | WARNING |
| 判据式 AC（合法的第一拍形态） | 不算 finding |

### 2.4 顺序服从依赖

- 声明的 wave/依赖顺序必须和依赖表一致：没有消费者排在生产者之前。
- 声明的执行方式必须和现实一致：串行 wave 允许文件重叠；声称并行 wave 要求文件互斥。
- 没有任务依赖一个 Plan 从没安排生产的东西。

| 情况 | 严重度 |
|---|---|
| 声明的顺序和声明的依赖矛盾 | BLOCKER |

## 3. Q2 — 关于代码库的说法属实吗

代码库是唯一权威。每条说法机械核掉——不许因为「看着对」就放行。

### 3.1 命令查证手册

| 说法类型 | 命令 | 备注 |
|---|---|---|
| 计数（「36 个 capability」「8 个技能」） | 到事实源头去数 | 计数驱动工作量——要数对 |
| 路径 / 文件名 | `test -e`、`ls`、`rg --files` | |
| 行号锚点（「`file.ts:619-669`」） | 在目标版本上 `sed -n 'Np' file` | 见下方「锚点漂移判断」 |
| 引用的文档章节 | `rg -n '^#{2,3} 章节' doc.md` | 这是 Plan 引用的权威依据 |
| 决策 / issue ID（`D-xx`、gap ID） | 到源头 `rg -n` 这个 ID | |
| AC 里点名的命令和 flag | 查命令是否存在、是否接受这些参数 | |
| 「新建」vs 已存在文件 | `test -e` | |
| 环境状态说法（「软链接存在」） | 实地查环境 | 仅当它驱动了工作 |

**版本纪律**：写明每条核查对着哪个版本跑的——Plan 的 `Base Commit`、worktree HEAD 或集成分支 HEAD。事实随提交漂移；不带版本的 finding，别人一提交就不可信。Plan 声明了 worktree 时，事实必须用 **worktree 的 HEAD** 查，不是集成分支。

### 3.2 锚点漂移判断

行号锚点是为了定位代码，不是要求精确。查锚点并读它周围几行：

- 落在所描述的代码上 → 通过
- 落在附近，代码明确可辨 → 通过
- 落在无关代码上，或代码在别处 → WARNING
- 代码在声明的版本上不存在 → 前提依赖它则 BLOCKER，否则 WARNING

### 3.3 与权威文档一致

1. 从 Technical Context 和 `Pre-read` 里，列出 Plan 声称作为依据的设计文档、规则文件、接口。
2. 确认引用的章节确实存在，且说的和 Plan 声称的一致。
3. Plan 做的每个决定，找出权威文档里的对应说法并对比。
4. 分歧分类：
   - **明说了**——Plan 声明了分歧并说明理由，或声明它更新文档 → 不算 finding
   - **推迟了**——Plan 明确排除（Out of Scope 带理由）→ 不算 finding
   - **静默**——既没承认也没说明理由 → finding

判断提示：不是每句文档都有约束力。旧文档可能描述的是已淘汰的模型，而 Plan 实现的是当前模型。判定冲突前，先确定哪份文档对所实施的模型说了算。

| 情况 | 严重度 |
|---|---|
| Plan 倚仗的错误前提 | BLOCKER |
| 会让任务做错事的错误说法 | BLOCKER |
| 触犯明确安全/安保约束的分歧 | BLOCKER |
| AC 命令在声明环境里跑不起来 | BLOCKER |
| 引用的文档章节不存在、或说的不一样 | WARNING |
| 对设计文档或项目规则的静默偏离 | WARNING |
| 不影响工作的描述性漂移（锚点偏几行） | WARNING |
| 无关痛痒的漂移（计数不精确、顺序差异） | INFO |
| 从工作区查不实的说法 | `Unverified`——不算 finding |

## 4. Q3 — 能否达成目标

只需要 Plan 本身（加上目标拆解——零条代码库命令）。抓的是结构检查抓不到的东西：一份 Plan 全过了，仍然交付缩水。

### 4.1 目标全覆盖

1. 把 `## Goal` 拆成独立有意义的部分。
2. 每个部分找出交付它的任务。
3. 没有任务的部分只是愿望，不是计划。

### 4.2 决策全落地

1. 每个 `D-xx`，找出实现它的任务。
2. 确认交付和决策范围一致。
3. 扫任务文本找缩水措辞：`v1`、`v2`、`simplified`、`static for now`、`hardcoded`、`placeholder`、`basic version`、`minimal`、`NOT wired to`、`NOT connected to`、`stub`、`future enhancement`、`will be wired later`、`skip for now`、`for now`。
4. 逐个裁定，按顺序问两个问题：
   - 缩水是否违背 Goal 或某个 `D-xx`？没有 → 不算 finding。
   - 缩水是否被 `D-xx` 或范围声明**授权**？授权了 → 不算 finding。Plan 说清楚分阶段交付，就是合法的。

### 4.3 AC 能查出问题

对每个 AC 问：如果功能坏了，这个检查能抓出来吗？

- 行为是声明、AC 却断言存在（「文件存在」）——证明不了行为。
- AC 复述改动（「函数被加了」）——什么都证明不了。
- 功能坏不坏都通过的 AC，是装饰品。

最强的 AC 会点名它能抓出的失败。弱「证伪力」是 WARNING，不是 BLOCKER——`plan check` 管命令存在，你管命令能否证明什么。

### 4.4 能交接

对每个任务问：执行者只拿 Plan + 声明的 `Pre-read`，能开工吗？

- 前面任务的接口、类型、输出是否**点名**，而不是暗示（「沿用任务 2 的返回结构」弱；「调用 `parseConfig(path)`，返回 `ParsedConfig`」就绪）？
- 任务自己的输出是否定义得足够清楚，让*下一个*任务能消费？
- `Pre-read` 列的文件对不对——那些文件存在吗？

别报那些只是明显序列一步的任务。及格线是「胜任的执行者能推进」。只有缺了会走错路的信息才报——要被猜的接口、歧义的输出结构、执行者无从发现的依赖。

| 情况 | 严重度 |
|---|---|
| 目标部分没有覆盖任务 | BLOCKER |
| 决策被缩减且 Plan 没承认 | BLOCKER |
| 缩水措辞被 `D-xx` 或范围声明授权 | 不算 finding |
| AC 查不出问题 | WARNING |
| 只凭 Plan + `Pre-read` 开不了工 | WARNING |
| `Pre-read` 点名的文件不存在 | WARNING |

**为什么静默缩减决策是 BLOCKER**：一份缩水的交付走到 `verify` 时，执行预算已经烧完。在它执行前抓住，正是本次审查的全部价值。分阶段交付没问题，前提是 Plan *说清了*这是阶段——调整 Goal，或拆一个明确的后续。静默缩减不是。

## 5. 严重度校准

四个等级，按读者该怎么做定义：

| 等级 | 含义 | 判定标准 |
|---|---|---|
| **BLOCKER** | 照字面执行会失败、违约或交付缩水 | 「这要上线，是坏的还是撒谎？」 |
| **WARNING** | 执行能成，但 Plan 不安全、歧义、或该验证的没验证 | 「会不会返工或藏缺口？」 |
| **INFO** | 值得知道，无需行动 | 「正常作者会耸耸肩吗？」 |
| **Unverified** | 从工作区查不实 | 「我是不是查不了？」 |

刻意缺席的：**规模/计数阈值**。上下文预算是按任务管的，不是按 Plan；大而内聚的 Plan 很正常。永远不要把任务数、文件数、wave 数当 finding 报。

### 校准练习

| 情况 | 正确裁定 |
|---|---|
| Plan 有 12 个任务，互相依赖；Plan 声明不拆分并说明理由 | 不算 finding（规模不是缺陷） |
| Plan 声明文件为「新建」，但文件已存在 | WARNING（前提过时；执行者会即兴发挥） |
| 任务引用一个没有其他任务创建的函数 | BLOCKER |
| 任务注册 5 个错误码，后面的任务用了第 6 个 | BLOCKER |
| 锚点 `file.ts:964` 落在 967，正是所描述的函数 | 不算 finding |
| 锚点 `file.ts:964` 落在无关代码块；函数在 1200 | WARNING |
| Plan 违背它同时引用的设计文档，且不承认 | WARNING |
| Plan 违背设计文档，且写明「本 Plan 取代文档 Y 的 §X」 | 不算 finding |
| AC 是 `rg -c 'pattern' file ≥ 1`，而文件在功能坏掉时仍可能含该 pattern | WARNING（证伪力弱） |
| 缩水到「v1」，而 `D-04` 说「先用静态数据，动态后做——本 Plan 交付静态层」 | 不算 finding |
| 缩水到「v1」，而 `D-04` 说「配置展示计算结果」 | BLOCKER |
| 因缺沙箱查不了的担忧 | `Unverified`，永远不算 finding |

## 6. 完整示例

### 例 A — 没人创建的符号（Q1）

**Plan 形态**：任务 2 建错误码模块，注册五个码：`A_MISSING`、`A_INVALID`、`S_MISSING`、`S_INVALID`、`C_UNRESOLVED`。任务 4 描述失败分支「fail fast with `TEMPLATE_MISSING`」。

**检查**：列出注册集合，列出全 Plan 用到的大写蛇形名，做差集。

```yaml
check: Q1_symbols
severity: blocker
plan_location: "{plan}.md:{任务 4 分支行号}"
reality: "注册集合在 {plan}.md:{任务 2 声明行号}；TEMPLATE_MISSING 不在其中"
impact: "任务 4 的失败分支照写没法实现；执行者会即兴加第二处注册，或错用别的码"
fix: "把 TEMPLATE_MISSING 加进注册任务，或改用已有错误码"
```

### 例 B — 文件两边漂移（Q1）

**Plan 形态**：任务 2 的 `Changes` 有「第 3 步：在 `src/lib/errors.ts` 注册五个错误码」。任务 3 有「第 2 步：在 `src/lib/errors.ts` 注册 `SYNC_APPLY_FAILED`」。`Affected Files` 表有十行组件；`src/lib/errors.ts` 不在其中。

```yaml
check: Q1_files
severity: warning
plan_location: "{plan}.md:{任务 2 第 3 步行号}"
reality: "Affected Files 表在 {plan}.md:{行范围} 没有 src/lib/errors.ts 这一行"
impact: "文件被两个任务改，却落在 Plan 声明的文件范围之外"
fix: "在 Affected Files 表加一行，写明这个文件和碰它的任务"
```

### 例 C — 错误前提（Q2）

**Plan 形态**：Technical Context 断言「旧 schema 路径已从 ontology 消失，所以初始化必然失败」。任务 4 删掉该路径的读取器，AC#7 断言全仓搜旧标识符零命中。

**检查**：在声明版本上，全仓搜旧路径和读取器的调用方。

```yaml
check: Q2_facts
severity: blocker
plan_location: "{plan}.md:{前提所在行}"
reality: "{file}:{line} 仍在 import 并调用旧读取器；Plan 的搜索清单没包含这个调用点"
revision: "{commit}"
impact: "前提「没有其他调用方」是假的；全仓 AC 过不了，因为有一处没点名的调用点还在"
fix: "把这个调用点写进某任务的范围，或加进删除任务"
```

注意 AC 本身如何揭示缺陷：一旦核查前提，Plan 自己的验收标准会在 verify 时失败——那时整个执行预算已经烧完。这正是 Q2 要防的。

### 例 D — 正确地不报 finding

**Plan 形态**：六个任务、11 行 `Affected Files`、四个 wave；`D-10` 写明「单 Plan 交付，不按任务数拆分；任务互相依赖；上下文预算按任务管」。

**正确处理**：对规模、任务数、文件数都不报 finding。`D-10` 是作者明确且有理由的决定。值得的话记进 Positive Findings（「单 Plan 决策明确，理由已述」）。如果审查表格诱使你报「6 个任务超过建议的 2–3 个」，那张表已经不存在了——这里没有它。

### 例 E — 没人认领的验收标准（Q1）

**Plan 形态**：13 个 Agent Verification AC。六个任务声明 `Verification Intent`；引用集合覆盖 AC 1–6、8、10、12、13。AC 7、9、11 没人引用；只有 AC#10 带明确的「(cross-task)」标记。

```yaml
check: Q1_acs
severity: warning
plan_location: "{plan}.md:{AC 7、9、11 的行范围}"
reality: "没有 Verification Intent 引用它们；只有 AC#10 标记了 cross-task"
impact: "三条验收标准没有主人，执行计划里没人负责证明它们"
fix: "把每个 AC 分给某任务的 Verification Intent，或明确标记 cross-task"
```

### 例 F — 查不出问题的 AC（Q3）

**Plan 形态**：任务 3 的行为声明是「非法状态输入被干净地拒绝」。它的 AC 是 `test -e src/lib/state.ts`——文件存在性，不是行为。

```yaml
check: Q3_acs
severity: warning
plan_location: "{plan}.md:{AC 所在行}"
reality: "AC 断言文件存在；拒绝路径坏了不影响文件存在与否"
impact: "声明的行为从未被真正验证；回归静默通过"
fix: "换成一条真正走拒绝路径并断言错误的命令，例如用坏状态跑脚本、检查退出码"
```
