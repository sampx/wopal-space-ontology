## 1. 通读文档

跑任何命令之前，带行号通读整份文档一遍。读的过程中建好三张清单：

1. **事实**——关于仓库、系统、其他文档的每一条具体断言（数量、路径、行号锚点、文档章节、ID、命令、参数）。
2. **符号**——Plan 模式：每个反引号代码名，谁的任务用它、谁的任务创建它。文档模式：每个具名的组件、能力、契约，文档在哪里给它安排了归属。
3. **文件**——提到的每一个路径，以及它是在哪被提到的。

然后跑命令。不要在读和验之间来回切换——每回读一次，亏的比省的多。从一开始就记住文档自己声明的执行方式（顺序波次容忍同波文件重叠；声明并行的波次要求文件互斥）。

## 2. Plan 模式 — Q1：各部分拼得上吗？

先从文档找任务衔接，再按需要核实已有代码、依赖与接口提供的符号。

### 2.1 预期文件范围（不做对账）

`## Affected Files` 表是预期足迹，不是合同；实现者在 Done 时回填实际值。**不要拿任务级文件清单对账表格。** 只剩两样可查：

1. **过期操作前提**：某行声明"创建"一个已存在的文件，或"删除"一个不存在的文件——实现者会在假前提上走错路（WARNING）。
2. **并行重叠**：声明并行执行时，波次间文件重叠是冲突（BLOCKER）。声明顺序分层时，重叠是 Plan 自己的设计——不是 finding。

**常见误报**：表格行写的是代码运行时产生的产物，不是 Plan 要写的文件——运行时产物不需要生产者。

### 2.2 符号有生产者

1. 按顺序走一遍任务。收集任务**用到**的代码名：函数调用、大写蛇形常量、导出类型、fixture、CLI 标志、环境变量。
2. 收集每个任务**声明**的名字："注册 X"、"创建 Y"、"导出 Z"。
3. 把用到的名字对到既有来源或生产者任务：符号存在、拼写一致；需要新建时，生产者任务排在消费者之前。
4. 任务注册一组名字时，核对其余地方用到的每个名字都在这组里。

| 情形 | 严重度 |
|---|---|
| 新符号既无既有来源也无任务生产者 | BLOCKER |
| 生产者名字与消费者期望的拼写不一致 | BLOCKER |
| 生产者排在消费者后面的波次 | BLOCKER |
| 生产者存在但导出/注册位置未写明且影响接线 | WARNING |

### 2.3 每个 AC 有归属，且归对了桶

1. 列出 `### Agent Verification` 里的每条 AC。
2. 从每个 Task 的 `**Verification Intent**` 收集被引用的集合。
3. 做差集。没人引用的 AC 没有归属。跨任务 AC 必须显式标注。
4. 查归桶：测试、lint、typecheck、可脚本化的断言归 Agent Verification；只有人类观察归 User Validation。

**尚未写命令的文字判定条件**：在动手写代码前，AC 可以先用文字写清通过/失败的判定条件（具体测试命令会在编码写测试的 RED 阶段填入）。不要因为现在还是文字条件就报错；只抓那些哪怕代码写坏了也检查不出来的无效条件。

### 2.4 顺序贴着依赖

- 声明的波次/依赖顺序必须和依赖表一致：消费者不排在生产者前面。
- 声明的执行方式必须符合实际：顺序波次容忍同波重叠；声明并行的波次要求文件互斥。
- 依赖的产物已经存在、有可行的取得路径或由前置任务产生。

## 3. Plan 模式 — Q2：关于仓库的陈述是真的吗？

仓库是现状事实的证据，当前用户授权是目标依据。核实关键断言，不把旧现状 DESIGN 当成新 Proposal 的目标。

### 3.1 命令手册

| 断言类型 | 命令 | 备注 |
|---|---|---|
| 数量（"36 个能力"） | 在真相源里数一遍 | 这个数驱动工作——必须数对 |
| 路径 / 文件名 | `test -e`、`ls`、`rg --files` | |
| 行号锚点（"`file.ts:619-669`"） | 目标版本上 `sed -n 'Np' file` | 见锚点漂移裁决 |
| 引用的文档章节 | `rg -n '^#{2,3} Section' doc.md` | 这是 Plan 的权威引用 |
| 决策 / issue ID | 在它的真相源里 `rg -n` | |
| AC 里点名的命令和参数 | 查命令存在、参数接得住 | |
| "新建" vs 既有文件 | `test -e` | |

**内容快照纪律**：注明每条核查对着的内容快照——当前工作树（可包含未提交修改）、Base Commit、worktree HEAD 或集成分支 HEAD。评审对象位于当前工作树时，默认核对当前内容；文档声明了既有 worktree 且评审目标就是该 worktree 的已提交状态时，再核对对应 HEAD。

内容快照纪律是为了说明“你到底评了哪份内容”，不是 Git hygiene 门禁。工作树里的设计/Plan/提案尚未提交、未 push、未 merge、甚至 untracked，只要它就是当前评审对象，**这些 Git 状态一律不是 finding**。不要因为旧 HEAD、Base Commit 或 Integration Branch 尚未包含当前修改，就推演未来 worktree 缺内容并报 Blocker/Warning；那属于后续 dev-flow 执行门禁，不属于 proposal review。

### 3.2 锚点漂移裁决

行号锚点用来定位代码，不是合同。探查锚点，顺带读前后几行：

- 落在描述的构造上，或在附近且构造清晰可辨 → 通过
- 落在不相干的代码上，或构造在别处 → WARNING
- 构造在声明版本上不存在 → 前提依赖它就是 BLOCKER，否则 WARNING

### 3.3 与权威的一致性

1. 从 Technical Context 和 `Pre-read` 列出文档点名作为依据的设计文档、规则文件、接口。
2. 确认引用的章节存在、且说的就是文档声称的意思。
3. 每条决策，在权威里找到管辖原文，比对。
4. 分歧分类：**已承认**（写明并说明理由 → 不是 finding）、**已推迟**（显式排除出范围并给理由 → 不是 finding）、**无声**（→ finding）。

提案驱动 Plan 以当前授权 Proposal 为目标依据，现状 DESIGN 描述尚未改变的系统；获准的新目标与旧现状不同不是冲突。旧 Plan 和 Issue 仍按原合同。真实安全/工程规约不得由 Plan 擅自覆盖，必要的规则维护按实施技能在代码和 DESIGN 之后完成。

## 4. Plan 模式 — Q3：执行它能交付目标吗？

对照当前授权目标，沿真实入口、调用路径和失败行为核实任务覆盖与验收，不只看文档自己的承诺。

### 4.1 目标被覆盖

把 `## Goal` 拆成独立有意义的部分；找到交付每部分的任务。没有任务的部分是意图，不是计划（BLOCKER）。

### 4.2 决策被交付

1. 每条 `D-xx`，找到实现它的任务。
2. 确认交付的就是决策陈述的范围本身。
3. 扫任务文本里的缩水词：`v1`、`简化版`、`先用静态的`、`硬编码`、`占位`、`基础版`、`最小`、`stub`、`没接到`、`先这样`。
4. 按顺序两问裁决：缩水和 Goal 或 `D-xx` 矛盾吗？`D-xx` 或范围声明**授权**它了吗？授权的缩水是分阶段交付——不是 finding。

**为什么无声缩水是 BLOCKER**：缩水的交付物到达 `verify` 时，执行预算已经花掉了。文档*说了*这是阶段就是分阶段交付，无声缩水不是。

### 4.3 AC 能失败

每条 AC：功能坏了，这条检查抓得住吗？明明要验功能行为，却只检查文件存不存在，这证明不了任何事；只把任务标题抄一遍更证明不了。关键验收抓不住错定为 BLOCKER，非关键验证缺口为 WARNING——`plan check` 脚本管格式上有没有填内容；你管填进去的条件到底能不能验出真假。

### 4.4 交接得出去

每个任务：只凭文档和声明的 `Pre-read`，合格的实现者能开工吗？

- 前置任务的接口、类型、输出是**点名**的，不是暗示的（"用 Task 2 的形状"很弱；"调用 `parseConfig(path)` 返回 `ParsedConfig`"才算就绪）。
- 任务自己的输出定义到下一个任务能消费的程度。
- `Pre-read` 列的文件存在。

只标会导致走错路的信息缺失。

## 5. Plan 模式 — Q4：Lean

对 Plan 创建的每个新东西——模块、类、接口、配置项、依赖、扩展点——按下面 6 步挨个问：

### 阶梯

1. **这东西真的需要存在吗？** 单实现接口、单产品工厂、给从不变化的值做的配置、没有消费者的扩展点、只有一个调用者的包装层。为未来瞎预留的需求 = 砍掉，一句话点出将来真遇到什么情况时再加。
2. **仓库里已经有现成的了吗？** Plan 要建的东西隔壁文件里就有。标 finding 前先用 `rg <pattern>` 搜——finding 必须写明现有实现的文件与行号（`file:line`），否则至多算 Info。
3. **标准库自带吗？** Plan 新加的依赖，语言标准库本来就能干。finding 里直接点名标准库函数。
4. **平台或运行时原生就有吗？** 代码或依赖在干平台白送的事（比如 CSS 能干的不写 JS、数据库约束能干的不在应用层手写、运行时内置 API 能干的不装包）。
5. **写法最直接吗？** 同样的功能，更短更直白的写法就能做好。finding 里给出更短写法。
6. **换新时排了拆旧吗？** 当 Plan 用新模块、新函数或新依赖替换旧方案时，必须检查是否安排了删除被淘汰的旧代码、旧单测和 `package.json` 里的旧依赖。只排"建新"不排"拆旧"，落地后一定留死代码。

### 依赖准入

Plan 里任何新增三方依赖，都需要一句明确的理由：标准库、平台原生、每个已装依赖为什么都不够用。加依赖没给理由 → WARNING。前面第 3–4 步能解决却加依赖 → WARNING，finding 直接点名该用什么。

### 严重度

| 情形 | 严重度 |
|---|---|
| 为未来瞎预留的抽象或扩展点 | WARNING |
| 重复造仓库里已有的轮子（点名 `file:line`） | WARNING |
| 标准库 / 已装包能解决却新增依赖 | WARNING |
| 替换旧方案却没排清理旧代码、旧单测或旧依赖 | WARNING |
| 同样逻辑有更短写法 | INFO |
| 风格或命名偏好 | 不是 finding |

单纯精简建议不阻断；有具体冗余成本才告警，技术偏好仅作建议。无需机械估算净减少行数或依赖数。

### 进化提案的能力门

Q1–Q4 之上，本体进化提案的交付物必须满足平台自身的能力标准：

- frontmatter 有 `name` + `description`；触发条件写在 description 里
- 正文 = 工作流、输出、注意事项；长内容下沉到 `references/`
- `scripts/` 只放确定性的、可复用的逻辑
- 不发明平台资产结构之外的多余结构

提案明确要求违反强制质量标准的成果 → BLOCKER；未规定的实现细节不报。这里只审提案明确要求的交付物；落地成果由实施评审复查。

## 6. 业务 Proposal 模式 — P1–P5

业务 Proposal 是确定的目标规格与重要决策记录。评审设计是否成立、完整且确定，而不只评文笔。通读一遍后，先把提案触及的 `implemented/` 记录读掉再形成任何裁决：没有对照被替代的那份记录，替代声明根本无法判断。

### 6.1 P1 — 这真是个"已经定下来"的决定吗？

先找到那句话说清"选了什么"，然后用两种方式检验：

1. **离开原文复述。** 合上提案，你能说出选了什么、排除了什么吗？说不出，实施时读者就会自己编一个。
2. **检验边界。** 提案有没有说自己**不做**什么？边界空着不是范围，是一张空白支票。

建立精简证据映射（权威约束或已确认用户决定 → 目标设计位置 → 预期行为及验收）。按 `dev-proposal/references/design-practices.md` 选择适用领域，并应用 `dev-doc-master` 五项行为覆盖标准。以具体角色、输入、职责和状态推演正常、异常及边界场景，检查默认值、权限、副作用、部分失败、恢复及兼容性。对照术语表及所属 DESIGN 核实定义。若两个独立实施者可以合理选择实质不同的职责、状态、接口或行为，指出缺失的决定和分歧结果。重要决策或关键契约缺失阻断就绪；正常实现自由不是问题。有已确定讨论结论时核对遗漏或弱化；无法取得讨论则披露限制，不推断已决定。

批准链：

| 信号 | 读法 |
|---|---|
| `Status: approved`，`Approved` 带日期与人 | 可能是真实授权；仍要确认对话，不能只看文件 |
| `Authorized scope` 同时写明具体包含项**与**排除项 | 可用的范围 |
| `Authorized scope` 写"全部"、复述标题，或只给一个没有边界的主题 | 范围缺失 → WARNING；当某个 Task 依赖缺失的那条边界时 → BLOCKER |
| 批准后实质调整未获用户授权 | 新范围未获批准 → BLOCKER；用户已经明确授权但提案尚未同步 → WARNING |
| `Status: approved` 但没有批准块 | 形状由脚本抓；评审把它当作未授权内容报告，而不是格式小毛病 |

**不要把格式有效当作批准的证据。** 脚本只能确认字段存在且写法正确；只有对话能确认是人给的授权。评审拿不到授权证据时在其他说明披露，不两头假设。用户在验收前明确授权的调整按 dev-proposal 融入当前提案，不重复审批。

### 6.2 P2 — 文中陈述的事实成立吗？

沿用第 3 节的命令手册与快照纪律。提案通常比 Plan 说得更少但更重：文件路径、当前默认值、错误串、数量、"目前系统这样做"。每一条都是决策的前提，错一条代价都很大。

独立发现适用 `AGENTS.md`，沿约束关系追溯产品 PRD/架构、项目与受影响模块 DESIGN、伴随契约及术语表。逐项判断重要目标决定是继承约束、在范围内明确改变某项决定，还是无声明地发生冲突。指出权威语句及目标条款（或缺失）和受影响行为/职责。明确属于范围的目标变化合理，其余约束仍有效；实质隐性违背阻断，单纯缺少引用按影响定级。用代码、测试或定向探查验证关键可行性；无法取证则披露，不把重要未验证前提判为就绪。

### 6.3 P3 — 设计决定是否最终确定且保护历史？

在目标设计正文核查最终选择和范围。按 dev-proposal 标准，只对需要长期背景的重要决定核查独立理由；真实被放弃方案与剩余影响可以解释选择，但不构成实施选项。不要求编造备选或单设理由章节。然后核对替代台账：

| 情形 | 判定 |
|---|---|
| 新提案改了默认值/边界/决策，写明老 `implemented/` 记录哪些被替代、哪些继续有效，并有相对链接 | 通过 |
| 直接原地改 `implemented/` 决策，没有新提案 | BLOCKER——历史决策被改写 |
| 把原本 `implemented/` 的提案退回 `proposed/` | BLOCKER——成交记录消失 |
| 新范围尚未全交付就改了老 `implemented/` 记录 | BLOCKER——未交付的改动被当成现有事实 |
| 完全替代，老记录仍留在活跃区并与之矛盾 | BLOCKER |
| 完全替代，吸收老理由或把老记录归档 | 通过 |
| 只同步路径、名字或实现细节，决策未变 | 通过——这是要求的行为 |

机械部分（`Status` 与目录是否匹配、骨架是否正确、链接是否可达）归 `verify-proposals.py`。不要重复查，把它的输出当事实底稿。

### 6.4 P4 — 它能被证伪吗？

逐项从重要变更契约及受影响不变量追到验收，再反向确认验收对应目标。对每条验收套用“如果做坏了，这条抓不抓得住”。检查验证边界及相关已有测试；私有 mock 不能证明绕开的真实协作或公开操作。按适用测试规约选择最低成本的充分验证层，不提前强求精确命令。从设计本身核查风险：缓解措施是可验收契约，关键可行性有证据，剩余影响及控制措施明确交用户接受。独立风险章节可选；“实施时注意”不算解决风险。关键验收无法证实或重要设计风险未解决阻断，较小缺口按影响定级。

部分交付纪律：留在 `proposed/` 且 `Status: approved` 的提案可能未实施、部分交付或待用户验收。真正的问题是反向的——证据只显示一个子集，却声称批准范围已全部完成，或者用"全部交付"的措辞描述部分范围。

### 6.5 P5 — 这项决策够精简吗？

与第 5 节同一把梯子，对象换成决策：

1. 这项决策需要存在吗——现在的行为真是个问题吗？
2. 是不是已经被某份 `implemented/` 记录或某条生效规则定了？点出文件。
3. 更小的决策够不够？
4. 它换掉的那项决策清理了没有？

### 6.6 审阅由已批准 Proposal 派生的 Plan

决策已经关掉了，这次评审只关乎实施。查：

- **范围忠实度**——每个 Task 都对应批准范围里的一块，没有 Task 超出。
- **覆盖完整**——批准范围每一部分都有 Task，没有悄悄丢掉。
- **顺序与交接**——即常规 Plan 模式的 Q1/Q3，不变。
- **不做二次审批**——某个 Task 只是换了内部实现手法、换了库、换了拆分方式，只要批准的设计决定、行为及上层约束仍然成立，就不是问题。

Task 超出批准范围 → BLOCKER（未获授权的工作）。悄悄丢掉范围的一部分却声称完成 → BLOCKER。如果 Plan 显示批准范围无法按原样交付，向用户提 Requirement Question，不要在评审期间重新设计。

## 7. 文档模式 — D1–D4

没有任务可调度，问题换形。Q4 的名字和严重度上限沿用。

### D1 — 文档自洽吗？

读的时候找：章节间自相矛盾；术语先用后定义、或一词两用；文档引入的组件、状态、契约没有归属；某节依赖文档从未提供的上下文。

**结构合规**：文档属于 `dev-doc-master` 体系时，结构规则（header 双区、命名、字段词汇、子文档发现方式）以 `dev-doc-master/references/consistency.md` 为准。机械部分已经被它的质量门禁（`scripts/verify-docset.py`）扫过——有就跑，把你的评审花在脚本看不见的东西上：*内容*是否配得上结构（链接指向的文档早已不再管辖这份文档、companion 被错认成 sub-design）。

**不要求 header 枚举子文档。** 所有主 DESIGN（产品与项目一视同仁）都刻意不在头部枚举 `Sub-DESIGNs`：子文档靠 `DESIGN-*.md` 文件名与自己的 `Parent` 头部链接被识别，主文档在正文（通常是 `## Module Architecture` 地图）链下来。把"主 DESIGN 头部没有列出子文档"当成问题属于误报。真正的缺陷正好相反：某个子文档只能从 header 点到，`verify-docset.py` 会把它报成孤立子文档。

| 情形 | 严重度 |
|---|---|
| 承重陈述的内部矛盾 | BLOCKER |
| 真歧义的未定义术语 | WARNING |
| 引入的组件或状态没有归属 | WARNING |
| 适用 DESIGN 或规约未通过强制结构、质量门禁 | BLOCKER；复用已有真实结果，不重复列相同问题 |

### D2 — 关于现实的陈述是真的吗？

和 Q2 同一套机械核查（命令手册、版本纪律、锚点漂移）。文档模式追加两项：

- **兄弟文档冲突**：两份文档把同一系统说成两样。先套 3.3 的权威规则；无声分歧是 finding。
- **现状 vs 产品意图**（doc-master 体系）：线画在哪取决于文档类型。
  - *项目与模块现状 DESIGN*（`DESIGN.md`、`DESIGN-<module>.md`）只写已交付、经核实的现实。"已废弃"、"legacy"、"原来在 X"、"不再"这类历史叙事是 finding；把未落地的方案写成现有能力同样是 finding。
  - *产品 PRD 与产品 DESIGN* 管产品意图，允许领先于实现做规划。前瞻内容是合法的。仍然算 finding 的是过程叙事（方案怎么改过、试过什么又放弃），以及把尚未交付的东西说成已经上线。
  - 写 finding 时点明文档类型。把现状规则套到产品 DESIGN 上，或在模块 DESIGN 里容忍历史叙事，都属于定错范围。

| 情形 | 严重度 |
|---|---|
| 承重路径上被代码打脸的断言 | BLOCKER |
| 现状 DESIGN 的过期事实或与适用规约冲突 | BLOCKER；仅提案非关键事实偏差按实际影响定级 |
| 模块 DESIGN 违反权威现状写作要求 | BLOCKER |
| 装饰性漂移 | INFO |

### D3 — 目标站得住吗？

- **可判定的目标**：旁观者分得清达没达成。"让系统更健壮"不可判定；"提交时零 schema 错误"可判定。
- **写明的边界**：文档说了自己不覆盖什么，或指了边界在哪。缺边界的文档是一张空白支票，实现者会拿去兑现。
- **需求缺口**：陈述了用户问题却没有任何需求回答它。文档的消费者会悄悄用他们自己的猜测把洞填上。
- **无声决策**：读者必须替作者做的选择，要么写明要么标记，不许埋在叙述里。

| 情形 | 严重度 |
|---|---|
| 达没达成没法判定的目标 | BLOCKER |
| 承重区域缺边界 | WARNING |
| 需求缺口（有问题无答案） | WARNING |
| 读者必须做决定的无声决策 | WARNING |

### D4 — 够精简吗？

每个功能、每一节、每个抽象都要对着目标挣到自己的位置：

- 回答不了任何已陈述问题的功能
- 给永远不会来的阶段预留的扩展点
- 模板建议但内容用不上的样板结构
- 没有读者的配置面

模板合规不是目标——结构为文档内容服务，不是反过来。纯精简建议按 Q4；违反适用 DESIGN 或规约的强制质量要求 → BLOCKER。不强制精简数量统计。

### 文风门禁（各模式通用）

文档的语言本身就是质量的一部分：大白话、具体、一句话一个想法、肯定式优先、用归属划边界而不是用排除。这道门抓：

- 读者要解码两遍的黑话或生造抽象名词
- 机器腔（名词化堆叠、被动语态链）
- 用否定下定义（"X 不做 Y"），而归属式（"Y 由 Z 负责"）说得更好

严重度：影响方案理解的实质表达缺陷 → **WARNING**；个别措辞 → **INFO**。受评审的现状 DESIGN 或规约违反权威技能质量要求 → **BLOCKER**。进化提案的技能交付物标准更明确：description 和正文必须大白话、精准——agent 读一遍就知道该干什么。

## 8. 严重度校准

四档，按读者该干什么定义：

| 档位 | 含义 | 判决测试 |
|---|---|---|
| **BLOCKER** | 错误方案、关键目标或验收缺失、未授权的计划范围、虚假证据、历史篡改、现状 DESIGN/各级规约不一致或违反强制质量要求 | 按 SKILL.md 判断实际缺陷 |
| **WARNING** | 可正确交付，但存在非关键歧义、验证缺口或证据充分的冗余成本 | 按 SKILL.md 判断，真实安全问题和强制质量违规不降级 |
| **INFO** | 值得知会的改进，无需行动 | "合理的作者会耸耸肩吗？" |
| **Unverified** | 断言在工作区里定不了案 | "我是不是没查成？" |

Blocker / Warning 必须有具体证据及影响；文档或规约的强制质量违规本身就是阻断依据，不需要虚构运行故障。只描述“现在还没准备好”“还没 commit”“最终环境还没拿到”不够。

刻意缺席：**规模/数量阈值**。任务数、文件数、波次数、文档长度永远不是缺陷。上下文预算按任务管理；大体量的内聚文档是正常的。

### 校准演练

| 情形 | 正确裁决 |
|---|---|
| 任务引用不存在且没有可行来源的函数 | BLOCKER（Q1） |
| 任务注册 5 个错误码，后面的任务用了第 6 个 | BLOCKER（Q1） |
| 锚点 `file.ts:964` 落在 967 行的描述函数上 | 不是 finding |
| reviewing 中的 DESIGN / Plan 尚未 commit、push 或 merge，但当前工作树内容可核对 | 不是 finding；直接评当前内容 |
| 当前 DESIGN 修改未进 HEAD，未来 approve 创建的 worktree 现在当然还看不到它 | 不是 finding；这是后续生命周期执行门禁，不是方案缺陷 |
| AC 要求最终在真实 Linux host 验证，并明确没有真实证据就不得勾选；当前开发机没有 Linux host | 不是 finding（Execution dependency） |
| Plan 与当前批准 Proposal 的关键行为或授权冲突 | BLOCKER（实施前范围/目标错误） |
| 已授权的新 Proposal 目标与现状 DESIGN 不同 | 不是 finding；实施后同步成果 |
| 缩到 "v1"，而 `D-04` 授权了静态层 | 不是 finding（Q3） |
| 缩到 "v1"，而 `D-04` 说"配置页展示计算出的费用" | BLOCKER（Q3） |
| Plan 加 `fast-xml-parser`，标准库没有 XML 解析器、也没装别的 | 不是 finding（Q4——第 5 级正当撑住） |
| Plan 新建工具模块，重复 `src/lib/hash.ts:12` | WARNING（Q4——第 2 级） |

| 设计文档 §2 说调度器管重试；§5 在 worker 里手写重试循环 | BLOCKER（D1——承重矛盾） |
| 现状 DESIGN 违反权威现状写作要求 | BLOCKER（D2——文档质量） |
| 产品 DESIGN 把尚未交付的能力写成未来工作，并明确标注未上线 | 不算 finding（产品意图） |
| 主 DESIGN 头部没有 `Sub-DESIGNs`，子文档通过 `Parent` 回链且能从模块地图点到 | 不算 finding（结构正确） |
| 子文档在磁盘上存在，但只有 header 提到它 | BLOCKER（D1——强制结构门禁） |
| 业务 Proposal 改了已交付默认值，并新建 `proposed/` 记录写明被替代的决策 | 不算 finding（正确的部分替代） |
| 业务 Proposal 直接原地改 `implemented/` 记录来改默认值 | BLOCKER（P3——决策被改写） |
| 业务 Proposal 声称批准范围已完成，而 Task 级验收只覆盖一个子集 | BLOCKER（P4——部分冒充全部） |
| 由已批准 Proposal 派生的 Plan 拆分方式与 Proposal 草拟的不同，但行为与边界一致 | 不算 finding（不做二次审批） |
| 由已批准 Proposal 派生的 Plan 含超出授权范围的 Task | BLOCKER（越界） |
| 业务 Proposal 有 `Status: approved` 与完整批准块，但评审拿不到授权对话 | `Unverified`，不算 finding |
| 设计文档目标是"改善开发者体验"，无任何可观察结果 | BLOCKER（D3——不可判定目标） |
| 提案明确要求将必需触发条件埋在正文而非 description | BLOCKER（违反强制能力标准） |
| 提案正文写"利用协同对齐层" | WARNING（文风门） |
| 缺沙箱查不成的疑虑 | `Unverified`，绝不是 finding |

## 9. 实例

### 实例 A — 符号无生产者（Q1，Plan 模式）

任务 2 注册五个错误码：`A_MISSING`、`A_INVALID`、`S_MISSING`、`S_INVALID`、`C_UNRESOLVED`。任务 4 描述失败分支"用 `TEMPLATE_MISSING` 快速失败"。

```yaml
check: Q1_symbols
severity: blocker
location: "{plan}.md:{任务 4 分支行}"
reality: "注册集合在 {plan}.md:{任务 2 行}；TEMPLATE_MISSING 不在其中"
impact: "任务 4 的失败分支照文面无法实现；实现者会即兴开第二个注册点"
fix: "把 TEMPLATE_MISSING 加进注册任务，或引用既有错误码"
```

### 实例 B — 假前提（Q2，Plan 模式）

Technical Context 断言"旧 schema 路径已不存在，初始化必然失败"。任务 4 移除该路径的读取器；AC#7 断言全仓搜索该旧标识符零命中。

在声明版本上，读取器还有一个 Plan 从未点名的存活调用点。

```yaml
check: Q2_facts
severity: blocker
location: "{plan}.md:{前提所在行}"
reality: "{file}:{line} 仍然 import 并调用旧读取器；搜索清单漏掉该调用点"
revision: "{commit}"
impact: "前提为假；全仓 AC 注定不过——到 verify 时才发现，预算已花光"
fix: "把存活调用点纳入某个任务的范围，或加进移除任务"
```

### 实例 C — 重复造轮子（Q4，Plan 模式）

任务 3 新建 `src/lib/retry.ts`，实现退避重试 helper。`rg 'retry|backoff' src/` 显示 `src/lib/http.ts:88` 已经有一个，四个调用点在用。

```yaml
check: Q4_ladder
severity: warning
location: "{plan}.md:{任务 3 行}"
reality: "src/lib/http.ts:88 已提供退避重试；4 个既有调用点"
impact: "两套重试实现在边界情况上各自漂移；更短的 diff 是复用既有 helper"
fix: "复用既有 helper；删掉任务 3，或把它缩成对既有实现的扩展"
```

### 实例 D — 不可判定的目标（D3，文档模式）

产品 DESIGN 的 Goal 写的是"改善 CLI 的开发者体验"。

```yaml
check: D3_goal
severity: blocker
location: "{doc}.md:{Goal 行}"
reality: "全文没有任何可观察结果；旁观者无法判断达没达成"
impact: "任何实现选择都能宣称成功；目标不会失败，所以什么也管不住"
fix: "写出变更产生的结果，例如'首次运行配置在一分钟内零手工编辑完成'"
```

### 实例 E — 静默改写已交付的决策（P3，业务 Proposal 模式）

一份提案放在 `proposed/architecture/`，`Status: proposed`，要改配置加载器的默认值合并行为。读的时候你发现它链接的 `implemented/architecture/2026-10-02-single-loader.md` 被原地改过了：`## Decision` 现在描述的是新的合并归属，而 `Status` 仍是 `implemented`，日期也没变。

```yaml
check: P3_supersession
severity: blocker
location: "{proposal}.md:{改动所在行}"
reality: "implemented/architecture/2026-10-02-single-loader.md:{行}：Decision 正文已是新行为，但文件仍是 Status: implemented，且时间早于本提案"
impact: "读 implemented 记录的人会以为新行为已经交付；当初的历史决策也无法从记录中复原"
fix: "撤销原地改动；改在新 proposed/ 记录里声明替代关系，等新范围全交付时双向互链"
```

### 实例 F — 部分交付冒充全部（P4）

一份提案的目标契约要求五个消费方全部改从 schema 读取默认值，交付证据却只列出两个已迁移模块。

```yaml
check: P4_falsifiability
severity: blocker
location: "{proposal}.md:{全范围声明所在行}"
reality: "{proposal}.md:{目标契约所在行}；交付证据只点名五个模块中的两个"
impact: "凭这份证据迁入 implemented/，记录就声称了一次并未发生的迁移；后续读者会信这个假前提"
fix: "保留在 proposed/ 并维持 Status: approved，直到全部消费方迁移完成；或经用户确认把提案范围收窄并写明"
```

### 实例 G — 正确地不报 finding（由已批准 Proposal 派生的 Plan）

一份已批准的 Proposal 授权"为两张报表做定时 CSV 导出，`Delivery: plan`"。派生 Plan 把它拆成四个 Task，用的调度库与 Proposal 草拟的不同，还加了一个 Proposal 没提过的锁文件。

**正确处理**：换库不报（属于内部手法），锁文件也不报（它保护的是已批准的行为）。评审只确认每个 Task 都在两张报表的范围内、且范围被完整覆盖。给出 `PASS`，并在 `简短核查说明` 里写明这两项检查怎么做的。

### 实例 H — 正确地不报 finding（规模与依赖准入）

六个任务、11 行 Affected Files、四个波次；`D-10` 写明"单 Plan 交付，不按任务数拆分；任务互相依赖；上下文预算按任务管理"。Plan 还新增了一个依赖，附一段话点名考虑过的标准库选项、以及各自为什么不行。

**正确处理**：规模不报 finding（规模不是缺陷），依赖也不报（第 5 级准入被显式满足）。需要的话两条都写进 简短核查说明。
