# df-proposal-review — 方案与计划评审

**你只判断一件事：照着这份方案字面执行，能不能做成、能不能达成目标、是不是用最简单直接的方式做成？**

四类文档共用这个技能，因为它们只是不同阶段上的同一件事：设计文档说"要做什么"，Plan 说"分几步怎么做"，进化提案说"怎么改一项空间能力"，业务 Proposal 说"该拍哪个板"。它们都在动手写代码前看，也都会栽在同一个坑里——照着字面做下去，要么卡死，要么造出一堆多余的东西。

**先审实质，再审格式。** 评审 DESIGN 时，先判断目标、行为、边界和归属是否正确完整，并能否沿真实代码调用路径实施。评审有 DESIGN 依据的 Plan 时，先逐项核对**新增或改变的设计契约 → 实施 Task → 可观察验收**，覆盖真实入口、失败路径和既有行为保护。闭环成立后再检查任务顺序、仓库事实、命令和格式。清单齐全不代表设计决策完整，也不代表功能交付完整；报告时先给影响架构和覆盖的实质问题，再谈次要的验证细节。

## 先选模式

看文档内容，一次选定：

- **Plan 模式** —— 文档在排任务：拆了具体步骤、先后依赖、验收条件。适用于 dev-flow Plan 和本体进化提案。
- **文档模式** —— 文档在定方案：写明目标、边界、需求、架构，还没有具体开发任务。适用于 PRD、DESIGN、子 DESIGN 等设计文档。
- **业务 Proposal 模式** —— 文档在记录一项待批准的决策：问题、选定的路径、备选方案、验收标准、风险。适用于 `proposals/{lifecycle}/{class}/` 下的业务/项目 Proposal。

如果一份文档两边都有（比如带任务列表的设计文档），两个模式都跑。

三个模式不能互相顶替。业务 Proposal 不是"任务更少的 Plan"：它承载的是必须由用户拍板的决定。按 Plan 去审它，会报出一堆根本不存在的"缺任务"；反过来按 Proposal 去审一份 Plan，等于重开用户已经关掉的决策。

如果同时要求评审 DESIGN **及其对应的 Plan**，先按文档模式评审 DESIGN，再按 Plan 模式检查它对设计的覆盖。以当前工作树的 DESIGN 内容为准，即使它尚未提交，也不能退回集成分支的旧版本来评审。

## 脚本查过的格式别重复查

Plan 模式下，`flow.sh plan check` 已经自动检查过固定格式：必填字段、占位符、TDD 与 Behavior 配对、复选框格式、AC 命令是否存在、状态名是否合法。进化提案也有 `wopal space evo check`。业务 Proposal 有 `dev-proposal/scripts/verify-proposals.py`，负责目录布局、生命周期骨架、授权字段与链接图。重复查这些纯属浪费时间、制造噪音。你要查的是脚本算不出来的东西——前后步骤能不能接上、写的情况跟仓库真实代码对不对得上、所有任务加起来能不能达成总目标。

有正式 DESIGN 依据的实施 Plan，不得安排编写、修改、批准或验证所依据 DESIGN 的 Task。设计是否已准备好、文档质量检查是否通过，应在 Plan 之前解决。遇到这种 Task 时，指出职责放错位置，并确认它是否掩盖了真正缺少的实施工作；不要只盯着文档检查命令是否通过。

方案没问题就直说没问题，马上结束。

### 先分清：方案缺陷，还是执行现场还没准备好

评审只报告**方案本身会把人带错**的问题，不把普通工作流状态、尚未完成的收尾动作、最终验收资源尚未就绪，冒充成设计缺陷。

以下情况**绝对不是 finding**：

- 设计文档、Plan、提案或代码还没 commit、还没 push、还没 merge，甚至仍是 untracked，但当前内容已经存在且就是本次评审对象；
- 最终发布前才需要的 CI、测试机、外部账号、真实设备或平台环境目前还没 provision；
- 某个依赖尚未安装、某个构建产物尚未生成，但 Plan 已明确安排在需要它之前完成；
- 文档仍处于 reviewing / draft / proposed 等正常生命周期状态；
- 验收项明确写着“没有对应环境就不得勾选”，而不是错误声称环境已经存在。

只有当方案**错误依赖这些条件已经成立**、**没有安排任何可行路径在需要时取得它们**，或因此会导致错误实现/无法交付目标时，才构成 finding。

**Git 状态硬边界**：Proposal Review 不要求评审对象或它引用的 DESIGN / Plan 先进入 commit、远端或目标分支。评审发生在提交之前完全正常，而且经常就是为了决定“这份内容值不值得提交”。只要当前工作树里能读到本次要评审的内容，就直接评审这份内容；**不得因为 HEAD、Base Commit、Integration Branch 里还没有这份修改而产出 Blocker、Warning 或 Info。** 以后某个生命周期步骤是否必须先 commit / integrate，属于 dev-flow 的执行门禁，不属于方案内容质量。除非用户明确要求检查“现在能不能执行生命周期命令”，否则不要把它写进评审结论。

严重度校准：**Blocker 必须证明“照着这份方案实施会做错、会卡死、或最终无法达成目标”。“实施前/验收前还要再做一步”本身不是 Blocker。**

### 先判断“哪里坏了”，再判断严重度

用户需要知道下一步该改什么，不只是看到一个红色标签。每条 Blocker / Warning 先归类：

- **Design gap**：目标态、架构、安全边界或产品决策本身没闭环，需要改 DESIGN / PRD。
- **Plan gap**：设计是成立的，但任务、接口、依赖或交接信息不足，需要改 Plan。
- **Verification gap**：实现路径成立，但 AC / 验证方式证明不了结果，需要改验收设计。
- **Reality mismatch**：方案依赖的仓库事实是错的，照着做会走错。
- **Lean**：能做成，但方案多造了不需要的东西；最高 WARNING。

**Execution dependency**（例如最终要一台真实 Linux 主机）本身不是 finding；只有它变成错误前提或没有可行取得路径时，才按上面最接近的类型报告。

在发出 Blocker / Warning 前，必须能补完这句话：**“照着文档做，在 {具体触发条件} 下会导致 {具体失败/返工/漏验收}。”** 补不出来，就不要用 Blocker / Warning。

**投入产出门槛：** 对每条候选问题，先衡量实际发生的可能性、对用户的具体影响，以及修复所需的开发、验证、长期维护和用户审阅成本。优先依靠已有技能规则、Agent 判断和正常评审；规则不能被脚本百分之百自动证明，本身不构成缺陷。若新增机制的实际收益不能明显覆盖成本，就不要列为 Blocker、Warning 或 Info；确需修复时，优先建议最小有效方案。

**评审范围门槛：** 只评设计是否正确、能否达成目标、是否可验证以及是否过度设计。执行 Agent 的人选、委派方式和运行引擎属于实施安排；默认协作分工可因用户决定或引擎能力而调整，不得仅因偏离默认分工就给设计提案记 Finding。用户单独要求检查执行准备时，另行说明执行安排的问题，不混入设计质量结论。

## 怎么干：通读一遍、列三张表、集中核实

评审拖得越久，废话越多。分两步走完：

**第一步——先确定目标与从设计到交付的对应关系。** 对 DESIGN，先梳理目标行为、边界、归属及代码中的实际入口。对 Plan，从所引用的 Active DESIGN 提取新增或改变的契约，逐项对应到 Task、AC 和实际运行路径；缺少对应关系首先作为候选问题。然后带行号通读评审对象一次，记录三张核对表：

1. **事实表**——文档里所有关于代码仓库、系统现状或其他文档的具体说法：数量、文件路径、行号范围、文档章节、编号（ID）、命令、参数。
2. **符号表**——每个反引号括起来的函数名/变量名/类型名（Plan 模式），每个具名的模块/组件/能力（文档模式），或每个具名的决策、默认值、边界与替代目标（业务 Proposal 模式），记下它在哪儿产生、在哪儿被使用。
3. **文件表**——文档里出现过的每一个文件路径，以及在哪一处提到的。

**第二步——先核对覆盖与设计风险，再逐项核实事实。** 文档模式先看 D3/D1，再看 D2/D4，并验证真实调用路径与相邻契约。Plan 模式先看 Q3/Q1，再看 Q2/Q4；Q3 必须对照引用的 DESIGN 和实际实施入口，不能只相信 Plan 自己的说法。业务 Proposal 模式先看 P1/P3，再看 P2/P4/P5；P1 要追批准记录，P3 要把提案触及的既有 `implemented/` 记录找出来。决策脉络理清后再集中运行事实核对命令，不要反复通读原文。

只做定点核实，不做大海捞针：查文件在不在用 `test -e`，看指定行号用 `sed -n 'Np'`，找章节和符号用 `rg -n`。绝不要为了核对一个小节去通读整本设计文档。一份正常规模的方案 15–25 条命令就能审完。

实在没法核实的说法放进 `Unverified`（未核实），绝不硬凑成问题（finding）。

## Plan 模式：查四个问题

| | 问题 | 重点抓什么 |
|---|---|---|
| Q1 | 前后步骤接得上吗？ | 没人创建的文件、没人定义的函数/符号、没人负责的验收项（AC）、执行顺序和依赖关系颠倒 |
| Q2 | 关于仓库现状的说法是真的吗？ | 路径已改名或不存在、行号指错地方、数量算错、跟设计文档冲突、命令根本跑不通 |
| Q3 | 做完真能达成总目标吗？ | 目标漏了没排任务、关键决定被悄悄缩水、永远不会报错的假验收项 |
| Q4 | 做法够精简吗？ | 为未来瞎预留的架子、重复造仓库里已有的轮子、多余的第三方依赖、换新忘了删旧 |

**从 Q3 开始，再看 Q1。** 对有正式设计依据的 Plan，先用设计的实际变化对照所有 Task 和 AC，并追踪正常入口以及绕过主要工具包装的入口；不要仅凭 `Affected Files` 或 AC 清单判断覆盖完整。核对完设计覆盖，再用 Q2 验证仓库事实、用 Q4 检查精简程度。Q4 发现的问题最高定为 WARNING，不单独卡死（BLOCK）。

### Q1 — 前后步骤接得上吗？

1. **每条验收项都有任务认领。** `Agent Verification` 里的每一条验收项（AC），都必须被某个 Task 的 `Verification Intent` 认领，或者明确标出是跨任务联调。顺手看一眼归类对不对：凡是能跑命令自动测的（单测、lint、类型检查）都该放在 Agent Verification，不能推给人工验收（User Validation）。
2. **用到的符号都有出处。** 后面任务调用的每一个函数名、常量名、类型名，前面必须有任务创建它，且名字拼写一模一样。比如任务 1 写"注册 5 个错误码"，任务 3 写"抛出 `TEMPLATE_MISSING`"，中间对不上号就会在实施时卡死。这是最容易抓出硬伤的一步。
3. **测试行为写得够具体。** TDD 任务里的每条 Behavior 都能直接写成一条失败测试，不用靠猜。只写一句"功能正常工作"属于没写清楚。
4. **执行顺序符合依赖关系。** 被调用的必须排在调用方前面。只有明确声明"并行执行"的任务，改同一个文件才算冲突。
5. **Task 交付的是实施，而不是生产设计。** 编写或检查所依据的 DESIGN 属于 Plan 之前的工作；即使设计文档尚未提交，也不应因此新增一个实施 Task。判断这种 Task 只是增加噪音，还是掩盖了遗漏的实施工作。

**文件表只是预计改动范围，不用逐行对账。** `Affected Files` 表只是预计会碰哪些文件，不要拿每个任务里的文件列表去跟总表死磕。只抓两件事：前提搞错了（比如文件明明已经存在，却写"新建该文件"），或者声明并行执行的任务改了同一个文件。

严重度：用到的符号没人创建、名字拼错、创建者排在调用者后面、并行任务改同一文件 → **BLOCKER**。验收项没人认领、Behavior 没法写成测试、自动化检查塞进了人工验收、文件新建/删除前提搞错 → **WARNING**。

### Q2 — 关于仓库现状的说法是真的吗？

一切以仓库里的真实代码为准。文档里的每个事实说法都要跑命令核对，不能看它"写得像真的"就放过。

| 文档说法 | 怎么查 |
|---|---|
| "共有 36 个能力" | 去代码或目录里亲手数一遍 |
| "`src/x.ts` 已存在" | `test -e` |
| "`file.ts:619-669`" | `sed -n '619p'`——行号偏几行没关系，但指到完全不相干的代码就不行 |
| "DESIGN.md §3 规定了 X" | `rg -n '^#{2,3} '` 找到对应章节看原文 |
| "D-12" / "issue #45" | 去对应文档或 issue 里核对编号 |
| "运行 `flow.sh verify`" | 看脚本里有没有这个子命令和参数 |
| "新建文件 F" / "删除文件 F" | `test -e` 看现在到底有没有 |

**写明你核对的是哪个内容快照**——例如当前工作树（包含未提交修改）、Base Commit、worktree HEAD 或主分支 HEAD。如果评审对象本身就在当前工作树里，默认以当前工作树内容为准；不要为了“可复现”把它降格回旧 HEAD。

接着核对它引用的上级文档（设计文档、`AGENTS.md`、现有接口定义）：找到原文比对。如果文档明确说了"这里跟原设计不同，原因是 X"，这叫合理调整；如果一声不吭就跟上级设计或规则对着干，就是违规。要是两份参考文档自己就矛盾，先分清哪一份是当前生效的权威版本。

这里核对的是**内容事实和实现前提**，不是 Git hygiene。当前工作树里的未提交 DESIGN / Plan 与已提交文件一样，都是合法评审对象。**不得把“当前 HEAD 还没有这段设计”“approve 后的新 worktree 现在还看不到它”“还没 push/merge”转换成 proposal finding。** 如果文档明确声称“commit X 已包含 Y”，但事实不是这样，可以只核对这句事实本身；不要把“Y 还没提交”升级成设计或 Plan 缺陷。

严重度：方案立脚的前提是错的、悄悄违背安全规则、验收命令根本跑不起来 → **BLOCKER**。跟文档有出入但不影响实际开发 → **WARNING**；不影响理解的细微出入或行号小偏移 → **INFO**。

### Q3 — 做完真能达成总目标吗？

**完整流程验收核对。** 涉及公开命令或用户流程的 Plan，先查看项目 `AGENTS.md` 中适用的验收规范。检查 Task 和 AC 是否能证明用户从真实入口完成目标任务、获得最终结果，并覆盖关键失败与副作用安全约束；不能因为列出了现有测试文件、测试全绿或依赖 Mock 的内部测试，就推断完整流程已验收。能自动执行的真实流程验证应归 Agent Verification，不应交由用户逐条手工回归。E2E 按完整用户任务定义，而不是按 GitHub 或网络访问定义；只对 Plan 实际声明的范围评审，不自行扩大产品范围。

最亏的失败：每个小步骤都合格，合起来却没把正事干完。

1. **总目标和设计变化没有漏项。** 把已确认的 DESIGN 中新增或改变的契约拆成具体行为；每项必须有实施 Task 覆盖，包括绕过主入口的调用方，以及关键回归的测试保护。
2. **既定决策没有缩水。** 每条 `D-xx` 拍板的决定，任务做出来的必须是完整效果；需要对照实际代码路径核实，而不是看 Plan 有没有重复设计原话。重点盯"v1"、"简化版"、"先写死（hardcoded）"、"先这样"这类缩水词：如果文档明确写了分阶段做，没问题；如果目标要完整版，任务里却悄悄缩水成残次品，必须揪出来。
3. **验收项真能抓出 bug。** 问一句：假如代码写坏了，这条 AC 会报错吗？不管代码对不对永远都能过的 AC 只是摆设。
4. **别人拿到就能直接动手。** 开发人员只看这份文档就能直接写代码吗？前一步任务产出的函数签名、数据结构要写清楚，不能只含糊写一句"使用上一步的结果"。只在缺了信息会导致写错代码时才报问题。

严重度：目标漏了没排任务、关键决策被悄悄缩水 → **BLOCKER**。验收项抓不住错、任务缺关键接口信息导致没法开工 → **WARNING**。文档自己明确说明的分阶段简化 → 不算问题。

### Q4 — Lean：做法够精简吗？

对 Plan 要新建的每一个东西（新模块、新类、新接口、新配置项、新依赖），按下面 6 步挨个问：

1. **这东西真的需要存在吗？** 只有一个实现类的接口、只造一种对象的工厂、永远不会改的配置项、没人调用的扩展钩子——这种"为未来预留"的架子直接砍掉，一句话说明白。
2. **仓库里已经有现成的了吗？** Plan 要新写的工具函数或模块，旁边文件里是不是已经有了？用 `rg` 搜一下，绝不让它重复造轮子。
3. **语言标准库自带吗？** 标准库几行就能干的事，不准引第三方包。
4. **平台或系统原生就有吗？** 运行时或系统原生就支持的能力，不准再包一层代码或装新依赖。
5. **写法最直接吗？** 同样的功能，能不能用更少的文件、更短更直白的结构做出来？
6. **换新时排了拆旧吗？** 如果 Plan 是用新模块、新写法或新依赖替换旧方案，必须检查它有没有安排删除被淘汰的旧文件、旧单测和 `package.json` 旧依赖——只排"建新"不排"拆旧"，落地后一定留死代码。

严重度——Q4 最高定为 WARNING：为未来瞎预留的抽象、重复造已有轮子、多余的新依赖、替换旧方案却没排清理任务 → **WARNING**（改法是给 Plan 瘦身或补上清理步骤）。同样的逻辑有更短写法 → **INFO**。完全没赘肉 → 写 `Lean already` 即可。

如果是本体进化提案，在 Q1–Q4 之外多查一条：要改的技能/规则/agent 必须符合平台规范——frontmatter 必须有 `name` 和 `description`、触发条件必须写在 description 里、正文只留工作流/输出格式/注意事项、长篇细则放进 `references/`、语言必须是大白话。违反 → **WARNING**。

当业务 Proposal 的交付物里包含技能、规则或命令时，同一条能力门禁同样适用：它承诺的产物必须守这些规范。这门禁看的是提案声明的交付物；落地文件由实施后评审复查。

## 业务 Proposal 模式：查五个问题

这里的产品是**决策本身**，不是文笔。从 P1 和 P4 起手：一项没被真正拍板的决策、一组没被认真比较的备选，会让下面所有检查失去意义。

| | 问题 | 重点抓什么 |
|---|---|---|
| P1 | 这真是个"已经定下来"的决定吗？ | 只描述了方向却没落到选择上、边界从来没被用户划定、批准后范围悄悄变大 |
| P2 | 文中陈述的事实成立吗？ | 路径已改名、拿"现状"当论据但代码不是这样、没人真的数过的数字 |
| P3 | 备选方案是真的吗？ | 为了衬托选定方案而编造的稻草人、真正够格的对手被漏掉 |
| P4 | 它能被证伪吗？ | 怎么都算过的验收标准、没有可观察结果的"提升"、列了风险却没定边界 |
| P5 | 这项决策够精简吗？ | 问题不需要的机制、除了一张任务表之外没有别的内容 |

### P1 — 这真是个"已经定下来"的决定吗？

找出那句话说清"选了什么"。如果读者读完方案章节仍然说不出选了什么、排除了什么，那这项决策没有被做出，只是被描述了一遍。

同一遍里把边界也查掉：

- 定下来的方案会说清自己**不做什么**。边界空着，实施的人就会替你编一个。
- `Status: approved` 必须能追到真实的用户批准和写明的 `Authorized scope`。格式齐全的批准块只是授权的**证据**，不是授权：如果范围写成"全部"，或者只是把标题复述了一遍，就视为范围未声明，直接指出。脚本能确认形状，只有对话能确认授权。
- 批准之后，任何新决策或实质范围变化都要重新确认。批准范围悄悄长大了，就等于在新尺寸上没被批过。

严重度：决策不可判定，或批准范围实际上什么都没授权 → **BLOCKER**。关键处缺边界 → **WARNING**。

### P2 — 文中陈述的事实成立吗？

与 Q2／D2 同一套办法。权威是仓库，不是文字。逐条机械核实，并写明核对的是哪个内容快照。

严重度：决策所依赖的前提是错的 → **BLOCKER**。过时说法但不影响决策 → **WARNING**。不影响理解的细微出入 → **INFO**。

### P3 — 备选方案是真的吗？

`## Alternatives considered` 存在的意义，是让被否掉的路子月底不会被人重新提一遍。逐条用这个标准读：**一个认真的作者会不会真的考虑过它？文中给出的理由真的能击败它吗？**

- 只用"增加复杂度"打发掉，既没说清会坏在哪、也没说清代价 → 不算真正的否决。
- 同伴文档、同类实现或用户已经提过的方案被漏掉 → 比较不完整。
- 从早先提案里被复活、却没说清当初的结论为何不再成立 → 分流环节缺失。

**替代关系的合规性在这里查，不另开一遍。** 涉及既有 `implemented/` 记录的决策：

| 提案的做法 | 判定 |
|---|---|
| 改了默认值、边界或决策，并写明替代了早先哪些决策、哪些继续有效 | 通过——部分替代，声明清楚 |
| 不新建提案，直接原地改动 `implemented/` 的决策 | **BLOCKER**——静默改写历史决策 |
| 把原本 `implemented/` 的提案退回 `proposed/` 重新审批 | **BLOCKER**——已闭环的成交记录消失了 |
| 声称要替代，但在新范围全交付之前就改了老记录 | **BLOCKER**——读者会把未交付的改动当成既成事实 |
| 完全替代后，老记录仍留在活跃区并与之矛盾 | **BLOCKER**——两套说法同时生效，读者无从选择 |
| 完全替代，交付时吸收老提案的理由或把它归档冻结 | 通过 |
| 只同步路径、名字或实现细节，决策未变 | 通过——原地事实同步正是要求的行为 |

其余情形严重度：被否掉的理由其实站不住，或真正够格的方案缺席 → **WARNING**。只是措辞不够讲究 → **INFO**。

### P4 — 它能被证伪吗？

逐条问验收标准：**如果交付的东西是错的，这条抓得住吗？** 只是把目标复述一遍、或任何合理实现都不可能失败的条目，是装饰。

- `## Risks` 要给每条风险定边界，不能只报个名字。"性能可能下降"却没阈值、没观测方法，是一句话，不是风险。
- 决策必须写明"出现什么现象就说明当初选错了"。没有这个信号，将来没人能回头修正。
- 提案声称部分交付时，核对声明与证据是否一致：留在 `proposed/` 且 `Status: approved` 的提案本来就是部分交付，如实写明不算缺陷；把部分范围说成全部完成才是。

严重度：验收标准永远不会失败，或"全部交付"的声称与证据矛盾 → **BLOCKER**。风险无边界、缺复查信号 → **WARNING**。

### P5 — 这项决策够精简吗？

爬 Q4 同一把梯子，只是对象换成决策而不是任务清单：

1. 这项决策真的需要做吗——现在的行为真是个问题吗？
2. 答案是不是已经被某份 `implemented/` 记录或某条生效规则定了？把它引出来。
3. 更小的决策够不够——改个默认值，而不是新造一个子系统？
4. 换掉的东西清理了没有——老决策、它的记录、它的链接？

严重度：与 Q4 同一上限。重复一份已有定论的方案 → **WARNING**（改法是引用既有记录）。同样决策写得更短 → **INFO**。没什么可砍 → 写 `Lean already`。

### 审阅由已批准 Proposal 派生的 Plan

这是最常见的越界，所以说清楚：**审一份已获批准的 Proposal 派生出来的 Plan，不是第二次设计审批。**

- 设计决策已经关掉了。不要重开它、不要重排备选方案、不要问用户当初是不是该选别的。
- 只查这些：每个 Task 是否都交付批准范围里的一块、有没有 Task 超出范围、Plan 自身的顺序与完成定义是否成立、照着做完能不能得到已验收的结果。
- 超出批准范围的 Task → **BLOCKER**（那是没被批过的工作）。交付不足却声称完成 → **BLOCKER**。只是内部实现手法与 Proposal 草拟的不同、但批准的行为与边界都还在 → 不算问题。
- 如果 Plan 暴露出批准范围其实无法按原样交付，那是给用户的 **Requirement Question**，不是评审期间重新设计 Proposal 的许可。

## 文档模式：查四个问题

设计文档还没有拆具体任务，改查下面四件事（D4 同样最高定为 WARNING）：

| | 问题 | 重点抓什么 |
|---|---|---|
| D1 | 文档前后自洽吗？ | 前后章节自相矛盾、生造概念没解释或前后意思不一、新模块没写明归谁管 |
| D2 | 关于现状的说法是真的吗？ | 文件路径已过期、说法跟现有代码矛盾、跟关联设计文档冲突、把变更历史当现状写 |
| D3 | 目标和边界清楚吗？ | 目标没法衡量算不算完成、没划定不做哪些事、列了痛点却没对应方案、关键选择悬而未决 |
| D4 | 内容够精简吗？ | 塞了没人要的功能、为了凑模板硬填的无用章节、为遥远未来预留的复杂设计 |

**先看 D3 和 D1。** 核实目标行为、所有相关入口、责任归属和失败语义，再决定文档结构或一致性问题是否有实质影响。

### D1 — 文档前后自洽吗？

查章节之间有没有自相矛盾；专业词或自定义概念是不是没解释就直接用，或者前后意思不一致；新引入的组件、状态归哪个模块管有没有写明。如果文档属于 `dev-doc-master` 规范体系，其结构规则（头部字段区、命名、子文档发现方式）以 `dev-doc-master/references/consistency.md` 为准，机械部分已由 `scripts/verify-docset.py` 扫描，跑一遍后把精力留给脚本看不见的内容逻辑。

**不要**要求主 DESIGN 头部枚举 `Sub-DESIGNs`。子文档靠 `DESIGN-*.md` 文件名与 `Parent` 链接自我标识，主文档在正文（通常是 `## Module Architecture` 地图）链接下来。主 DESIGN 没有头部索引是正确的，不是残缺；真正的缺陷是某个子文档只能从头部点到——脚本会把它报成孤立子文档。

严重度：核心结论前后矛盾 → **BLOCKER**；概念含糊有歧义、新组件没写明归属 → **WARNING**。

### D2 — 关于现状的说法是真的吗？

跟 Q2 一样跑命令核实：文档里凡是提到现有代码、系统行为或其他文档的地方，全部核对真伪。关联文档之间的冲突沿用 Q2 的权威判定。

历史叙述要**按文档类型分别判断**，因为 `dev-doc-master` 体系把线画在两个位置：

- **项目与模块现状 DESIGN**（`DESIGN.md`、`DESIGN-<module>.md`）**只写已交付、经核实的现实**。这里出现"已废弃"、"legacy"、"原来在 X"、"不再"这类翻旧账的叙述，或者把未落地的方案写成现有能力，都是问题——读者要看的是系统现在怎么跑。
- **产品 PRD 与产品 DESIGN** 管产品意图，允许领先于实现做规划。前瞻内容是合法的；仍然算问题的是**过程叙述**（方案怎么改过、试过什么又放弃），以及把尚未交付的东西说成已经上线。

把现状规则套到产品 DESIGN 上，或在模块 DESIGN 里容忍历史叙述，都属于定错范围。写 finding 时请点明文档类型。

严重度：关键流程上的说法跟实际代码相反 → **BLOCKER**；过期的说法但不影响核心设计决策 → **WARNING**；不影响理解的细微出入 → **INFO**。

### D3 — 目标和边界清楚吗？

目标（Goal）必须能判断"怎样才算做完"。边界（Boundary）必须写明本次不包含什么。列出来的用户痛点必须有对应的需求方案去解决——有痛点没方案，写代码的人就会自己瞎猜。需要拍板的选择必须在文档里定下来，不能含糊带过。

严重度：目标含糊到没法判断算不算完成 → **BLOCKER**；缺边界说明、有痛点无方案、关键选择没拍板 → **WARNING**。

### D4 — 内容够精简吗？

每个功能、每个章节、每层抽象都必须服务于本次目标。没人提过的多余功能、给猴年马月预留的扩展接口、为了套模板硬凑的空洞章节——统统砍掉。

严重度：与 Q4 一样，最高 **WARNING**，精简写法建议为 **INFO**。

### 语言与文风把关（两种模式通用）

文档写得像不像人话，直接决定执行会不会走样：要求用大白话、具体明确、一句话只说一件事。凡是堆砌技术黑话、生造晦涩概念、翻译腔/机器腔浓重、让人读两遍还摸不着头脑的句子，统统当作问题标出来，并直接给出大白话改法。严重度：一段话要反复琢磨才能看懂 → **WARNING**；个别句子别扭 → **INFO**。

这条规矩同样管技能（Skill）文件本身：如果提案要新建或修改一个技能，它的 `description` 和正文必须直白清楚，让人和 AI 读一遍就完全明白什么时候用、怎么用。

## 评审效率——目标 2 轮内收敛

力求在**两轮内**（初审 + 一次复审）收敛评审：

1. **首次评审覆盖所有实质缺陷**：一次性列全会改变实施、验收或设计决策的问题；没有具体触发与影响的边缘疑虑不是 finding。相同根因造成的多个症状合并成一条，不要刷屏。
2. **复审聚焦核验修复**：复审只验证已指出的修复项及直接触碰区域，避免在后期发散引入缺乏依据的个人偏好。

评审技能只负责实事求是呈现缺陷，不擅自设卡中断。迭代预算、熔断上限与升级用户机制属于控制工作流（如 `dev-flow`）。

## 裁决与报告

按对用户目标的影响排列问题：先报告设计正确性和实施覆盖缺失，其次是验收缺口，最后才是格式与命令细节。仅靠自动格式检查通过，不能声称完成了深入的设计或实施方案评审。

```
PASS   — 无 Blocker，无 Warning
REVISE — 无 Blocker，至少一条 Warning
BLOCK  — 至少一条 Blocker
```

`Unverified` 永远不改裁决。

评审开始时，每个问题建一条 todo，做掉一条勾一条。所选模式的全部问题都过手才准裁决。预算耗尽不许装作做完：报告里显式给出 `UNCOVERED CHECKS` 节，写明什么没做、为什么。

```markdown
# 提案评审 — {提案名}

## Summary
- Review type: Proposal（Plan 模式 | 文档模式 | 业务 Proposal 模式）
- Verdict: PASS | REVISE | BLOCK
- Readout: 可实施 | 需修 Plan / 验收 | 需改设计
- Counts: Blocker N / Warning N / Info N / Unverified N
- Verified against: {Base Commit | worktree HEAD | integration HEAD}
- Lean count: {net: -N lines, -M dependencies possible | Lean already}

## Blocker
### B-01: {问题标题}
- Kind: Design gap | Plan gap | Verification gap | Reality mismatch | Lean
- Location: `{文档}:{行}`
- Reality: `{文件}:{行}` 或 `{命令输出}` — {为什么这与文档矛盾}
- Impact: {执行时怎么失败}
- Fix direction: {补什么、改什么}

## Warning
{同 Blocker 格式；Impact 可省}

## Info
{每条一行}

## Unverified
- {断言} — 未能核实的原因：{原因}

## Requirement Questions
{仅当需求本身含糊、且无法从文档和代码定案时}

## Positive Findings
- {已核实项：说明怎么核实的，让读者信得过结论}

## UNCOVERED CHECKS
{仅当有检查没能完成}
```

`PASS` 必须附简短的 `Positive Findings`——查了什么、怎么查的。光秃秃的 PASS 是要读者凭信仰接受裁决。

## 裁决之后

- **`REVISE` / `BLOCK`**：修订后的文档必须复审后才算干净——没经复验的修复不是修复。复用同一个评审会话（reply），先前的 finding 还在上下文里。
- **`PASS`**：这是给评审请求方的输入，不是自动门禁。它不授权 `approve`，不替代 `plan check` 或 `evo check`，不改变执行中的状态。
- 评审不授权动手改。finding 交回文档所有者。
