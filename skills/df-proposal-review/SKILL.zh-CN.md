# df-proposal-review — 提案评审

**你只判断一件事：照着这份提案字面执行，工作能不能成、能不能交付目标、是不是用最省的方式交付？**

三类文档共用这个技能，因为它们本质是同一件事在不同尺度上的形态：设计文档提议"建什么"，Plan 提议"怎么执行"，进化提案提议"怎么改一项能力"。它们都在动手前阅读，也都死于同一种方式——照着字面执行，要么失败，要么造出一堆没人要的东西。

## 先选模式

看文档本身，一次定死：

- **Plan 模式** —— 文档在调度工作：任务、依赖、验收标准。覆盖 dev-flow Plan 和本体进化提案。
- **文档模式** —— 文档在陈述意图：目标、边界、需求、架构。还没有任务。覆盖 PRD、DESIGN、子 DESIGN 以及一切设计文档。

如果文档两种面孔都有（比如带任务清单的设计文档），两个模式都跑。

## 脚本管的部分别碰

Plan 模式下，`flow.sh plan check` 已经管住了表单：字段齐全、占位符、TDD↔Behavior 配对、checkbox 形状、AC 命令存在性、状态合法性。进化提案有自己的门禁：`wopal space evo check`。复查这些是浪费，只会产出噪音。你的审查对象是正则算不出来的东西——各部分是否拼得上、是否贴得住现实、加起来是否等于目标。

提案没问题就快说没问题，然后停。这个评审是被刻意调用的，不是走仪式。

## 怎么干：读一遍、建三张清单、再验证

效率是评审质量的一部分——耗时拉长的评审只会产出噪音。两遍走完。

**第一遍——带行号通读文档一遍。** 读的过程中填好三张清单，后面全靠它们干活：

1. **事实**——文档里关于仓库、系统、其他文档的每一个具体断言：数量、路径、行号、文档章节、ID、命令、参数。
2. **符号**——每个反引号里的代码名（Plan 模式），或每个具名的组件/能力（文档模式），谁创建它、谁使用它。
3. **文件**——提到的每一个路径，以及它是在哪被提到的。

**第二遍——从清单出发回答问题。** Plan 模式：Q1 和 Q3 只需要文档本身；只有 Q2 触碰仓库——把命令攒一批一起跑。文档模式：一致性和目标检查靠文档本身，然后对照代码和兄弟文档验现实。不要在检查之间反复回读文档——每回读一次，亏掉的比省下的多。

验证，不是巡查：路径用 `test -e`，行号锚点用 `sed -n 'Np'`，章节和符号用 `rg -n`。永远不要为了确认一节内容去通读整份设计文档。一份正常的提案大约 15–25 条命令就能审完。

定不了的断言放进 `Unverified`——绝不拔高成 finding。

## Plan 模式：四个问题

| | 问题 | 抓什么 |
|---|---|---|
| Q1 | 各部分拼得上吗？ | 没人产出的文件、没人创建的符号、没人认领的 AC、顺序和依赖打架 |
| Q2 | 关于仓库的陈述是真的吗？ | 过期路径、错位锚点、虚报数量、和设计文档的无声冲突、跑不起来的命令 |
| Q3 | 执行它能交付目标吗？ | 有目标无任务、决策被悄悄缩水、验不了任何事的 AC |
| Q4 | 这是最省的交付方式吗？ | 投机抽象、重复造轮子、多余依赖 |

Q1–Q3 判断 Plan 能不能成。Q4 判断它成的时候有没有虚胖——一个 Plan 可以三关全过但形状不对。Q4 自身永不 BLOCK：极简类发现封顶 WARNING。

### Q1 — 各部分拼得上吗？

1. **行为有人认领。** 每条 Agent Verification 都被某个 Task 的 `Verification Intent` 引用，或显式标注跨任务。顺带查归位：能机械验证的（测试、lint、typecheck）归 Agent Verification，不该塞给 User Validation。
2. **符号有生产者。** 任务用到的每个代码名，都由更早的任务创建，拼写完全一致。前一个任务"注册五个错误码"，后一个任务"用 `TEMPLATE_MISSING` 快速失败"——裂缝就在这。这是全评审产出最高的一条检查。
3. **行为规格是真的。** TDD 任务的每条 Behavior 不用猜就能变成失败测试。"工作正常"是未定义行为。
4. **顺序贴着依赖。** 消费者排在生产者后面。任务间重叠只在声明并行执行时才是冲突。

**文件是预期范围，不是合同。** `Affected Files` 表是预期足迹；不要拿任务级清单去对账。只查两样：过期的操作前提（"创建"一个已存在的文件）、声明并行时的文件重叠。

严重度：符号无生产者、生产者拼写不一致、生产者在后面的波次、并行文件重叠 → **BLOCKER**。AC 无人认领、Behavior 不可测、可自动验证的检查塞进 User Validation、过期文件前提 → **WARNING**。

### Q2 — 关于仓库的陈述是真的吗？

仓库是唯一权威。每条事实断言机械核实；绝不因为"看起来对"就放行。

| 断言 | 核查 |
|---|---|
| "36 个能力" | 在真相源里数一遍 |
| "`src/x.ts` 存在" | `test -e` |
| "`file.ts:619-669`" | `sed -n '619p'`——小幅漂移没关系，落在不相干的构造上不行 |
| "DESIGN.md §3 说了 X" | `rg -n '^#{2,3} '` |
| "D-12" / "issue #45" | 在它的真相源里找到这个 ID |
| "运行 `flow.sh verify`" | 命令存在吗、接这个参数吗 |
| "创建文件 F" / "删除文件 F" | `test -e` |

**注明你核查时对着的版本**——Base Commit、worktree HEAD 或集成分支 HEAD。没有版本的 finding，谁一提交就烂掉。文档声明了 worktree 的，就在 worktree 的 HEAD 上探查。

然后对照它引用的权威（设计文档、`AGENTS.md`、既有接口）：找到权威原文，比对。文档自己承认并说明理由的分歧是决策；无声的分歧是违约。两份文档打架时，先判定对这个文档所实现的模型哪一份才是权威，再定冲突。

严重度：工作依赖的假前提、对安全约束的无声背离、跑不起来的 AC 命令 → **BLOCKER**。对工作无影响的无声文档分歧 → **WARNING**；装饰性漂移 → **INFO**。

### Q3 — 执行它能交付目标吗？

最贵的失败：每关都过，交付却缩水。

1. **目标被覆盖。** 把 Goal 拆成独立部分；每个部分都要有任务。
2. **决策被交付。** 每条 `D-xx`，任务交付的是它陈述的东西本身，不是影子。盯缩水词（"v1"、"简化版"、"硬编码"、"先这样"），然后裁决：缩水和 Goal 矛盾吗？有显式授权吗？只有无声缩水是 finding。
3. **AC 能失败。** 功能坏了，这条判据会红吗？怎么都不红的 AC 是装饰品，不是验证。
4. **交接得出去。** 实现者只拿这份文档就能开工吗？前置任务的接口和输出是点名的，不是暗示的。只标会导致走错路的信息缺失。

严重度：有目标无任务、决策无声缩水 → **BLOCKER**。AC 验不了任何事、任务凭文档自身开不了工 → **WARNING**。文档自己授权的缩水 → 不是 finding。

### Q4 — Lean：这是最省的交付方式吗？

对 Plan 创建的每个新东西爬梯子。停在最先撑住的那一级；新东西必须落在那一级上：

1. **它根本需要存在吗？** 只有一个实现的接口、只造一个产品的工厂、给从不变化的值做的配置、没有消费者的扩展点——投机需求直接砍，一句话说明。
2. **仓库里已经有了吗？** Plan 要新建的 helper、模块、模式，隔壁文件里已经活着——重复造轮子是最常见的赘肉。用 `rg` 查，不靠感觉。
3. **标准库能干吗？** 一个新依赖，干的活标准库本来就会。
4. **平台原生覆盖吗？** 代码或依赖在干平台白送的事。
5. **活动部件最少吗？** 同样的逻辑，更短更直接的写法就能交付。

严重度——Q4 永不 BLOCK：投机抽象、重复造轮子、多余新依赖 → **WARNING**（修法是给 Plan 瘦身；极简判断见仁见智，不是执行失败）。同样逻辑有更短写法 → **INFO**。没得砍 → 说一声 `Lean already`，走人。

本体进化提案在此基础上加一道门：落地结果必须满足平台自身的能力标准——frontmatter 有 `name` + `description`、触发条件写在 description 里、正文只放工作流 + 输出 + 注意事项、长内容下沉到 `references/`、不发明多余结构。交付物违反 → **WARNING**。

## 文档模式：四个问题

文档模式没有任务可调度，问题换形。Q4 保留名字和严重度上限。

| | 问题 | 抓什么 |
|---|---|---|
| D1 | 文档自洽吗？ | 章节互相打架、术语没定义或一词两用、状态没有归属 |
| D2 | 关于现实的陈述是真的吗？ | 过期路径、被代码打脸的断言、和兄弟文档的无声冲突 |
| D3 | 目标站得住吗？ | 没法判定的目标、边界缺口、没人接的需求、无声决策 |
| D4 | 够精简吗？ | 没人要的功能、从模板抄来而不是长出来的结构 |

### D1 — 文档自洽吗？

章节之间自相矛盾；术语先用后定义、或两种用法；文档引入的组件或状态没人负责。还有结构合规：文档属于 `dev-doc-master` 体系时，结构规则（header 双区、双向索引、命名）以 `dev-doc-master/references/consistency.md` 为准——其中机械部分已经被它的质量门禁脚本扫过（`scripts/verify-docset.py`），有就跑；把你的评审花在脚本看不见的东西上。

严重度：承重陈述的内部矛盾 → **BLOCKER**；真歧义的未定义术语、文档引入的组件缺归属 → **WARNING**。

### D2 — 关于现实的陈述是真的吗？

和 Q2 同一套机械核查：关于代码、系统、其他文档的每条断言都对着现实定案。兄弟文档冲突沿用 Q2 的权威规则。属于 `dev-doc-master` 体系的文档还要守**目标态写作**——"已废弃"、"legacy"、"原来在 X"、"迁移"这类历史叙事就是 finding，因为读者要学的是现在的结构，不是它的历史。

严重度：承重路径上被代码打脸的断言 → **BLOCKER**；不影响决策的过期陈述 → **WARNING**；装饰性漂移 → **INFO**。

### D3 — 目标站得住吗？

文档的 Goal 必须可判定：旁观者分得清达没达成。边界：文档说了自己不覆盖什么，或指了边界在哪。需求缺口：陈述了一个用户问题却没有任何需求回答它，这是洞不是细节——这份文档的消费者会悄悄把它填上。无声决策：读者必须替作者做的选择，要么写明要么标记，不许埋着。

严重度：达没达成没法判定的目标 → **BLOCKER**；缺边界、无人接的需求 → **WARNING**。

### D4 — 够精简吗？

每个功能、每一节、每个抽象都要对着目标挣到自己的位置。没人问题的功能、给永远不会来的阶段预留的扩展点、模板建议但目标用不上的样板结构——砍。模板合规不是目标：结构为文档自己的内容服务。

严重度：与 Q4 同一梯子——封顶 **WARNING**，更短写法建议 → **INFO**。

### 文风门禁（两种模式通用）

文档的语言本身就是质量的一部分：大白话、具体、一句话一个想法、肯定式优先、用归属划边界而不是用排除。堆黑话、生造抽象名词、机器腔的段落都是 finding——提案只有被读者一遍读懂才算能用。标注时给出问题所在行和白话改写方向。严重度：读者要读两遍才能懂的段落 → **WARNING**；个别别扭的句子 → **INFO**。

这道门同样管技能自身：本体进化提案的交付物是技能时，它的 description 和正文必须大白话、精准——agent 读一遍就知道该干什么。

## 预算——每份提案最多评审 2 次

每份提案最多评审**两次**：首次评审 + 至多一次复审；复审报告即终局。

1. **首次评审必须穷尽**：所有 finding 一次性列全，包括边缘发现。藏着掖着是缺陷服务。
2. **复审 = 验证修复 + 全量重扫**：本轮发现的一切即终局——没有下一轮来补漏。

## 裁决与报告

```
PASS   — 无 Blocker，无 Warning
REVISE — 无 Blocker，至少一条 Warning
BLOCK  — 至少一条 Blocker
```

`Unverified` 永远不改裁决。

评审开始时，每个问题建一条 todo，做掉一条勾一条。四问全部过手才准裁决。预算耗尽不许装作做完：报告里显式给出 `UNCOVERED CHECKS` 节，写明什么没做、为什么。

```markdown
# 提案评审 — {提案名}

## Summary
- Review type: Proposal（Plan 模式 | 文档模式）
- Verdict: PASS | REVISE | BLOCK
- Counts: Blocker N / Warning N / Info N / Unverified N
- Verified against: {Base Commit | worktree HEAD | integration HEAD}
- Lean count: {net: -N lines, -M dependencies possible | Lean already}

## Blocker
### B-01: {问题标题}
- Location: `{文档}:{行}`
- Reality: `{文件}:{行}` 或 `{命令输出}` — {为什么这与文档矛盾}
- Impact: {执行时怎么失败}
- Fix direction: {补什么、改什么}

## Warning
{同 Blocker 格式；Impact 可省}

## Info
{每条一行}

## Unverified
- {断言} — 未能核实的原因：{原因}

## Requirement Questions
{仅当需求本身含糊、且无法从文档和代码定案时}

## Positive Findings
- {已核实项：说明怎么核实的，让读者信得过结论}

## UNCOVERED CHECKS
{仅当有检查没能完成}
```

`PASS` 必须附简短的 `Positive Findings`——查了什么、怎么查的。光秃秃的 PASS 是要读者凭信仰接受裁决。

## 裁决之后

- **`REVISE` / `BLOCK`**：修订后的文档必须复审后才算干净——没经复验的修复不是修复。复用同一个评审会话（reply），先前的 finding 还在上下文里。
- **`PASS`**：这是给评审请求方的输入，不是自动门禁。它不授权 `approve`，不替代 `plan check` 或 `evo check`，不改变执行中的状态。
- 评审不授权动手改。finding 交回文档所有者。
