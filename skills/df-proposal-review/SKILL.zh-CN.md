# 提案评审

## 评审对象和依据

评审判断方案是否能正确、完整、精简地达成用户目标，是否可实施、可验收。先审实质，再核实事实和格式；独立只读，不替用户决定产品方向，不代作者修改文档。

按实际对象选择模式：

| 模式 | 对象 | 评审依据与目标 |
|---|---|---|
| 业务 Proposal | 业务或项目提案 | 用户目标、现有代码、相关决定与规约；判断设计决策和验收要求是否成立 |
| Plan | dev-flow Plan、本体进化提案 | 当前已授权的来源、任务衔接和真实实施路径；判断能否完整落实目标 |
| 文档 | PRD、产品 DESIGN、项目或模块现状 DESIGN | 文档所属类型及其权威技能标准；判断意图或现状描述的正确性、完整性和质量 |

混合对象按相应模式分别检查，合并同源问题。业务 Proposal 不要求编写 Task；Plan 不重新审批已经确定的设计决定。提案驱动交付以当前 Proposal 为唯一实施目标依据，Plan 只组织执行。Issue 路线和进行中的旧 Plan 沿用原合同。现状 DESIGN 是实施成果和当前系统事实的参考，不是提前编写的新目标；产品 PRD/产品 DESIGN 的前瞻规划职责不变。

## 核实方法

完整阅读评审对象，梳理目标、决定、行为边界、关键路径及验收要求，再列出需要验证的事实、符号、文件及依赖，定向读取实际代码和适用文档/规约。先闭合目标到行为到验收的证据链，不因清单齐全而认定方案完整。详细方法、例子与命令见 `references/review-rubric.md`。

使用实际评审的工作树内容（包括未提交变更）或指定版本，报告核查范围。没有提交、推送、合并，正常草稿状态，尚待执行的安装、构建或最终验收环境本身均非缺陷；只有方案依赖错误前提或没有可行的取得路径才报告问题。

复用适用的 `flow.sh plan check`、`wopal space evo check`、`verify-proposals.py`、`verify-docset.py` 等机械门禁及真实结果；不重复人工检查其已证明的事项，不把未来才需完成的检查当成当前失败。评审文档或规约时加载 `dev-doc-master`、`dev-proposal`、`space-master` 等对应技能，按实际 SOP 和质量要求核查。未经核实的结论明确注明，不冒充缺陷。

## 业务 Proposal：五项检查

| 检查 | 要点 |
|---|---|
| P1 决定与边界 | 用户要解决的问题、选定设计、范围、排除项、默认值、关键行为和失败边界清晰；待用户决定的问题不得伪装成已批准 |
| P2 事实与可行性 | 现有系统事实、依赖、调用路径、技术约束真实；方案有可行的实现路径 |
| P3 备选与历史决定 | 真实比较已考虑的替代方案，判断理由有效；按 dev-proposal 检查已交付历史决定的替代和保护 |
| P4 验收与风险 | 验收能证明用户目标和关键失败行为；能区分成功、失败。对实质风险说明影响及必要的控制或观察方式 |
| P5 简洁性 | 不为没有需求的功能、抽象、配置、依赖或流程增加成本；有证据才建议精简 |

未批准的草稿可以有明确列出的待决问题，但不能以此声称已具备实施条件。已批准提案的授权以真实用户决定为准，不以格式代替授权。在验收前，用户明确授权的新决定（含扩大范围或方向调整）应融入原提案，不要求重复审批。未明确授权的实质变更仍需用户决定；无法核实授权时说明限制，不假定违规。历史 `implemented/` 决策和冻结归档遵循 `dev-proposal` 的保护规则。

提案以用户偏好语言、清晰精炼的肯定式目标态写作；新决定替换失效内容，范围、方案、验收及风险自洽，不叠加过程记录或制造备选方案。

## Plan：四项检查

| 检查 | 要点 |
|---|---|
| Q1 衔接 | 任务先后与依赖一致；符号、数据和接口有实际来源；并行任务写集无冲突，验收责任明确 |
| Q2 事实 | 路径、符号、命令、接口及现有行为等关键前提真实；引用当前适用依据 |
| Q3 覆盖与验收 | 当前授权的每项关键行为都有实施任务及可观察验收，覆盖真实入口、关键失败路径和既有行为保护 |
| Q4 精简 | 复用现有能力、标准库和原生机制，避免不必要的抽象或依赖，清理替换产生的死代码 |

先查 Q3 和 Q1，再核实 Q2、Q4。Plan 忠实落实当前授权即可；内部实现方式与提案草图不同并不构成问题。旧的现状 DESIGN 与获准的新目标有差异是正常的；按 `df-implement` 在实施后同步 DESIGN 和各层级规约，而不是要求事先改成新目标。Plan 安排实施及必要成果同步，不承担第二次设计审批。对旧 DESIGN 驱动 Plan 仍核查其原合同。

对公共命令和用户操作，依据适用规约检查真实入口到可观察结果、重要失败路径及状态安全；能自动验证的行为由 Agent 验证。测试命令可在实施中确定，只要预先写明可判定的验收要求。现有代码或依赖提供的符号无需新增生产任务。

## 文档：四项检查

| 检查 | 要点 |
|---|---|
| D1 自洽 | 章节、术语、职责、边界及关联文档一致 |
| D2 事实 | 代码、路径、默认值、接口、状态和失败行为符合真实证据 |
| D3 正确完整 | 产品文档审目标、需求、架构和可行性；项目/模块现状 DESIGN 审实际行为、职责与契约覆盖，不要求虚构未来目标 |
| D4 质量与简洁 | 按权威技能核查结构、语义覆盖、可读性、证据及适用质量规则，不复制细则 |

产品 PRD 和产品 DESIGN 可以表达未来规划；项目、模块现状 DESIGN 必须准确记录已实现的系统。核查现状文档与代码、适用规约及相关文档的一致性，不把未实施提案内容当作现状。遵循 `dev-doc-master` 的 SOP 和质量标准；涉及项目、模块、目录、文档或其他适用规约时，按其权威技能检查质量和相互一致性。

## 严重度

每个问题只定级一次，必须有具体依据、证据和影响。先区分方案决策缺陷、实施安排缺陷、验收缺陷与当前成果质量缺陷，再确定修正对象。

- **Blocker**：方案照此执行会导致目标无法达成、真实功能破坏、安全风险、错误设计或不可行路径；Plan 实质越过当前授权或遗漏关键目标；关键验收无法证明目标；虚假授权/完成证据、历史决策篡改；评审中的现状 DESIGN 或任一级适用规约存在事实或相互不一致、违反权威技能 SOP 或质量要求。明确要求交付违反强制质量规则的成果也阻断。
- **Warning**：不妨碍核心目标正确实现，但需修正的实质歧义、非关键验证缺口、过时提案表述、证据充分的冗余机制或维护成本。已获用户授权但尚未融入当前提案的调整是提案维护告警，不是未授权设计。
- **Info / 建议**：有实际参考价值的技术选型、合理取舍或更简洁的做法，不要求修复。普通正确做法、用户已认可的取舍和个人偏好不报问题。

不要因未来步骤尚未完成而判 Blocker；也不要把违反文档/规约强制质量要求降为 Warning。精简建议不能仅凭个人偏好阻断，只有独立成立的严重缺陷才阻断。建议采用最小有效修法，不另造流程或架构。无法判定的产品意图交用户决定；未验证事项如实注明。

## 评审报告

使用用户偏好语言，先让用户看懂问题并能决定是否修正，再提供实施者定位证据。按真实影响排序，合并同源发现，不输出内部分析过程。

```markdown
# 提案评审报告
范围：{评审对象、模式及核查依据/版本}
结论：PASS | REVISE | BLOCK（{N} Blocker / {N} Warning）

## Blocker
### B-01：{通俗标题}
- 位置：{文件:行号}
- 问题：{事实依据、具体问题及后果}
- 修正要求：{应修改的方案、任务或文档}
- 验收：{如何核实已修正}

## Warning
### W-01：{通俗标题}
{同样信息，简洁表达}

## 其他说明
{必要的用户决策、未验证事项或未覆盖范围}
```

空章节省略。Info、积极发现、技术建议合计最多一两句话；PASS 简述实际核查内容。无需机械输出精简行数、任务数或过程统计。给结论前尝试完成适用检查；无法完成时明确披露原因，不冒充完整评审。

PASS：已覆盖范围无 Blocker 或 Warning。REVISE：有 Warning、无 Blocker。BLOCK：至少一项 Blocker。未验证项本身不是缺陷，但不能将关键未验证内容当作已通过。

## 评审之后

评审不授权实施、审批或修改状态。问题交文档所有者修正；复核只查修正与直接影响，力求两轮内收敛，不遗漏有依据的发现，不重开已确认的选择。主控按现有流程处理审批、实施与验收。
