# 设计分析与讨论

用户要求写提案，不代表设计已经成熟。先把重要问题想清楚，再编写正式提案。设计已经明确时直接核对，不重复提问。

## 调查设计依据

- 从用户目标和当前问题出发，区分需求与用户初步提出的解决办法。
- 读取适用的 AGENTS.md、产品 PRD/架构 DESIGN、项目主 DESIGN、受影响模块 DESIGN、配套契约与现有术语表（如有），沿文档的约束关系向上追溯。查阅相关已实施提案、代码与测试，验证关键现状。范围由实际影响决定，不遍历无关模块。
- 找出必须延续的职责、依赖方向、接口、业务规则与不变量。若目标需要改变既有设计，明确指出要改变的决策、原因、影响范围与继续有效的约束，交用户决定。现有实现与已定设计不一致时，报告证据并解决影响本次设计的冲突；不把现有代码或局部便利当作推翻架构的授权。
- 复用项目已有的设计规范和术语；必要的技术验证由 Agent 完成。未能验证的前提明确标记，关键可行性未确定时不宣称设计就绪。

## 领域建模

按实际设计对象找出重要概念、含义、关系、职责、状态所有者与业务约束；使用统一术语。主动指出同词异义、同义异词、职责重叠及与代码或文档的冲突。用具体正常、异常与边界场景检验模型，追问会改变设计结果的条件。简单变更不需要独立领域模型。

新术语或定义调整先记入本次目标设计，现状 DESIGN 与已有术语表不预写尚未交付的变化。

## 按依赖关系分轮讨论

1. 识别会影响产品行为、架构、接口、状态、关键约束或交付边界的决策，按依赖关系排列；优先解决影响后续分支的决定。
2. 每轮只提出前提已明确且相互独立的问题；独立问题可以合在一轮。每个问题写清需要决定什么、可行取舍、推荐答案及理由。能从证据或既定授权确定的事实，不问用户；代码实现细节由实施者选择。
3. 用户回答后更新设计决定，重新检查下游问题、边界场景和矛盾；已明确的决定不重复询问。用户提出的方案也应接受事实、场景和现有架构检验。
4. 每轮记录已经明确的决定及必要理由、相关术语和仍待确定的问题。长讨论使用空间允许的临时记录或未批准草稿，避免上下文丢失；记录不是审批，不作为实施授权，不将讨论流水账带入最终提案。
5. 当所有会实质改变目标设计的决策已经明确、关键可行性已核实、重要风险已转为设计约束或被明确接受时，停止讨论并进入规格编写。不能解决的关键问题继续与用户讨论，不用默认值或模糊描述替代其决定。
