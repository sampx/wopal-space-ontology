# 分类方案最佳实践

按本次设计对象选择适用领域，可组合多类。下表是分析问题与目标规格的最低考虑范围，不是固定章节目录；无关的设计要素不必写。具体项目规范与上层设计优先，通用要求见 specification.md。

| 方案领域 | 至少考虑并明确适用的设计内容 |
|---|---|
| 产品功能 | 用户、目标、端到端场景、功能边界、业务规则、默认行为、异常反馈与可观察结果 |
| UI / UX | 信息架构、页面或组件职责、交互与导航、加载/空/错误/成功状态、可访问性、响应式与既有设计系统（适用时） |
| 服务端 | 模块归属、调用及数据流、接口、状态所有者、并发与一致性、权限、失败及可观测行为 |
| API / SDK | 调用者、接口语义、输入输出与约束、默认值、认证授权、错误语义、生命周期、重试或幂等、兼容与版本 |
| CLI | 命令用途、参数与默认行为、输入来源、输出与退出码、状态副作用、非交互行为、失败及恢复 |
| 架构重构 | 现状及目标的职责和依赖方向、关键协作关系、迁移边界、保持不变的行为与契约、替代机制的清理及过渡风险 |
| 数据与存储 | 数据模型和所有权、唯一性及不变量、读写与事务、并发、保留/删除、迁移、恢复及一致性 |
| 工作流程 | 角色与权限、输入输出、状态与转换条件、步骤顺序、审批责任、失败/中断/重入和恢复 |
| 测试体系 | 要证明的行为与风险、验证边界、测试层次、环境及数据隔离、质量门禁与失败诊断 |
| Agent 或自动化能力（项目内） | 触发条件、职责与授权边界、输入输出、决策规则、工具及状态、失败与恢复、验证场景 |

选择真正影响行为和架构的细节。例如 CLI 不只列命令名，要定义错误退出及失败时状态；UI 不只列页面，要定义操作触发后的反馈；重构不只画模块图，要定义保留的行为与职责转移。用具体场景和可核查约束消除歧义，不为假想的未来扩展增加设计。
