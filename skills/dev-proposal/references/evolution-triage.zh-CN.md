# 已实施提案的再变更分流

本文件回答一个问题：**一项已交付的决定，后来又要变，怎么改才算对？**

## 1. 先分清"改事实"和"改决定"

| | 改事实 | 改决定 |
|---|---|---|
| 典型动作 | 文件挪了位置、包改名了、配置 key 换了、默认值在代码里挪到别处但值没变 | 默认值变了、边界收窄或放宽、失败语义变了、选了另一条路 |
| 判定问句 | "读者按老文档理解现在的代码，会不会理解错？" | "如果老文档的作者今天重新拍板，他会做同样的选择吗？" |
| 处置 | 原地更新 `implemented/<class>/` | 新建 `proposed/` 提案 |

两个问题都答"是"很少见；一旦第二个答"否"，就一定走新建提案，不能靠原地改写糊过去。

**"优化""增强""顺手改好"这三个词不构成分类依据**。它们描述的是改动者的自我感觉，不是决定是否变化的客观事实。只要核心默认值、边界或对外契约变了，就是设计调整。

## 2. 三种情形

### 2.1 纯事实漂移 — 原地同步

代码挪了路径、包改了名、结构换了位置，但**决定本身一字未改**。

处置：

1. 在同一交付内改 `implemented/<class>/` 里的事实描述（路径、符号名、配置 key、模块归属）。
2. 不改 `Status`，不加变更日志，不加 `## History`，不写"本次更新了……"。
3. 修好因此断掉的入链。

为什么可以原地改：`implemented/` 的职责是"这套决定现在长什么样"。它跟着代码走，否则读者读到的是过期地图。

为什么不能加变更日志：现状文档记录的是现在，不是改动过程。变更过程在 Git 里。

### 2.2 设计调整 / 优化 / 局部推翻 — 新建提案

只要需要改变原决定、核心默认值、边界，或需要用户重新拍板，就新建提案。

处置：

1. 在 `proposed/<class>/` 新建 `yyyy-mm-dd-<slug>.md`，走独立评审与用户批准。
2. 新提案的 `## Problem` 必须说明它相对哪份老提案做了什么调整，并给出老提案的相对链接。
3. **全范围交付前，不修改老的 `implemented/` 提案。** 老提案代表仍然生效的历史决定；新提案还没交付就改老记录，会让读者以为改动已经生效。
4. 新提案全范围交付、迁入 `implemented/<class>/` 时，**同交付双向互链**：
   - 新提案写清部分替代了老提案的哪些决策、老提案哪些决策继续有效；
   - 老提案把被替代的段落改成现状，并链向新提案。
5. 未被替代的老提案内容原样保留——它仍然有效。

**严禁的两件事：**

- 把已 `implemented/` 的提案移回 `proposed/` 重新走审批。历史决定被搬回待审区，读者就再也分不清哪条是成交的。
- 把已 `implemented/` 的提案原地改写成另一项决定。文件名不变、状态不变，内容却换了主张——这是最隐蔽的记录腐坏，因为它看起来毫无变化。

### 2.3 彻底推翻 / 功能下线 — 完全替代

原决定整体失效，新决定替代它。

处置：新建提案（同 2.2），并在**全范围交付时当场**处置老提案，不等日后大扫除。二选一：

**A. 吸收后删除**

前提：新提案已完整保留老提案里仍然独特的：

- 当初的问题陈述与动机；
- 备选方案及各自失败的原因；
- 已知代价与遗留缺口；
- 验证方式与必要的观察条件。

配套动作：修好所有入链，然后删除老文件。

**B. 迁入 `archived/<class>/` 永久冻结**

前提：老提案仍有独立历史价值（例如它是某条长期约束的来源，或者被外部文档引用），但不再指导日常工作。

配套动作：按归档流程加 `Archived: YYYY-MM-DD`，冻结正文，修复或删除活跃文档中的入链。

不允许的第三种做法：既不吸收也不归档，让老提案留在 `implemented/` 里与新提案并存且互相矛盾。这会让读者同时看到两套说法，且没有任何线索判断哪套生效。

## 3. 归档之后

`archived/` 是**永久只读**的：

| 禁止 | 说明 |
|---|---|
| 解冻修改 | 包括"只是更新一下路径"——事实漂移也不能改归档记录 |
| 改状态 | `Status: implemented` 是终态，归档不引入新状态 |
| 补写归档日期之外的元信息 | 只允许 `Archived: YYYY-MM-DD` 一行 |
| 翻译 / 重排 / 重命名 | 冻结的含义就是字节稳定 |
| 校验其出链 | 归档记录允许有断链，那是历史快照的固有属性 |

后续演进只能新建活跃提案。需要历史背景时，新提案可以用相对链接指向归档记录。

## 4. 三种情形的判定流程

```text
发现已有 implemented/ 提案覆盖同一主题
        │
        ├─ 决定、默认值、边界都没变？
        │      └─ 是 → 原地同步事实，结束
        │
        ├─ 只是部分决策要改，其余继续有效？
        │      └─ 是 → 新建 proposed/ 提案 ──全交付──▶ 双向互链
        │
        └─ 整条决定失效，新的替代它？
               └─ 是 → 新建 proposed/ 提案 ──全交付──▶ 吸收删除 或 归档冻结
```

## 5. 常见误判

| 说法 | 为什么错 | 正确做法 |
|---|---|---|
| "只是小优化，我直接改 implemented 那份" | 优化若动了默认值或边界，就是设计调整 | 新建提案 |
| "新提案还没做完，但我先把老提案改成一致的" | 老提案仍代表生效决定；未交付的改动不该提前改写历史 | 等新提案全交付时同批互链 |
| "我把老提案移回 proposed 再走一次审批" | 历史决定被搬回待审区，成交记录丢失 | 新建提案，老提案保留或归档 |
| "归档了但顺手把过时路径改对" | 冻结记录不允许任何内容改动 | 保持原样；用新提案承载现状 |
| "老提案没用了，直接删" | 删除前必须确认独特理由已迁入新提案 | 先吸收，再删 |
| "两份提案都在 implemented，读者自己看" | 读者没有判断依据 | 双向互链，或吸收删除 |
