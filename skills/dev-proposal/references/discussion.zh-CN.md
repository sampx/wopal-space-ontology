# 提案分析与方案讨论

用户要求写提案，不代表设计已经成熟。先把重要问题想清楚，再编写正式提案。设计已经明确时直接核对，不重复提问。

## 调查设计依据

- 从用户目标和当前问题出发，区分需求与用户初步提出的解决办法。
- 读取适用的 AGENTS.md、产品 PRD/架构 DESIGN、项目主 DESIGN、受影响模块 DESIGN、配套契约与现有术语表（如有），沿文档的约束关系向上追溯。查阅相关已实施提案、代码与测试，验证关键现状。范围由实际影响决定，不遍历无关模块。
- 找出必须延续的职责、依赖方向、接口、业务规则与不变量。若目标需要改变既有设计，明确指出要改变的决策、原因、影响范围与继续有效的约束，交用户决定。现有实现与已定设计不一致时，报告证据并解决影响本次设计的冲突；不把现有代码或局部便利当作推翻架构的授权。
- 复用项目已有的设计规范和术语；必要的技术验证由 Agent 完成。未能验证的前提明确标记，关键可行性未确定时不宣称设计就绪。

## 领域建模

领域建模是主动澄清概念和规则，而非仅仅读取已有术语。随着设计讨论推进：

- 发现术语与现有定义冲突时当场指出差异，引用原定义并请用户确定含义；发现一词多义时提出精确的候选名称。例如“账号”究竟指客户身份、登录主体，还是服务凭证？
- 对同一领域概念选定一个标准名称，必要时记下容易混淆的旧称。定义用一至两句说明概念是什么，利用其他标准术语说明其关系；概念的行为和实现另归设计契约。只关注项目特有的领域概念。存在多个领域上下文时先确定术语所属范围，尊重已有术语组织方式。
- 用具体场景追问概念之间的关系、职责、数量约束、状态和生命周期。例如订单部分取消时，发票的有效金额由谁决定？用反例检验定义，直到它能区分实际情形，而不只是听起来合理。
- 用户陈述当前行为时核对代码及测试，明确指出事实矛盾。例如代码只支持整单取消，而用户描述的是部分取消；先厘清当前事实及目标是否改变，不能混为一谈。

术语及重要决策一旦确定，立即记录到本次讨论记录中，而不是等待最终总结。新定义及未来变更进入 Proposal 的目标设计；现状 DESIGN 和已有术语表按交付规则维护。简单变更只需解决相关概念，无须另建模型文件。

## 按依赖关系分轮讨论

构建设计决策树：一个决定的不同答案会产生、消除或改变后续问题。持续追问到设计明确，而不是按预设清单完成访谈。

1. 找出影响产品行为、架构、接口、状态、关键约束或交付边界的未决问题及依赖关系。每轮列出所有前提已经确定、彼此独立的待决问题；尚依赖本轮答案的问题留到下一轮。规模较大时按主题组织讨论，保持依赖关系。
2. 事实由 Agent 调查，设计决策由用户确定。若某个问题缺少事实，先查代码、文档或执行必要探查；支持委派时可并行调查，其他已具备前提的问题继续讨论。调查结果未返回前，不猜测依赖它的设计结论。
3. 编号提问，说明决策背景、真正存在的取舍、推荐答案及理由。尽量把推荐方案写成用户回答“是”即可确认的明确问题；用户可直接纠正或选择其他方案。不是所有问题都需要列举选项。

每轮示例：

> **Q1 — 凭证归属**：是否由账号管理模块持有凭证，调用方仅使用账号标识？
>
> **推荐**：是。集中管理可以保持权限与更新规则一致。
>
> **Q2 — 历史记录**：删除账号后是否保留使用记录？
>
> **推荐**：保留必要审计记录，但清除有效凭证，以满足审计和安全要求。

以上两问假设前置设计已明确且答案互不依赖。若 Q2 的答案依赖 Q1，则推迟 Q2。

4. 发出一轮问题后等待用户回答，逐项确认回答覆盖的范围；未回答或含混的决定仍然未定。根据答案重算下一轮问题，补充新出现的分支和反例。用户方案同样接受证据、场景和现有架构检验。
5. 每轮维护简洁的设计记录：已确定决定及必要理由、新术语、待解决问题及依赖。长讨论写入空间允许的临时记录；正式提案在讨论收口后编写。记录是规格综合的输入，不是批准或实施授权。

**收口条件**：所有实质影响目标设计的决策均已明确；每个相关领域的关键场景和边界有确定答案；关键可行性有证据；重要风险已有契约化控制或明确接受；不存在被默认为已确定的关键分支。向用户复述完整设计结论，确认双方理解一致；若用户已明确确认相同结论，无须再问。随后综合规格，不在写作时擅自补做决定。

参考思想：[grill-with-docs](https://github.com/mattpocock/skills/tree/main/skills/engineering/grill-with-docs) 的设计决策依赖、分轮讨论和领域建模方法；本技能仍拥有正式提案写作与审批记录。
