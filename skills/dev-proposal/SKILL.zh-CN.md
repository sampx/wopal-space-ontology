# dev-proposal — 业务提案

Proposal（提案）记录本次变更的**确定目标方案、重要决策和验收标准**。先讨论清楚，再编写提案规格。用户负责产品和架构决策，Agent 负责事实调查、方案分析、推荐和准确记录。

## 职责与权威

| 对象 | 职责 |
|---|---|
| PRD / 产品 DESIGN | 产品意图、上层架构及能力边界 |
| 项目/模块 DESIGN | 经核实的已交付行为、职责与契约 |
| GLOSSARY | 标准领域术语与概念定义 |
| Proposal | 本次拟议变更的方案；批准后成为授权变更的目标依据 |
| Issue / Plan / Task | 既定决策内的任务或实施组织、进度与证据 |

设计是一种活动；DESIGN 是正式设计文档。提案阶段读取适用 DESIGN 和 GLOSSARY，分析设计约束、讨论目标方案，**只在 Proposal 中记录尚未交付的目标契约和新术语**。不提前修改项目/模块现状 DESIGN，不从现状文档反向链接未实施或被否决的提案。实施验证后，由 `df-implement` 按 `dev-doc-master` 同步现状文档。

获批 Proposal 只拥有本次授权变更的目标权威；未明确改变的上层架构、既有契约与工程规约继续有效。设计决定确定，内部代码实现自由。

## 何时需要提案

出现任一情况时写 Proposal：

- 存在多条可行路径，需要作出无法从代码或既有授权推导的重要决定；
- 改变已生效的默认值、边界、权限、失败语义或对外契约；
- 部分或全部推翻已实施决定；
- 改变多个项目或模块的共同约定，或需用户重新决定范围。

同时满足以下三点则无需提案：

- 任务或缺陷处于既有决定的范围内；
- 一条 Issue 或直接实施即可明确范围与验收；
- 无需用户重新作出设计决定。

普通 Bug、样式微调、机械改名和保持契约的内部重构直接走 Issue 或实施，不为每项开发制造档案。先搜索同主题活跃与已实施提案；纯事实漂移原地同步，改变决定才新建。

## 工作流概览

按用户请求从对应环节进入，不要求简单的批准、迁移或事实维护重新经历方案讨论。

| 环节 | 核心工作 | 产出或完成条件 |
|---|---|---|
| 1. 调查 | 判断必要性、归属，核实事实、现有决策及上层约束 | 问题和设计依据明确 |
| 2. 讨论 | 领域建模、按决策依赖分轮讨论、检验场景和风险 | 重要决策全部明确 |
| 3. 编写 | 整理提案规格、验收及验证边界，自检 | `Status: proposed` |
| 4. 评审 | 交 `df-proposal-review` 独立评审，解决重要发现 | 提案可供用户决定 |
| 5. 批准 | 用户明确批准范围并选择 Delivery，提交批准记录 | `Status: approved` |
| 6. 交付 | 路由实施；维护用户明确授权的调整 | 交付证据与授权一致 |
| 7. 收口 | 全范围交付且用户验收后迁移，处理历史替代 | `Status: implemented` |

否决和归档按生命周期规则处理。Proposal 不记录 Plan/Task 的执行状态，不由 Agent 自行批准。

## 调查与方案讨论

调查或讨论新提案时读取 `references/discussion.md`；按实际对象选读 `references/practices.md`。已明确的方案直接核对，不重复访谈。

### 调查依据

- 明确用户目标、实际问题和影响范围，区分需求与用户初步提出的解决办法。
- 读取适用 AGENTS.md、产品 PRD/架构 DESIGN、项目主 DESIGN、受影响模块 DESIGN、伴随契约与已有术语表；沿约束关系向上追溯。
- 查阅相关活跃及已实施 Proposal、真实代码和测试；仅调查本次影响范围，事实由 Agent 核实。
- 明确必须继承的职责、依赖、接口、规则和不变量。需要改变既有决定时说明改变项、原因、影响和保留约束，交用户决定；发现设计与代码冲突时指出证据。
- 主动核实关键技术可行性，不能以未验证的关键前提宣称方案就绪。

### 领域建模与决策讨论

- 澄清领域概念、标准术语、关系、职责、状态归属和业务规则；主动指出歧义、重叠与定义冲突。
- 用具体正常、失败及边界场景检验方案，追问会导致不同结果的条件。
- 构建决策树，先解决影响后续分支的决定。每轮只提出前置条件已明确且相互独立的问题；可批量询问。
- 问题编号，说明需要决定什么、真实取舍、推荐答案及理由；尽量让用户回答“是”即可确认。能查证的事实不问用户。
- 每轮等待用户回答，明确哪些决定已经确定，重新计算后续问题；未回答或含混的仍未决。及时记录决定、必要理由、术语和未决问题。
- 长讨论使用空间允许的临时记录，不当作正式提案或实施授权。

收口条件：所有实质影响目标方案的决策已确定，关键场景和边界有答案，关键可行性有证据，重要风险已形成契约化控制或被用户明确接受。复述方案确认双方理解一致；已有明确确认时无需重复询问。任何重要未决问题都返回讨论，不在写作时擅自补决定。

## 编写提案规格

正式动笔前读取 `references/specification.md` 和 `references/lifecycle.md`，使用 `templates/proposal-proposed.md`。编写是综合已经确定的方案，不是重新选型。

### 正文结构

| 章节 | 要求 |
|---|---|
| Problem | 问题、影响与变更目标 |
| Design Basis | 适用的权威设计、继承约束及明确改变的既有决定 |
| Proposal | 确定的目标方案、范围和新增或改变的契约 |
| 专属章节 | 按真实领域组织，按需展开接口、状态、迁移等 |
| Design Decisions（可选） | 有长期价值的最终选择及理由 |
| Acceptance criteria | 可观察、可核查的完成条件 |

保留固定章节的英文标题，正文使用用户偏好语言。以用户场景与实际领域概念组织内容，不机械套用技术目录，不将代码文件清单或实施任务冒充方案。明确排除项及保持不变的行为，引用既有不变契约。

### 契约与决策

每个重要能力及流程采用 `dev-doc-master/references/design-project-guide.md` 的五项契约覆盖标准：主体与触发、协作与时序、权限与不变量、状态与副作用、完整失败结果与恢复。按适用性覆盖，不强制无关章节；用分类实践补足具体领域的要素。

重要选择本身必须写进目标方案。只有难以逆转、缺少背景会令人疑惑且确有取舍的决定才单独记录理由。被放弃的方案不构成实施选项。风险尽量消除；缓解措施写成可验收契约；重要剩余风险和代价明确交用户接受，不保留无价值的讨论过程。

### 验收与自检

- 每项重要变更契约及受影响的既有不变量都应有可证伪验收，覆盖真实入口、正常行为、关键失败与状态副作用。
- 明确通过什么入口和可观察结果证明契约，按适用测试规约选择最低成本且充分的验证层；不提前锁定每条测试命令。
- 逐项核对讨论结论，防止遗漏、弱化、未授权扩张、术语冲突和架构偏离。
- 模拟未参与讨论的实施者：仅看提案及权威引用，能否得到实质一致的职责、接口、状态和行为？仍需猜测的重要决定回到讨论。

自检通过后交独立评审。提案保持 `Status: proposed`，评审通过也不代替用户批准。

## 归属、路径与生命周期

涉及创建、批准、迁移或链接维护时读取 `references/lifecycle.md`，其中包含完整字段与操作细则。

- 产品级：`docs/products/{product}/proposals/`；项目级：`projects/{project}/docs/proposals/`。一项决定只有一个归属；跨项目决定归明确主导者。
- 路径：`<proposals-root>/{lifecycle}/{class}/yyyy-mm-dd-<slug>.md`。日期取首次提出日，slug 用小写 kebab-case（2–4 词），迁移不改文件名。
- 分类闭集：`feature`、`bug-fix`、`simplification`、`architecture`、`process`、`testing`。
- 新提案必填标题、独立 `Status: proposed` 行及 `Class`、`Created`；无中央索引，不另建实施进度字段。

| 目录 | Status | 进入条件 |
|---|---|---|
| proposed/ | proposed | 完成提案编写 |
| proposed/ | approved | 用户明确批准，补齐授权字段 |
| implemented/ | implemented | 全范围交付且用户验收 |
| rejected/ | rejected — 理由 | 明确否决且有防止重复错误的价值 |
| archived/ | implemented | 已不再指导日常工作，加 Archived 日期并冻结 |

归档不是新 Status；拒绝或失去保留价值的文件按规则及删除授权处理，并修好入链。冻结记录不修改正文、不更新事实、不核查出链。

## 批准与交付

用户批准后补齐 `Approved: YYYY-MM-DD — <approver>`、`Authorized scope`（含明确排除项）及 `Delivery`。状态改为 approved，仍在 proposed 目录。

`Delivery` 必须由用户选择：

- `direct`：不拆 Plan，由 `df-implement` 默认通过 `git-worktrees` 建立隔离工作树。
- `plan`：由 `dev-flow` 编排 Plan/Task，管理隔离工作树与共享交付。

根据项目数、并行需求和分批验收等客观事实帮助用户选择，不替用户选路。创建交付分支或工作树之前，先在集成分支单独提交已批准 Proposal，使其成为交付基线。关联 Plan、提交、评审和验收证据以链接记录，不复制进度表。

### 验收前调整

当前获批 Proposal 是授权变更的目标依据，实施不得自行改变决定、范围或验收。用户在测试或验证中明确认可的新决定即是本次交付的授权，无需重复审批。

将调整融入原文件的范围、设计依据、目标方案、验收及受影响的决策理由和剩余风险，优先在改代码前完成，已改代码则在交付前补齐。保持路径、approved 状态和交付基线；主控协调 Plan 与共享文件。直接替换失效内容，不追加新旧并列的方案或过程日志。

### 验收后迁移

仅当批准范围全部交付并经用户验收时，迁入 implemented，改 Status，使用 `templates/proposal-implemented.md`：Proposal → Decision，保留 Design Basis 与有价值的决策理由。`## Consequences` 只写仍约束将来工作的实质性遗留风险与代价，不写验收记录、测试或门禁结果，不复述交付内容；清除计划期标题及表述。

同一交付同步受影响的现状 DESIGN 和术语表，DESIGN 的 Key Decisions 链接已实施记录；修复所有旧路径入链。部分交付保持 approved。单个 Plan 完成不能触发整个 Proposal 迁移。

## 已实施提案的维护与替代

遇到已实施决定时读取 `references/supersession.md`。

- 纯事实漂移：决定、默认值及边界不变，同交付原地同步事实及链接。
- 部分替代：新建提案并在 Problem 链接原记录；新范围全交付且验收前不改原决定，交付时双向链接并说明替代与保留内容。
- 完全替代：新建提案；全交付时吸收原记录仍独有的理由、代价与验证等内容后删除，或因独立历史价值迁入 archived 冻结。
- 已实施决定不能退回 proposed 或原地改成不同决定；归档只添加 Archived 日期并修复外部入链，归档正文永久冻结。

否决仅在有长期防错价值时留存；否则按删除授权删除并修复入链。微小 UI 或机械变更不为归档而归档。

## 校验与交接

每次写入或状态迁移后运行（路径相对本技能目录）：

```bash
python3 scripts/verify-proposals.py <proposals-root>
```

移动、删除时按 lifecycle 指南搜索入链，使用可重复的 `--link-scope <docs-dir>` 校验引用者；跨仓库引用人工核对。退出码 0 只证明当前快照的格式与链接合规，不证明设计正确、历史未被改写或用户已经批准。

独立评审由 `df-proposal-review` 负责，交付实施由 `df-implement` 或 `dev-flow` 路由。本技能只拥有 Proposal 的讨论、写作、授权记录及生命周期维护。
