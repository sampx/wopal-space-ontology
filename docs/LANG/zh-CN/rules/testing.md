# 测试最佳实践

## 目标

- 测试的首要价值是**可靠区分正确实现和错误实现**：坏代码应稳定变红，好代码应稳定通过。
- 同一代码、同一输入和同一受控环境重复执行，应得到确定结果；顺序、机器负载或无关测试不应改变结论。
- 以最低成本获得足够强的错误证明。只有低层测试无法证明的风险，才升级到更昂贵的测试层。
- 测试速度也是质量属性：开发者应先获得局部、快速反馈，再按风险升级到更宽的验证。

## 测试价值

- 每个测试必须保护一个明确的可观察行为、协议或不变量；无法说明“破坏什么实现会让它失败”的测试需要重新设计。
- 断言结果、状态、协议或副作用，不以私有实现细节、调用次数或内部结构代替行为契约，除非这些本身就是公开契约。
- 成功路径不能只断言“没有抛错”；验证输出或最终状态。错误路径要显式制造失败条件，并断言具体错误、原状态和清理结果。
- 对关键逻辑采用 fault-injection / mutation 思维：如果故意引入目标缺陷，现有测试应可靠失败。不要用测试覆盖率百分比代替这种证明。
- 行为代码优先使用 red → green → refactor：先让测试因缺失/错误行为而失败，再实现；测试本身必须先证明能抓到问题。

## 最低成本分层

- 测试层级按**需要证明的边界**选择，不设固定 Unit/Integration/E2E 百分比。
- 优先顺序通常是：纯逻辑 Unit → 边界/Contract → Integration → System/E2E → Release-specific verification。
- 能在低层稳定证明的行为，不因为“更真实”而无意义升级到真实网络、真实进程或完整系统。
- 需要验证真实序列化、协议兼容、进程边界、文件系统、数据库或本地工具协作时使用 Integration/Contract；需要验证外部系统或真实宿主语义时才使用 System/E2E。
- 高层测试发现缺陷后，如果该缺陷能在更低层稳定复现，应补低层回归测试；不要只保留昂贵的系统级复现。
- 发布门禁验证“这个候选是否可交付”的发布不变量，不应无条件重复整套 nightly/full CI。若产品要求 Full CI 作为发布前提，优先复用同一 SHA 已获得的可信结果，而不是重复计算同一套昂贵测试。

## 确定性与隔离

- Unit/Contract 测试默认不得偷偷依赖真实网络、墙上时钟、用户 HOME、当前 cwd、未声明环境变量、固定端口、共享临时目录、随机顺序或机器全局缓存。
- 需要这些依赖时显式注入、冻结、模拟或隔离；如果真实语义本身就是被测对象，则把测试提升到拥有该资源的层级。
- 每个测试只拥有自己创建的资源，并在成功、失败、取消和异常路径都完成清理。不要删除或复用其他测试拥有的状态。
- 修改 process-global / runtime-global 状态（如 env、cwd、locale、全局 mock、singleton cache）必须有明确 owner，并恢复到进入测试前的精确状态。
- 测试不得依赖其他测试留下的数据；任意顺序、单独运行和组合运行应具有相同语义。
- 并发只用于真正独立的测试。只要共享进程全局、端口、路径、数据库记录、mock registry 或生命周期资源，就不能假定并发安全。

## Test Double 与边界

- 不把“Unit”定义为“所有依赖都 mock”。保留稳定、便宜、进程内的真实协作者通常比过度 mock 更有价值。
- Test double 应放在明确的外部系统、传输、时间、随机性或高成本边界，或用于隔离本测试不拥有的副作用。
- 优先通过 dependency injection、service/factory/layer 或显式 seam 注入替身；避免 process-wide monkey patch/module replacement 造成跨测试污染。
- 对跨模块/跨进程协议使用 contract test 锁定双方必须共同满足的事实，避免双方各自 mock 出互相不兼容的世界。

## 异步与时间

- 以**事件、状态或被测操作自身的完成信号**同步；禁止用固定 sleep/delay 猜测“应该已经好了”。
- timeout 只作为失败兜底和死锁保护，不作为 readiness 机制，也不能用单纯增加 timeout 修复 flaky。
- 对一次性就绪、完成或关闭，优先暴露 Promise/Future/Deferred/Latch/callback 等可观察信号；轮询只能观察真实发布状态并具有明确终止条件。
- 使用 fake clock 时必须由测试显式推进并恢复；真实时钟只用于真正验证时间/调度语义的更高层测试。

## Flaky Test 处理

- flaky test 是缺陷，不是“偶尔的 CI 噪声”。先分类根因：产品竞态、测试污染、资源生命周期、错误同步、顺序依赖、真实外部依赖或环境假设。
- 修复必须解释根因并消除触发条件；一次 rerun 成功不是证据。
- **禁止**用以下手段把 flaky 变绿：失败自动 retry/until-green、单纯增加 timeout、弱化/删除断言、缩短观察窗口、固定 sleep、全局串行化整套测试。
- 某个测试因为真实共享资源而必须非并发，可以限制该测试或该 fixture 的并发范围；不能把整个 suite 串行化来掩盖 ownership 问题。
- flaky 修复至少验证原失败场景、独立冷进程以及相关组合/顺序执行；验证组任一次失败都表示问题尚未解决。
- Full suite 仍失败时读取失败证据并重新分类，不得循环重跑直到出现绿色结果。

## 性能与验证成本

- 优先运行能回答当前问题的最小测试集合：目标测试 → 所属模块/包 → 相关组合/集成 → 全量 suite。
- 不要在每次小修改后重复运行昂贵 system/E2E；在风险边界变化或准备交付时再升级验证范围。
- 项目应为关键测试入口维护可解释的性能基线或预算；明显变慢需要说明原因并修复无意义的真实 I/O、重复 setup 或重复 suite。
- 测试并发是降低独立测试成本的手段，不是正确性的前提。测试必须先做到隔离，再并发。
- CI 应让失败尽量靠前、反馈尽量局部；nightly/full CI 负责全仓健康扫描，release gate 负责发布候选特有风险，避免同一工作在多个 gate 无理由重复。

## 外部系统与共享资产

- 真实外部账号、仓库、服务或固定拓扑若必须长期存在，应作为受控测试资产只读复用；不要为了单次测试随意破坏或重建共享资产。
- 测试创建的临时分支、文件、数据、容器、进程、监听器和 socket 必须由该测试清理，不留下跨运行残留。
- 真实凭证和生产数据不得写入 fixture、日志或断言输出；外部系统失败应被区分为产品失败、环境失败和测试基础设施失败。

## 评审检查

测试相关变更在交付前至少回答：

1. 这个测试保护什么行为或不变量？
2. 什么实现缺陷会让它可靠失败？
3. 是否用了能证明该行为的最低成本层级？
4. 是否依赖未声明的时间、网络、环境、路径、全局状态或顺序？
5. 异步同步是否基于事件/状态，而不是等待时间？
6. 所有资源与 process-global 状态是否有 owner，并在异常路径恢复？
7. 并发是否只发生在真正独立的状态之间？
8. flaky 修复是否有根因证据，而不是 retry/timeout/弱断言/全局串行化？
9. 验证是否从低成本到高成本逐层升级，而非直接依赖最贵的 suite？
10. 新测试的成本是否与它证明的风险相称？
